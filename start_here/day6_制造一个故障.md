# D6 · 制造一个故障（80 分钟）

> **今天做的事：让车"生病"，然后看它怎么报警、怎么记录病历。**
>
> 这是测试工作最有成就感的环节 —— 你亲手制造一个问题，然后验证系统**该不该、能不能**发现它。

---

## 先说清楚：一个"故障"要经过哪些环节

```
① 制造异常        ② 系统感知        ③ 显示给人看      ④ 记录病历
水温升到 125℃  →  车检测到"超限"  →  仪表水温灯亮   →  记下 P0116
（你做的事）      （ECU 的活儿）      （给司机看）      （给维修工看）
```

**这四步，一步都不能少。** 少任何一步都是缺陷：

| 如果缺哪一步 | 后果 | 这就是你要抓的 bug |
|---|---|---|
| ② 系统感知不到 | 灯不亮、没记录 | 传感器/检测逻辑有问题 |
| ③ 灯不亮 | 司机不知道，发动机可能报废 | 显示逻辑问题（**严重**） |
| ④ 没记录 | 维修工查不出原因 | DTC 记录逻辑问题 |

> 🎯 **今天你要验证的就是：这四步是否都正常工作。**

---

## 第 1 步：起三个程序（车、仪表、诊断仪）

开**三个终端**，都在项目根目录：

**终端 1 —— 车**：

```bash
python simulators/ecu_sim.py --speed 60
```

**终端 2 —— 仪表（要能看见灯）**：

```bash
python simulators/dashboard.py
```

**终端 3 —— 诊断仪**：

```bash
python simulators/uds_client.py
```

> 💡 三个窗口并排放，方便同时看。

---

## 第 2 步：确认"现在没病"

**在终端 3（诊断仪）** 输入：

```
19 02 ff
```

**应该看到**：`无故障`（空列表）。

**看终端 2（仪表）**：顶部那一排警告灯 **应该全是灭的**。

> ✅ 这两条先记下来：**"无故障时，无 DTC + 灯全灭"**。
> 这是你的**基线** —— 后面出问题时，就是和这个基线对比。

---

## 第 3 步：让它"发烧"（制造水温过高）

**切到终端 1（车）**，输入：

```
coolant 125
```

按回车。（意思是：把目标水温设成 125℃，而正常范围是 80~105℃）

**然后盯住终端 2（仪表）看 20 秒**。你会看到（数值每次略有浮动）：

```
0~7 秒：水温数字慢慢往上爬（90 → 100 → 110 → 120...）
        灯还是灭的（还没进入"连续确认"）
约 8 秒：水温越过 120℃
约 9~10 秒：水温报警灯亮起 🔴
```

> ⏱️ **为什么不是立刻亮？** 两个原因：
> 1. **物理原因**：水温是一阶惯性（时间常数约 4 秒），从 90℃ 升到 120℃ 要 8 秒左右
> 2. **逻辑原因**：系统要**连续 2 个诊断周期**（2 × 0.5s）都检测到超限，才确认故障（防误报）
>
> **这两点合起来 ≈ 9~10 秒；脚本里给 20 秒以上超时是为了留足余量。**

---

## 第 4 步：查"病历"（读故障码）

**切到终端 3（诊断仪）**，输入：

```
19 02 ff
```

**这次你会看到**：

```
→ 正响应 SID=0x59 payload=02ff011600af
```

**怎么读**：

| 部分 | 意思 |
|---|---|
| `59` | "读故障码"的响应 |
| `02ff` | 把你问的子功能原样回给你（`19 02 FF` 的后半段） |
| `0116` | 故障码的编码（翻译过来是 **P0116**） |
| `00af` | **状态字节** —— 十六进制 `AF`，用二进制看是 `1010 1111`，每一位代表一个状态 |

**状态字节 `0xAF` 里比较重要的位**：

| 位 | 含义 | 现在 |
|---|---|---|
| `0x01` | 本轮检测到故障（testFailed） | ✅ 是（水温确实还高） |
| `0x02` | 本操作周期内失败过（testFailedThisOperationCycle） | ✅ 是 |
| `0x04` | 待定（pending） | ✅ 是 |
| `0x08` | **已确认（confirmed）** | ✅ 是 ← **这个位决定"正式记录"** |
| `0x20` | 清除后失败过（testFailedSinceLastClear） | ✅ 是 |
| `0x80` | **请求点亮警告灯（warningIndicatorRequested）** | ✅ 是 ← **这个位决定"灯亮不亮"** |

> 💡 完整值 = `0x01 + 0x02 + 0x04 + 0x08 + 0x20 + 0x80` = **`0xAF`**（如上表）；
> 你实际看到的可能是 `00af` / `00AE` 等略有差异的值（取决于检测进行到哪一步），
> 但 `0x08` 和 `0x80` 都应该是 1 —— 这是"已确认 + 点灯"的标志。
>
> 💡 详细解释见 [docs/04_DTC详解.md](../docs/04_DTC详解.md)（现在不用全懂）。

---

## 第 5 步：清除故障（模拟"4S 店清码"）

**在终端 3** 输入：

```
clear_dtc
```

**你会看到**：响应成功。

**切到终端 2（仪表）看**：水温灯 **应该灭了**（因为 DTC 被清了）。

再输入 `19 02 ff` → **应该显示无故障**。

---

## 第 6 步：**关键实验 —— 清码 ≠ 修好**

等等 15 秒，**再看一次**：

```
19 02 ff
```

**你会发现：P0116 又回来了！**

### 为什么？

```
你只是"清了记录"，但**水温还是 125℃**（你根本没修它）。
所以系统过一会儿又会检测到 → 又记录一次。
```

**这就是真实世界的经典场景**：
> "我的车亮了故障灯，去 4S 店清了个码，过了几天又亮了。"

**不是 4S 店坑你，是故障真的还在。**

> 🎯 **测试要验证的正是这个**：
> 清码后，如果**故障条件还在**，系统**必须能重新检测出来**。
> 如果清完码就再也不报了 → 那才是真 bug（检测能力被清坏了）。

## 第 7 步：跑一遍"自动化版本"

你刚才手工做了一套完整流程（制造→确认→读码→清码→重建），
项目里已经把这条路写成自动化用例了：

```bash
python -m robot --outputdir results scenarios/04_dtc_lifecycle.robot
```

**看 4 个用例**：

```
故障条件持续时应记录为 confirmed 状态    ← 对应第 3、4 步
清除 DTC 后记录应归零                    ← 对应第 5 步
故障条件仍在时 DTC 应重新记录             ← 对应第 6 步
仪表警告灯应与诊断记录一致                ← 灯和 DTC 要同时对上
```

**这就是"手工操作 → 自动化"的完整翻译**。你已经走过了整条路。

## 🆘 卡住了怎么办

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 灯一直不亮 | 水温还没到 / 等的时间不够 | 多等 10 秒；确认终端 1 里 `coolant 125` 输入成功了 |
| `19 02 ff` 一直无故障 | 同上 | 同上 |
| 灯亮了但读不到 DTC | 读得早了一点 | 再等 2 秒重读 |
| 清除后灯不灭 | 用的不是 `clear_dtc` / DTC 没清掉 | 看响应是否成功；重试 |
| 仪表窗口关了 | — | 重开 `python simulators/dashboard.py`（车不用重启） |

## 📌 今天你学到的事

1. **一个故障的完整链路**：制造 → 感知 → 显示 → 记录，四步缺一不可。
2. **故障不是"立刻"就报的**：有物理延迟 + 逻辑确认周期（防误报）。
3. **DTC = 病历**，带状态位（告诉你"现在还在不在"）。
4. **清码 ≠ 修好** —— 故障条件还在，就会重新记录。
5. **测试的价值**：验证这四步都对，且异常时该报就报、该灭就灭。
