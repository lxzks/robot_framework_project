## 先看个生活场景

**场景**：你在家等外卖。

| 做法 | 问题 |
|---|---|
| ❌ **定时开门**：睡 30 分钟，然后去开门 | 早到了外卖凉了（白等）；晚到了你没听见（错过） |
| ✅ **反复看**：每 2 分钟瞄一眼门口，看到骑手就开门；超过 60 分钟还没到就打客服 | **到得早就早吃、到得晚就多等一会儿、真出问题能报警** |

**自动化测试的"等待"，和等外卖一模一样**：

```
❌ Sleep 8s：固定睡 8 秒 —— 猜时间
✅ 轮询：反复问"到了吗？"，到了就继续，超时就报错 —— 不猜
```

## 第 1 步：看看项目里的"正确等法"

项目已经把"反复问"封装成一个关键字了：

```
Wait Until Signal In Range    EngineData    VehicleSpeed    50    70    timeout=20
```

**读法**：
- `EngineData` 报文里的 `VehicleSpeed` 信号
- 等到它进入 **50 ~ 70** 这个范围
- **最多等 20 秒**（超时就报错）

**它内部在做的事**（不用你写，但要知道）：

```
开始计时
循环：
    读一次车速
    如果在 50~70 之间 → 立刻返回（继续往下走）
    如果不在 → 等 0.2 秒，再读一次
    如果超过 20 秒 → 报错："20 秒内没进入范围"
```

## 第 3 步：亲眼看看"为什么轮询更稳"

做一个实验（3 分钟）：

**实验 A：把目标车速改成 200（永远达不到）**

```
Suite Setup      Start Vehicle Environment    speed=200
```

同时把等待范围改成 `190    210`，跑：

```bash
python -m robot --outputdir results test_car.robot
```

**你会看到**：等满 20 秒后报错 —— **明确告诉你"20 秒内没等到"**。

**对比**：如果用 `Sleep 8s`，8 秒后读到 64，断言失败，你会以为是"断言写错了"，
而不是"车根本没到目标速度"。**这就是轮询的价值：它把"超时"和"值不对"分开了。**

> 把 `speed=200` 改回 `60`，再跑一次确认恢复 PASS。

## 第 4 步：理解"超时时间"该怎么定

`timeout=20` 不是随便写的。**正确做法：按"物理过程最长时间 + 余量"定。**

本项目里的例子：

| 你要等什么 | 物理上要多久 | 超时定多少 | 为什么 |
|---|---|---|---|
| 车速从 0 到 60 | 60 ÷ 8 ≈ **7.5 秒** | **20 秒** | 7.5 秒 + 启动开销 + 余量 |
| 水温从 90 到 120 | 一阶惯性，约 **15 秒** | **25 秒** | 15 秒 + 2 个诊断周期确认 + 余量 |
| 故障确认（要 2 个诊断周期） | 2 × 0.5 = 1 秒 | 一般 5 秒起 | 留足 |

> 🎯 **判断标准**：你的超时应该是"**正常情况下的 2~3 倍**"。
> 太短 → 偶发失败；太长 → 真出问题时等太久。

## 📌 今天你学到的事

1. **等**有两种：`Sleep`（猜时间，会 flaky）和**轮询**（问状态，稳定）。
2. **轮询的三要素**：等什么、等多久、超时了说什么。
3. **超时不是随便设的**，要按物理过程算。
4. **flaky 测试（时好时坏）绝大多数是"猜时间"造成的** —— 你现在有这个直觉了，这很值钱。
