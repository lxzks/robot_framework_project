## 一、闭环测试的思路

前面 5 个练习都是"单点验证"（读一个值、发一个请求）。真实工作的测试是**场景**：

```
造场景  →  验证感知  →  验证记录  →  执行干预  →  验证恢复
（水温125）（灯亮）    （DTC确认）  （清除DTC）   （灯灭/重建）
```

这条链跨了 **3 个子系统**：CAN 信号（ECU 发）→ 仪表显示（GUI/headless）→ 诊断（UDS）。
测试的价值正在于**验证它们串起来是对的**，而不是各自单独对。

**真实对照**：客户投诉"水温灯偶尔亮，清了码过几天又亮" —— 一台架上跑这个闭环，
就能回答"是真故障还是误报"。

## 二、任务

在 `exercise.robot` 写一个**完整闭环套件**（用 `Suite Setup` 造故障场景）：

### 前置配置
```robotframework
Suite Setup      Start Vehicle Environment    coolant=125
Suite Teardown   Stop Vehicle Environment
```

### 四个用例（按时间顺序）

| # | 用例 | 做什么 | 关键关键字 |
|---|---|---|---|
| 1 | 水温超限应点亮水温报警灯 | 等仪表水温灯亮（要等水温爬升+故障确认，给 25s） | `Telltale Should Be Lit` |
| 2 | 诊断仪应能读到 confirmed 的 P0116 | 轮询等 DTC 列表出现 P0116 | `Wait Until Keyword Succeeds` + `DTC List Should Contain` |
| 3 | 清除 DTC 后报警灯应熄灭 | 清除 → 断言灯灭 | `Clear DTC` + `Telltale Should Be Off` |
| 4 | 故障仍在时 DTC 应重新确认 | 清完别急着走 —— 故障条件还在，系统应该重新记录 | `Wait Until Keyword Succeeds` |

**注意**：第 4 个用例是"恢复性验证" —— 清除只是重置状态机，不是修好故障。
真实维修场景里"清码后灯灭了，开两天又亮"就是这个现象。

## 三、这道题训练什么

| 能力 | 体现在哪 |
|---|---|
| **跨系统断言** | 同一个故障在"仪表视角"和"诊断视角"都要能看到 |
| **场景时序** | 水温爬升（物理惯性）→ 故障确认（2 个诊断周期）→ 点灯，每个环节都有延迟 |
| **干预与恢复** | 清 DTC 是"干预"，之后验证系统仍能重新检测，说明没被清坏 |
| **超时设计** | 每个等待的超时值都要有物理依据（25s = 水温 90→120 约 8s + 2 个确认周期 + 余量） |

## 四、怎么跑

```bash
python -m robot --outputdir results/training training/L6_full_cycle/exercise.robot
```

这个套件单跑约 **15~20 秒**（要等水温爬升约 8s + 2 个确认周期，再算环境启动/清理），别以为卡住了。
