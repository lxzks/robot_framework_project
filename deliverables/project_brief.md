## 五、技术亮点（面试官最可能追问的 4 个）

### 1. 为什么用 UDP 组播模拟 CAN 总线，而不是买硬件？

> 硬件（CANable 约 100 元）能验证物理层，但**跨进程、多节点、可复现**的需求用软件更合适。
> 我把总线抽象成一层，`bus.py` 里只需改 `interface`（`udp_multicast` → `socketcan`/`serial`）
> 就能接真实硬件，**上层代码零改动** —— 这是真实项目的做法（硬件在环 HIL 也是这个思路）。

### 2. 怎么保证测试不是"假通过"？

> 三层保证：
> ①**断言强度**：不用"值在 0~8000 范围内"这类永远为真的断言，改用**联动断言**（如"转速 ≈ 车速 × 80"），
> 参数写错立刻暴露；
> ②**需求追溯**：每个用例挂需求编号，工具反查"哪条需求没被覆盖"；
> ③**负向覆盖**：权限拒绝（NRC）、未解锁写入、刷写失败路径都单独验证。
> 我还主动做过"弱断言扫描"，揪出过 2 处恒真断言（`count >= 0`）并改成交叉校验。

### 3. 需求变了怎么办？

> 需求清单是 YAML（带编号/来源/验证方法），用例用 `[Tags]` 挂需求编号。
> 需求一改，跑 `trace_matrix.py` 就能列出"受影响的用例"和"未覆盖的需求"。
> 这也是我做这套追溯体系的原因 —— 手工维护 Excel 迟早会失真。

### 4. 你项目里最难的一个 bug？

> **UDP 组播的"自发自收"导致节点永远无法睡眠。**
> 现象：做网络管理时，ECU 熄火后应用报文停了、NM 报文也在发，但**永远进不了睡眠** ——
> "总线静默"判定始终不成立。
> 根因：`python-can` 的 `udp_multicast` 接口**不支持 `receive_own_messages` 过滤**，
> ECU 收到了自己发出的 NM 帧，把"总线活动时间"不断刷新。
> 修复：监听时显式忽略本节点发送的 ID 集合（`SELF_TX_IDS`）。
> **教训**：仿真环境的传输层语义 ≠ 真实总线语义，排查时先问"这个现象在真车上会发生吗"。

## 六、这个项目的局限（主动披露，体现诚实）

| 局限 | 说明 | 真实工作怎么补 |
|---|---|---|
| 无物理层验证 | 只做应用层，不测电压/终端电阻等 | 台架 + 示波器/CANoe |
| DTC 覆盖 3/5 | P0117/P0135 需特殊工况 | 补充低温箱、手动注入 |
| 功能安全仅教学级 | E2E 保护/看门狗/降级机制做了验证（32 章），但无 ISO 26262 安全分析（HARA/FMEA）与完整 ASPICE 证据链 | 入职后按 FuSa 流程补安全分析 |
| 未接真实硬件 | 全部为软件仿真 | 换 `bus.py` 的 interface 即可 |
| 时长与规模 | 单机约 6 分钟跑完 276 用例（本机实测 359~380s（多次实测）；CI 双版本矩阵无缓存约 8 分钟/版本） | 真实项目用例量在数千级，需并行化 |

> 💡 面试时**主动讲局限**，说明你知道边界在哪 —— 这比"我的项目完美"可信得多。

```bash
# 1. 建虚拟环境 + 装依赖
python -m venv .venv
.venv\Scripts\activate            # Windows；Linux/macOS 用 source .venv/bin/activate
pip install -r requirements.txt

# 2. 验证环境
python training/check_all.py          # 预期：12/12 通过

# 3. 一键跑全量（测试 + 报告 + 覆盖率 + 追溯矩阵）
python run_tests.py --report
# 产物：results/test_summary.html / coverage.html / trace_matrix.html
```
