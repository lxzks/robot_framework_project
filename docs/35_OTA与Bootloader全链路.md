## 35.0 为什么 OTA 是"测试工程的分水岭"

刷写/OTA 测试和普通功能测试最大的差别：

| 维度 | 普通功能测试 | OTA / 刷写测试 |
|---|---|---|
| 失败代价 | 功能不可用，可重试 | **可能变砖**、无法启动、需要返厂/售后解锁 |
| 时序依赖 | 少 | 强（会话/安全/下载/传输/校验/复位有严格先后） |
| 异常路径 | 相对少 | 极多：坏包、断网、断电、存储满、版本不兼容、回滚失败… |
| 安全要求 | 一般 | 极高（固件签名、安全启动、防降级/防篡改） |
| 测试设计 | 正向为主 | **负向/异常路径为主**（本章 17 套件 10 条里 5 条负向/异常：断电回滚、坏包×3、丢块重传） |

> 💡 面试可讲的判断："OTA 测试做得好不好，不看你能不能刷成功，而看**刷坏了能不能恢复**。"
> 本章 17 套件的 ③、⑥~⑨ 条就是围绕"坏包/中断/回滚/重传"设计的。

## 35.1 先分清三个词：OTA、刷写、Bootloader

| 术语 | 含义 | 本项目对应 |
|---|---|---|
| **刷写（Flashing）** | 通过 UDS 把固件写进 ECU Flash 的动作：0x34/0x36/0x37 + 0x31 校验 | `simulators/ecu_sim.py` 的 Bootloader 状态机 |
| **Bootloader（BL）** | ECU 里一段"永远不被升级"的小程序，负责启动 APP、接收新固件、校验、切换分区 | ECU 的"编程会话 + 0x34/36/37"行为 |
| **OTA（Over-The-Air）** | 完整链条：云端打包/签名 → 车端下载 → 包校验 → 预编程检查 → 刷写 → 复位激活（可能还含灰度、断点续传、回滚） | `simulators/ota_server.py` + `libraries/OtaLibrary.py` + `tests/robot/17_ota_bootloader.robot` |

一句话：**刷写是 OTA 的最后一步**。OTA 测试必须把"云端 → 车端 → ECU"整条链路都测到，
否则会出现"云端包没问题、刷写也没问题，但版本没生效 / 断电后变砖"这类线上事故。

## 35.2 Bootloader、APP 分区与 A/B 方案

### 35.2.1 单个 ECU 里的两个"程序"

```
┌────────────────────────────────────────────────────────────┐
│ ECU Flash                                                   │
│  ┌──────────────────────┐  ┌────────────────────────────┐  │
│  │ Bootloader（Boot 区） │  │ 应用程序 APP（App 区）      │  │
│  │ - 上电最先运行       │  │ - 业务功能（动力/诊断/通信） │  │
│  │ - 接收/校验/写入固件 │  │ - 可被整体替换              │  │
│  │ - 切换 A/B 分区      │  │                            │  │
│  │ - 通常不可升级/需签名 │  │                            │  │
│  └──────────────────────┘  └────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

**为什么要分 Bootloader 和 APP**：APP 可以放心刷坏——只要 Bootloader 还在，
上电后 BL 发现 APP 校验失败就停在编程模式，等诊断仪重新刷；BL 自己刷坏了才是真变砖。

### 35.2.2 A/B 双分区（本章的重点概念）

```
单分区（很多老 ECU）：          A/B 双分区（现代 ECU/车机常见）：
  ┌────────────┐                ┌────────────┐  ┌────────────┐
  │   APP      │ 直接覆盖       │  Slot A    │  │  Slot B    │
  │            │ → 刷到一半断电  │ 当前运行    │  │ 新固件写入  │
  └────────────┘   就两头不是   └────────────┘  └────────────┘
                   （变砖风险）     ↑ 启动时选择校验通过的那个
```

A/B 的核心价值：**刷写失败/断电时，旧分区从未被破坏 → 启动仍能跑旧版本 = 天然回滚**。

本项目在教学上模拟了 A/B 语义（不真写双分区，但**行为等价**）：

1. 刷写过程只把数据收进 `flash_state`（内存里的"待写区"），**不动当前运行版本**；
2. `31 01 FF00` 校验通过 → 只登记"待激活版本"（`_pending_activation`），版本 DID 仍然返回旧值；
3. `11 01` 复位 → Bootloader 才"切槽"：版本 DID（F195）更新为新版本、`_active_slot` 翻转 A↔B；
4. 校验失败/中途复位 → 没有待激活记录 → 版本保持旧值（回滚）。

> 这就是 17 套件 ④ 断言"刷写成功后版本仍是 v1.0.0"、⑤ 断言"复位后才变 v1.1.0"的原因 ——
> **A/B 生效点在复位，不在刷写完成**。理解这一点，才能设计出"断电不变砖"的测试。

## 35.3 刷写的三个阶段：预编程 → 编程 → 后编程

真实 Bootloader 刷写流程被严格分成三个阶段（OEM 流程文件里通常这么叫）：

| 阶段 | 目的 | 典型服务 | 本项目实现 |
|---|---|---|---|
| **预编程（Pre-programming）** | 确认"现在可以刷"：车速=0、档位 P、电压正常、无关键故障、版本兼容 | `10 03`（扩展会话）、`31 01 0203`（条件检查）、`31 01 0202`（依赖检查）、读版本 DID | `_svc_routine_control` 的 0x0203 / 0x0202 |
| **编程（Programming）** | 真正下载：编程会话 + 解锁 + 0x34/0x36/0x37 | `10 02`、`27 01/02`、`34`、`36`×N、`37` | `_svc_request_download` / `_svc_transfer_data` / `_svc_request_transfer_exit` |
| **后编程（Post-programming）** | 校验 + 生效：完整性检查、复位、读版本确认 | `31 01 FF00`、`11 01`、`22 F195` | `_svc_routine_control` 的 0xFF00 + `_svc_ecu_reset` 的激活逻辑 |

### 35.3.1 完整时序（本项目 17 套件 ④ 的实际流程）

```
OTA Agent / 测试库                     ECU（Bootloader 视角）
  │ 10 03（扩展会话）                    │
  │ ────────────────────────────────────>│
  │ 31 01 02 03（预编程条件检查）         │  车速=0？电压 10.5~15.5V？
  │ <────────────────────────────────────│ 通过 → 71 01 02 03 00；不满足 → 7F 31 22
  │ 10 02（编程会话）                      │
  │ ────────────────────────────────────>│
  │ 27 01 / 27 02（安全解锁）              │
  │ 31 01 02 02（编程依赖检查）            │ 无未完成下载 → 71 01 02 02 00
  │ 2E F1A1 <目标版本>（暂存）             │
  │ 2E F1A2 <期望CRC32>（暂存）            │  ← 教学扩展：给 FF00 做第二道校验
  │ 34 00 44 08000000 00000200（512B）     │ → 74 20 04 00（单块上限 1024B）
  │ 36 01 <64B> … 36 08 <64B>              │ → 76 01 … 76 08（块序号回显）
  │ 37（退出传输）                         │ → 77
  │ 31 01 FF00（完整性校验）                │ 长度 + CRC32 → 71 01 FF 00 00/01
  │ 11 01（复位）                          │ 切 A/B 槽、激活新版本、清刷写状态
  │ 22 F195（读版本）                      │ → 62 F1 95 "v1.1.0"
```

顺序错误会有明确 NRC（这也是测试点）：
- 没进编程会话就发 `34/36/37` → `0x7F`（当前会话不支持）；
- 编程会话但没解锁 → `0x33`；
- 没 `34` 就发 `36` → `0x24`（序列错误）；
- 块序号跳号/丢块 → `0x73`（wrongBlockSequenceCounter）；
- 没 `36` 就 `37` → `0x24`。

## 35.4 关键服务与例程（本项目实现约定）

### 35.4.1 0x34 / 0x36 / 0x37（刷写三件套）

```
34 00 44 <addr 4B> <size 4B>   请求下载（dataFormat=00，ALFID=44）
  → 74 20 04 00                 lengthFormat=0x20，单块上限 1024B
36 <block 1B> <data …>         传输数据（块序号 1,2,…,0xFF,0x00,1…）
  → 76 <block>                 回显块序号（测试必须断言回显！
36 …（重复 N 块，每块 ≤ 单块上限）
37                             退出传输
  → 77
```

> 本项目在 06 套件里已有这套的"协议一致性"验证（单块上限/序号错乱 NRC 0x73/未下载先传 0x24 等）；
> 17 套件则从 **OTA 业务流程**角度再走一遍（含真实 512B 镜像、CRC 校验、版本切换）。

### 35.4.2 0x31 例程（三个和刷写相关的 RID）

| 请求 | RID | 作用 | 本项目响应 |
|---|---|---|---|
| `31 01 0203` | 预编程条件检查 | 车速=0、电压正常、无未完成下载 | 通过 `71 01 02 03 00`；不满足 **NRC 0x22** |
| `31 01 0202` | 编程依赖检查 | 编程会话已进、下载前状态干净 | `71 01 02 02 00`，有未完成下载 → `0x24` |
| `31 01 FF00` | 检查编程完整性 | 长度 + CRC32 校验（本项目扩展） | `71 01 FF 00 00`=通过 / `...01`=失败 |

> 为什么 0x0203 不满足要回 **NRC 0x22（conditionsNotCorrect）** 而不是正响应里带失败结果？
> ISO 14229 的惯例：**"能不能执行这个例程"的前置条件不满足 → 负响应 0x22**；
> 而例程执行完成但结果失败，才用正响应 + routineStatusRecord。测试要能区分这两者。

### 35.4.3 完整性校验（FF00）为什么既校验长度又校验 CRC？

- 只校验长度：坏数据只要**长度对**就能通过 → 会把损坏镜像激活（本项目旧实现就是这样）。
- 加 CRC32 之后：长度对但内容坏 → 校验失败 → **保持旧版本**。
- 本项目通过 `0x2E F1A2` 把"期望 CRC32"暂存进 ECU（教学扩展；真实 Bootloader 通常
  把 CRC/签名放在下载元数据或 Flash 尾部，由 BL 自己计算比对）。

17 套件 ⑥ 用两条断言覆盖"两道防线"：
1. OTA Agent 侧：manifest CRC 错 → 下载后本地校验失败 → `Should Refuse Image`（压根不写 ECU）；
2. ECU 侧：`Force Flash Corrupted Image` 绕过 Agent 校验强写 → `31 01 FF00` 返回 `01` → 拒绝激活。

## 35.5 版本 DID 与"生效"语义

| DID | 名称 | 读写 | 语义 |
|---|---|---|---|
| **F195** | 应用软件版本 | 只读 | 当前**运行**的 APP 版本（v1.0.0 → 刷写成功+复位后 v1.1.0） |
| **F1A3** | Bootloader 版本 | 只读 | 刷写能力的载体版本（BL-1.0.0）；OTA 包可要求最低 BL 版本 |
| **F186** | 硬件版本 | 只读 | 硬件平台标识（HW-VISTEON-P7），用于**版本兼容性判断** |
| F1A1 | OTA 目标版本暂存 | 可写（0x2E） | 刷写流程写入"这包是什么版本"，FF00 通过后作为激活目标 |
| F1A2 | 期望 CRC32 | 可写（0x2E） | 刷写流程写入期望校验值，FF00 用它做 CRC 校验（一次性） |

**版本生效时序（A/B 语义，必须背下来）**：

```
时刻             F195 值     _pending_activation      说明
──────────────────────────────────────────────────────────────
刷写前           v1.0.0      None                     当前运行旧版本
31 01 FF00 通过   v1.0.0      {"version": "v1.1.0", …}  新版本已写好、待激活
11 01 复位        v1.1.0      None                     切槽成功、激活
31 01 FF00 失败   v1.0.0      None                     校验失败、旧版本不动（回滚）
中途断电/复位     v1.0.0      None                     flash_state 清除、旧版本不动
```

> 测试价值：如果实现错误地在 **FF00 通过时**就把 F195 改成新版本，会产生"版本显示已升级但
> 实际没重启仍是旧程序"的假成功；17 套件 ④ 的 `Software Version Should Be v1.0.0` 专门抓这个。

## 35.6 回滚与断点续传

### 35.6.1 三类"回滚"要分清

| 类型 | 触发 | 本项目验证 |
|---|---|---|
| **刷写失败回滚** | 校验失败/坏包 → 不激活，旧版本继续运行 | ⑥⑦⑧：坏包拒绝后版本保持（当前运行版本 v1.1.0 不被坏包改变） |
| **断电/复位回滚** | 刷写中途断电 → flash_state 丢失 → 旧版本启动 | ③：`Simulate Power Loss During Flash 2` + `Should Rollback To Version v1.0.0`（**顺序关键：必须在成功刷写之前**，否则运行版本已等于目标版本，断言无法区分"回滚成功"与"错误激活"） |
| **应用级回滚**（真实项目） | 新版本启动失败/看门狗复位 → BL 回退到上一稳定版本 | 教学简化（A/B 语义已覆盖"旧版本不被破坏"这一本质） |

### 35.6.2 断点续传（Resume）的两个层面

1. **OTA 下载层（本项目实现）**：云端支持按 `offset/length` 返回数据（等价 HTTP Range）。
   网络断了重新连上后，从已下载的 offset 继续，不用从头下。
   17 套件 ⑨ 用"前 128B + 从 128B 续传"拼接，并断言拼接后 **CRC32 与 manifest 一致**。
2. **刷写层（本项目实现）**：丢块重传。块序号机制让 ECU 能识别"这块我收过/没收过"：
   丢块后下一块序号不连续 → ECU 回 `0x73`，测试端补发正确块后继续。
   17 套件 ⑨ 用 `Flash With Retry skip_block=2` 模拟。

> 真实项目的挑战：断点续传要解决"已写入 Flash 的数据是否可信"（掉电后 Flash 数据可能半写），
> 所以真实实现通常"断电后从块边界重新校验收到的数据"或"整包重试"。

## 35.7 CRC32 与签名：教学简化 vs 真实安全链

| 层次 | 本项目（教学） | 真实量产 |
|---|---|---|
| 包完整性 | **CRC32**（32 位，能查传输错误，不能防篡改） | SHA-256 摘要 + **RSA/ECDSA 公钥签名**（防篡改、防伪造） |
| 来源认证 | 无 | 云端证书 + TLS（HTTPS/mTLS）+ 车端证书 |
| 启动校验 | 校验通过就激活 | **Secure Boot**（逐级验签：BL 验 APP，HSM 验 BL） |
| 防降级 | 版本号靠 manifest 比较 | 安全版本计数器（anti-rollback counter）+ HSM 存储 |
| 回滚保护 | A/B 语义 | A/B + 回滚计数 + 失败自动回退 + 售后回滚许可 |

> 教学项目用 CRC32 是因为它能把"整条链路 + 两道防线 + A/B 回滚"讲清楚且零依赖；
> 面试时**一定要主动说清"真实项目还要签名/安全启动/防降级"**，否则会被认为不懂安全。

## 35.8 本项目实现

### 35.8.1 文件与角色

```
simulators/ota_server.py        OTA 云端 mock（独立进程，TCP 127.0.0.1:8080）
                                 manifest / download(offset,length) / inject / reset / stats
simulators/ecu_sim.py           ECU + Bootloader 状态机（预编程/编程/后编程、A/B、版本 DID）
libraries/OtaLibrary.py         OTA Agent + 诊断仪关键字（SUITE 作用域）
tests/robot/17_ota_bootloader.robot  10 条端到端用例
resources/common.resource       起 ECU + headless 仪表（套件 Teardown 回收）
```

### 35.8.2 OTA 云端 mock 协议（JSON 行）

| 请求 | 响应 | 说明 |
|---|---|---|
| `{"cmd":"manifest"}` | `{"ok":true,"manifest":{...}}` | 版本/旧版本/大小/分块/CRC32/目标 ECU/兼容性/回滚标志 |
| `{"cmd":"download","offset":N,"length":M}` | `{"ok":true,"data":"<hex>"}` | 按 Range 下载分块（支持断点续传） |
| `{"cmd":"inject","kind":"crc"}` | `{"ok":true,"injection":"crc"}` | 坏包注入：`crc` / `size` / `version` |
| `{"cmd":"reset"}` | `{"ok":true,"injection":"none"}` | 恢复正常包 |
| `{"cmd":"stats"}` | `{"ok":true,"stats":{...}}` | 下载次数/字节数/注入状态 |
| `{"cmd":"quit"}` | `{"ok":true}` | 关闭连接 |

固件参数（固定、可复现）：镜像 **512B**、分块 **64B**、旧版本 `v1.0.0`、目标 `v1.1.0`、
Bootloader `BL-1.0.0`；端口可用 `OTA_HTTP_PORT` 覆盖。

### 35.8.3 ECU 侧 Bootloader 状态机（`simulators/ecu_sim.py` 新增部分）

| 状态/字段 | 作用 |
|---|---|
| `flash_state`（已有） | 本次下载的地址/大小/已收字节/块序号 + 新增 `data`（供 CRC 计算） |
| `_expected_crc` | 由 `0x2E F1A2` 预置的期望 CRC32；`FF00` 用它校验（None=只校验长度，兼容旧套件） |
| `_pending_activation` | `FF00` 通过后登记 `{version, slot}`，等 `0x11` 复位激活 |
| `_active_slot` | A/B 当前槽（A↔B），复位后翻转 |
| `_precheck_speed` | 预编程检查用"模拟车速"（由工程 DID F1B0 byte3 设置，自动化测试用） |

**关键实现原则**：所有新增逻辑都是**叠加**在现有服务上（0x34/36/37 原有行为保持），
所以 02/03/06/14 与 scenarios/07 全部回归通过。

### 35.8.4 OtaLibrary 关键字一览

| 关键字 | 作用 |
|---|---|
| `Start OTA Server` / `Stop OTA Server` | 起/停 OTA 云端 mock 子进程（端口就绪检查、异常端口报错、terminate+wait+kill 回收） |
| `Get OTA Manifest` | 取包元数据 dict |

### 35.8.5 17 套件逐条讲（10 条，全部可跑）

| # | 用例 | 标签 | 验证点 |
|---|---|---|---|
| ① | OTA manifest 应包含完整包元数据且镜像校验通过 | REQ-OTA-001 | 版本/大小/分块/CRC/兼容性字段 + 下载镜像 CRC32 一致 |
| ② | 预编程条件检查应通过且异常条件下被拒绝 | REQ-OTA-001 | 正常通过；9V 欠压 → 0x22；模拟车速 30 → 0x22 |
| ③ | 刷写中断电或复位应回滚到旧版本 | REQ-OTA-005/003 | 传 2/8 块后复位 → **版本仍为 v1.0.0**（A/B 未激活新版本）；随后预编程检查仍通过 |
| ④ | 完整刷写链路应成功且版本待复位后激活 | REQ-OTA-002 | 0x34+8×0x36+0x37+FF00 结果 0；**复位前版本仍 v1.0.0** |
| ⑤ | 刷写后 ECU 复位应激活新版本 | REQ-OTA-003 | 11 01 → F195 = v1.1.0；读 F1A3 正常 |
| ⑥ | CRC 错包应被拒绝且版本保持旧值 | REQ-OTA-004 | Agent 拒绝 + 强写后 ECU FF00 拒绝（两道防线） |
| ⑦ | 大小不符的包应被拒绝 | REQ-OTA-004 | 云端只给 400B → 下载不完整 → 拒绝 |
| ⑧ | 版本不兼容的包应被拒绝 | REQ-OTA-004 | compatible=false / 要求 BL-9.9.9 → 拒绝 |
| ⑨ | 丢块后重传应成功且断点续传数据一致 | REQ-OTA-005 | 128B+续传拼接 CRC 一致；丢块 0x73→重传→结果 0 |
| ⑩ | 刷写后默认会话仍可读新版本 DID | REQ-OTA-003 | 10 01 后 22 F195/F1A3/F186 均可读 |

> 🔁 **顺序说明（为什么 ③ 回滚排在 ④ 成功刷写之前）**：回滚用例必须在**运行版本还是 v1.0.0** 时执行，
> "断电/复位后仍为 v1.0.0"才有区分度；如果放在成功刷写之后（运行版本已等于目标版本 v1.1.0），
> 该断言会变成恒真——**假通过**。交叉审查（task-31）发现原顺序问题后，已把本用例前移到成功刷写之前，
> 并明确断言回滚到 **v1.0.0**。这也是"用例顺序本身就是测试设计"的典型案例。

## 35.9 真实 OTA 架构长什么样

```
┌─────────────┐   HTTPS/mTLS    ┌──────────────────────────────┐
│  OTA 云端    │ ◄─────────────► │ 车端 TBOX / 网关              │
│ - 包管理     │   证书/签名      │ - 下载（断点续传/限速）        │
│ - 灰度发布   │                 │ - 包校验（哈希+签名）          │
│ - 版本策略   │                 │ - 车辆状态检查（驻车/电量）     │
│ - 回滚策略   │                 │ - 分发到各 ECU（CAN/以太网）    │
└─────────────┘                 └───────────────┬──────────────┘
                                                │ UDS over CAN / DoIP
                                    ┌───────────▼───────────┐
                                    │ ECU Bootloader         │
                                    │ - 安全启动/验签         │
                                    │ - A/B 分区、回滚计数    │
                                    └───────────────────────┘
```

真实 OTA 的额外测试面（本项目未覆盖，面试要能说）：
- **证书/签名/TLS**：过期证书、错误 CA、被篡改的包、重放旧包；
- **安全启动链**：BL 验 APP 签名失败不能启动、HSM 密钥管理；
- **防降级**：旧版本包（CVE 修复后）必须被拒绝；
- **资源约束**：电量低/存储不足/网络差（弱网、限速、丢包）；
- **灰度与回滚**：批次发布、失败率超阈值自动回滚、售后强制回滚；
- **合规**：UN R156（软件升级管理体系 SUMS）、ISO 24089（道路车辆软件更新工程）。

## 35.11 自查题（先想 30 秒再看要点）

1. **OTA 和刷写的区别？为什么 OTA 测试不能只测刷写？**
   > 要点：刷写只是 UDS 写 Flash 的动作；OTA 含云端打包/签名/下载/校验/灰度/回滚/版本策略。只测刷写会漏掉"包下载错、版本不生效、断电变砖"等。
2. **A/B 分区为什么能"刷坏了也不变砖"？**
   > 要点：新固件写入非活动分区，旧分区不动；校验通过 + 复位才切换；失败/断电时启动仍选旧分区。
3. **预编程/编程/后编程三个阶段的典型服务？**
   > 要点：预编程 10 03 + 31 01 0203/0202；编程 10 02 + 27 + 34/36/37；后编程 31 01 FF00 + 11 01 + 22 F195。
4. **为什么完整性校验不能只校验长度？**
   > 要点：长度对的坏数据也会通过，导致激活损坏镜像；要长度 + CRC/哈希（真实项目还要签名）。
5. **本项目 17 套件的 ④ 为什么断言"刷写成功后版本还是 v1.0.0"？**
   > 要点：A/B 语义下版本在复位后才激活；如果 FF00 通过就改版本，会出现"版本已变但程序没重启"的假成功。
6. **丢块时 ECU 回哪个 NRC？测试端怎么处理？**
   > 要点：0x73 wrongBlockSequenceCounter；测试端识别后补发正确块（本项目 `Flash With Retry`）。
7. **断点续传在 OTA 下载层怎么实现？测试怎么验证拼接正确？**
   > 要点：云端按 offset/length 返回（Range）；测试先下前段再续传后段，拼接后 CRC32 与 manifest 一致。
8. **真实 OTA 相比本项目还缺哪些安全机制？**
   > 要点：签名验签、TLS/mTLS、Secure Boot、防降级、证书管理、灰度回滚策略；CRC32 只能查传输错误不能防篡改。

### 本章要点回顾（面试速答）

- OTA = 云端 + 车端 + Bootloader 的完整升级链；刷写只是最后一环。
- Bootloader/APP 分离 + A/B 双分区 = 刷坏了也能启动旧版本（回滚的本质）。
- 三阶段：预编程（条件检查）→ 编程（会话+解锁+34/36/37）→ 后编程（FF00 校验 + 复位激活）。
- 版本 DID：F195 运行版本（复位后才更新）、F1A3 Bootloader、F186 硬件；F1A1/F1A2 是刷写暂存。
- 失败路径比成功路径重要：坏包（CRC/大小/兼容性）、断电回滚、丢块重传、断点续传。
- 教学用 CRC32 讲清楚"两道防线"；真实项目必须签名 + 安全启动 + 防降级。
