## 读之前：这些词先混个脸熟（5 分钟）

> 🚗 **如果你没开过车 / 没见过实车仪表，请先跳到下面那个【零基础专线】看完三张图再回来** ——
> 那一步比读术语表重要得多。

本教程会大量使用行业缩写。**第一次见不用慌** —— 下面这些是最核心的，
扫一眼有个印象就够了，真正用到时（18 章 / 02 章 / 03 章）会详细讲。

| 缩写/术语 | 一句话说明 | 详细讲在哪 |
|---|---|---|
| **ECU** | 车上的"小电脑"，一辆车有几十个（分别管发动机、车门、仪表…） | [18.1](18_零基础常识速成.md#181-一辆车上有多少个电脑) |
| **CAN** | 车上的"总线" —— 所有 ECU 共用一根线互相喊话的规则 | 18.2 / [02](02_车载网络基础.md) |
| **报文 / 帧** | CAN 上发的一条"消息"：一个编号（ID）+ 最多 8 字节数据 | 18.2 / 02 |
| **信号** | 报文那 8 字节里切出来的一个个数据（车速、转速、水温…） | 18.2 / 02 |
| **DBC** | 车上的"字典" —— 说明报文里哪几位是什么信号 | [02.4](02_车载网络基础.md) |
| **周期报文** | ECU 按固定间隔反复发的报文（车速每 100ms 一帧） | 18.2 |
| **诊断 / UDS** | 4S 店插电脑读故障用的那套协议（车能回答"我哪儿坏了"） | 18.3 / [03](03_UDS协议详解.md) |
| **DTC** | 故障码（`P0116` 这种）—— 车的"病历" | 18.4 / [04](04_DTC详解.md) |
| **NRC** | 诊断的负响应码 —— ECU 在说"我拒绝，原因是…" | 03.2 |
| **DID** | 诊断读数据时用的"编号"（如 `F187` = 零件号） | 03.5 |
| **ISO-TP** | 数据超过 8 字节时的"分段传输"规则（读 17 位 VIN 就要用） | 03.1 |
| **会话 / 安全访问** | 诊断的两道门槛：工作模式 + 密码锁（种子-密钥握手） | 18.3 / 03.3 |
| **刷写** | 给 ECU 重装固件（像手机刷机 / OTA 升级） | 18.5 |
| **Telltale / 警告灯** | 仪表上所有报警灯的统称（水温灯、机油灯、安全带灯…） | [18.0](18_零基础常识速成.md) / 01 |
| **HMI** | 人机界面 —— 这里主要指仪表和中控屏 | [09](09_仪表盘HMI测试实战.md) |
| **台架 / HIL** | 实验室里"真 ECU + 电脑模拟其余部分"的测试台 | 18.6 |
| **CANoe** | Vector 公司的商业总线工具（行业标配；本项目用 Python 平替它） | 18.6 / 13 |
| **Tier1 / OEM** | 供应商 / 整车厂（**你入职的就是 Tier1**） | 18.1 |
| **暗电流** | 熄火后全车的耗电（要求 < 20mA，超标会导致亏电打不着火） | 18.0 |
| **功能安全 FuSa** | "电子系统坏掉也不能伤人" —— 汽车行业的安全总纲 | 18.8 / 12 |
| **ISO 26262 / ASIL** | 功能安全的国际标准；ASIL 是它定义的等级（A~D，D 最严） | 18.8 / 12 |
| **ASPICE** | 汽车**开发流程**标准（客户按它审核供应商，所以测试要留证据） | 18.8 / 20 |
| **AUTOSAR** | 汽车软件架构标准（统一通信/诊断接口） | 18.8 |
| **MIL / SIL / HIL** | 测试的三个层次：纯仿真 → 跑真代码 → 真硬件在环 | 12.1.5 |

> **不用背。** 这张表的用法是"读教程时遇到不认识的词，回来查一眼"。
> 真正记住它们的方式是**用它们** —— 写脚本时会反复碰到 ECU / 报文 / 信号 / 诊断这几个。

## 一、你即将面对的工作是什么

伟世通（Visteon）是 Tier 1 供应商，核心产品是**数字座舱**（仪表、中控、HUD、域控）。
你的岗位 `Sr Engineer I System Validation` —— 注意是 **System Validation（系统验证）**，
不是 Software Test（软件测试）。**这个区别决定了你的工作重心**。

### 1.1 三类工作，按重要性排序

| # | 工作项 | 具体内容 | 对应章节 |
|---|---|---|---|
| ① | **验证工程**（岗位核心） | 读系统需求 → 判断可测性 → 写测试规范 → 执行 → **需求追溯** → 出验证报告 → 提缺陷 | **20**、17、13 |
| ② | **系统专项验证** | 通信/诊断/DTC/刷写/**异常与鲁棒性**/电源管理/网络管理 | 02-04、07-10、**19** |
| ③ | 脚本与工具 | 用 Robot Framework / Python 把重复验证自动化 | 05、**14-16**、13 |
| ④ | 问题定位与报告 | 抓 Trace 做时间线分析、写缺陷单、跟进修复验证 | 16、20 §8 |

**关键认知**：这个岗位交付的不是"我跑过 116 个用例"，而是**一条证据链**：
"每条需求都被验证过，这里是追溯矩阵、规范和报告"。第 ① 项是它跟普通测试岗的分水岭。

### 1.2 用 5 个同类 JD 交叉验证过的能力要求

```
① 验证工程链  Test based on Requirements / requirements traceability /
              test specifications / verification metrics / test reports  ← 岗位看家本领
② 系统专项    通信 / 诊断 / 电源 / NM / Fault Injection / FuSa 基础 / OTA
③ 工具链      CANoe·CANape / .blf·.asc trace 分析 / HIL / DOORS·Jama / JIRA
```

三块在本仓库的对应：① → **20 章 + requirements/ + deliverables/**
② → **19 章（12 个真实场景）** ③ → **13 章（Trace 导出/报告/CI）**

## 三、入职前 4 周冲刺计划（今天 → 11-13）

> ⚠️ **先看这一句，能省你很多弯路**：
> **教程的"编号顺序"（01→02→…→20）不等于"学习顺序"。**
> 编号是内容组织方式；学习顺序以本节为准（先常识 → 再协议 → 再写脚本 → 再实战 → 最后交付）。
> 章末的"下一章"链接是**同类内容的顺读**（如 14→15→16→17 是"写脚本"线），
> 不要把它当成唯一路径 —— **按下面的周计划走**，需要时用链接跳读。

> 每周约 12-15 小时。**每周都有可验收的产出**，不是"读完了"而是"能做什么"。
> 时间不够时看 §3.5 的三条路线。

> **判断标准**：面试官最想听的是"**你完整做过一个项目**"，不是"你读完 22 章"。
> 所以时间紧时，**宁可少读、要把一个场景走通并讲清楚**。

**时间不够时的优先级铁律**：`18 常识` → `15 模式库` → `20 交付链` 这三章是
**岗位语言**，必须读；`02/03/04` 协议细节可以边工作边补。

### 4.2 三组命令（从体验到全链）

> ⚠️ **所有命令都在项目根目录执行**（即 `robot_framework/` 这一层，能看到
> `docs/`、`simulators/`、`tests/` 的那一层）。这是新手最容易踩的坑 ——
> 报"找不到文件"时，先 `pwd` 看看你在哪。

```bash
# ① 手动体验（三个终端，感受系统怎么跑）
python simulators/ecu_sim.py --speed 60      # 终端1：车辆（ECU）
python simulators/uds_client.py              # 终端2：诊断仪（手发 UDS 请求）
python simulators/dashboard.py               # 终端3：仪表盘（有界面，看指针动）

# ② 实训自检（确认环境正常，然后做题）
python training/check_all.py                 # 预期：6/6 个参考答案通过

# ③ 全链一条命令（测试 + 交付报告 + 覆盖率 + 需求追溯矩阵）
python run_tests.py --report
# 产物：results/test_summary.html（交付报告）
#      results/coverage.html（覆盖率）
#      results/trace_matrix.html（需求追溯矩阵）
#      results/bus_trace.asc（CANoe 兼容 Trace）
```

> 直接 `python -m robot --outputdir results tests/robot/ scenarios/` 也可以，
> 但用 `run_tests.py` 会自动注入解释器、串联所有报告 —— 这也是 CI 用的同一入口。

## 六、给零基础读者的四条建议

1. **先"看图"再"看字"**（没开过车的尤其重要）。`docs/images/` 里有三张图 ——
   仪表盘布局、动力链、开车流程。先看懂"车长什么样、开车时发生什么"，
   再读文字，效率差好几倍。然后**跑起来**：`ecu_sim.py` + `dashboard.py`
   看仪表指针从 0 爬到 60，再回去读 CAN 报文定义 —— 一切都会具体很多。

2. **每个概念都要"用手算一遍"**。教程里所有关键数字（位仲裁、BCD 编码、ISO-TP 拆帧、
   周期抖动）都给了可复算的例子，请拿笔算一遍。**看懂 ≠ 会。**

3. **遇到 bug 是常态**（这条对你这门工作尤其重要）。本项目开发过程中修掉了 **20+ 个真 bug**
   （DTC BCD 编码错、CAN 流控帧方向发反、cantools 枚举坑、UDP 组播回环导致永不休眠……），
   06 章有完整排坑记录。**你未来的工作就是每天和这类问题打交道** ——
   排查方法（分层定位、手动复现、质疑假设）比结论更重要，16 章专门讲这个。

4. **别忘了"交付"这件事**。很多新人技术不错但不会交付：测试跑完了不知道怎么讲、
   缺陷单写得开发看不懂、客户问"这条需求验了吗"答不上来。
   **20 章那套东西（追溯矩阵/规范/报告）是你和普通测试拉开差距的地方**，
   哪怕技术细节还没吃透，先把这套语言学会。

### 关于每章末尾的"自检题"（新手必读）

- **没有标准答案** —— 答案都在本章正文里。找不到就说明那节没读透，**回去重读那一节**。
- **怎么算过**：不看答案，能**用自己的话**讲出来（能举例更好）。
  "看着眼熟"不算掌握 —— 这是新手最容易骗自己的地方。
- **18 章额外给了"自查要点"表**（新手第一站，常识最容易自欺），做完对着表看一眼。
- **卡住了怎么办**：把题目 + **你自己的理解**一起问 AI（"我理解是 X，对吗？"）——
  比直接看标准答案学得多，因为你能看到自己是哪一步想歪的。
- 想练手就直接做题：`training/` 里的 6 个练习都有参考答案和判分器，比自检题更硬核。
