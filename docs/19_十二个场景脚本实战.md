## 19.2 场景 1：动力域信号验证

**业务背景**：仪表盘上所有动力信息（车速/转速/水温/档位/里程）都来自 ECU 的周期报文。
这是"每天都会跑"的基础回归。

**三个层次的验证**（这是方法论，不只是这一场景的）：
1. **存在性**：信号在不在（ECU 发了没有）
2. **范围**：值合不合理（用物理极限判：水温不可能 -50℃）
3. **联动**：信号之间关系对不对 ← **最有价值**

```robotframework
转速应与车速保持设计比例
    ${speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    90    110    timeout=25
    ${rpm}=    Read Signal From Bus    EngineData    EngineSpeed
    ${expected}=    Evaluate    max(800, ${speed} * 80)
    ${diff}=    Evaluate    abs(${rpm} - ${expected})
    ${tolerance}=    Evaluate    max(200, ${expected} * 0.05)
    Should Be True    ${diff} <= ${tolerance}
    ...    msg=转速 ${rpm} 与期望=${expected}（车速×80）偏差 ${diff}，超过容差 ${tolerance}
```

**为什么联动断言值钱**：如果 ECU 的转速模型写错（比如系数写成 60 而不是 80），
单看"转速在 0~16000 范围内"永远是绿的 —— **只有联动断言能发现**。

**新技巧**：里程单调性用"排序前后是否相同"来验（比在 Evaluate 里手写列表推导稳）：

```robotframework
${sorted}=    Copy List    ${readings}
Sort List    ${sorted}
Lists Should Be Equal    ${readings}    ${sorted}    msg=里程未单调累积
```

## 19.3 场景 2：警告灯矩阵

**业务背景**：警告灯（telltale）是**法规强制**的安全显示项。三个测试层面：
① 该亮时亮 ② **不该亮时别亮**（最易漏测） ③ 全亮自检（产线 EOL 用）。

**脚本技巧**：数据驱动遍历 12 个灯名，失败时能精确报出是哪个灯没实现：

```robotframework
@{ALL_TELLTALES}    MilWarning    OilPressureLow    CoolantTempHigh    BatteryLow
...                 AbsFault    AirbagFault    SeatbeltWarning    TurnLeft
...                 TurnRight    HighBeam    LowBeam    ParkBrake

自检清单应包含全部 12 个灯名
    Enter Extended Session                 # ⚠ 0x31 例程在默认会话不可用！
    Start Light Test Routine
    ${lit}=    Get Lit Telltales
    FOR    ${telltale}    IN    @{ALL_TELLTALES}
        Should Contain    ${lit}    ${telltale}
        ...    msg=灯光自检未点亮 ${telltale}，实际点亮: ${lit}
    END
```

> 🔴 **写这个场景时真的抓到一个 bug**：ECU 的灯光自检清单漏了 `SeatbeltWarning`，
> 只点亮 11 个灯。而**灯清单在三个地方各有一份**（ECU 的 override、仪表 UI、DBC 信号），
> 三处不同步就是典型缺陷。这就是"遍历式断言"的价值 —— 它精确地指出了是**哪一个**灯。

## 19.4 场景 3：诊断权限矩阵

**业务背景**：诊断服务有**严格的权限模型**，权限边界是 Tier1 交付物里必查的项。

**用矩阵表达覆盖**（一眼看出有没有漏）：

```
                默认会话   扩展未解锁   扩展已解锁   复位后
读数据           ✅ 允许     ✅ 允许      ✅ 允许     ✅ 允许
写数据           ★0x7F      ★0x33       ✅ 成功     ★0x7F
```

**关键写法**：写操作后**必须回读**（正响应只说明"收到了"，不代表"写对了"）：

```robotframework
扩展会话已解锁写数据应成功且可回读
    Enter Extended Session
    Security Unlock
    Write DID    F1A0    56332E302E30
    ${ver}=    Read DID As ASCII    F1A0      # ★ 回读验证
    Should Be Equal    ${ver}    V3.0.0
```

**"复位后权限应失效"** 这条容易被忽略：权限残留是安全隐患（退出诊断后别人能直接接着写）。

## 19.5 场景 4：DTC 全生命周期

**业务背景**：DTC 有状态机（连续 N 个周期异常才 confirmed），为的是**防误报**。

**技巧**：用**状态掩码**查询，比"码存在"更严格：

```robotframework
DTC 应以 confirmed 状态存在
    [Arguments]    ${expected_dtc}
    ${records}=    Read DTC By Mask    08          # 08 = confirmed
    ${names}=    Evaluate    [r[0] for r in $records]
    Should Contain    ${names}    ${expected_dtc}
    ...    msg=confirmed 状态列表中未找到 ${expected_dtc}，实际: ${names}
```

**闭环的最后一步最容易被漏**（"故障仍在时应重新记录"）：它证明清除没破坏检测能力。
真实场景对照："清码后过几天又亮"。

## 19.6 场景 5：会话时序与保活

**业务背景**：非默认会话有 **S3 定时器**（本项目 5 秒）：静默超时会自动回退默认会话
并锁定安全访问 —— 防止"诊断接头拔了但权限还开着"。

**时序类需求的铁律：验"变化"，不是验"状态"**。要同时证明两件事：
1. **静默 → 会回退**（超时生效）
2. **保活 → 不会回退**（保活有效）

```robotframework
静默超过 S3 时间应回退默认会话并锁定权限
    Enter Extended Session
    Security Unlock
    Sleep    6s                                    # 这里的 Sleep 是需求本身
    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x7F   # ← 0x7F 而不是 0x33
```

**NRC 的区别就是证据**：`0x7F`（会话不支持）= 已回退默认会话；
`0x33`（权限不足）= 还在扩展会话但没解锁。**断言哪个 NRC 决定了用例在验什么**。

## 19.7 场景 6：座舱多屏一致性

**业务背景**：车机上点歌/开导航/调空调，仪表要立即同步（链路：车机状态 → CAN → 仪表）。

**最后一个用例很特别** —— **域隔离验证**：

```robotframework
座舱设置不应影响动力域信号
    Set Headunit Media State    track_index=5    volume=100
    Broadcast Headunit State To Bus
    Start Bus Recorder
    Drain Bus For    2
    Stop Bus Recorder
    Period And Jitter Should Be Within    0x100    100
    ...    period_tolerance_ms=25    jitter_tolerance_ms=60
```

**真实缺陷对照**：车机疯狂发报文会把总线负载拉高，挤压动力报文的周期 ——
"娱乐功能影响安全功能"是真实发生过的严重问题。这条用例就是防它。

## 19.8 场景 7：刷写流程与失败路径

**业务背景**：刷写（固件升级）是诊断测试里权重最高的场景 —— **失败路径比成功路径更重要**
（刷一半失败不能让 ECU 变砖）。

六条用例 = 1 条成功流程 + 4 条失败路径 + 1 条**恢复验证**：

| 用例 | 验证点 |
|---|---|
| 完整刷写流程应成功 | 四步曲 + 完整性校验 0x00 |
| 失败路径_未解锁 | NRC 0x33 |
| 失败路径_块序号错乱 | NRC 0x73（真实刷写最常见的失败：丢块） |
| 失败路径_字节数不足 | 校验结果 0x01（固件不完整必须被识别） |
| 失败路径_地址超范围 | NRC 0x31（越界保护） |
| **刷写失败后应能重新开始** | 失败一次不该把 ECU 卡死 |

**用例隔离**（刷写场景必须做）：

```robotframework
Test Teardown    复位 ECU 清理刷写状态

复位 ECU 清理刷写状态
    Run Keyword And Ignore Error    Send UDS Request    11 01
    Sleep    0.2s
```

> 不做隔离会导致"前一个用例留下的 flash_state 让后续 0x34 全撞 NRC 0x24" ——
> 而且**单独跑能过、连续跑才挂**，是最难查的一类失败。

## 19.9 场景 8：总线健康度监控

**业务背景**：报文**周期是设计指标**（车速 100ms / 水温 200ms / 灯状态 500ms）。
周期跑偏或抖动过大会让依赖它的节点异常。台架上用 CANoe 看这个，我们用录制器自己算。

**两个概念**（真实工作高频词）：
- **周期均值**：相邻两帧时间差的平均 —— 该 100ms 就得接近 100ms
- **抖动 Jitter**：最大间隔 − 最小间隔 —— **均值正常但抖动大是最隐蔽的问题**

```robotframework
车速报文周期应为 100ms 且抖动可控
    Period And Jitter Should Be Within    0x100    100
    ...    period_tolerance_ms=20    jitter_tolerance_ms=40
```

**这个场景还演示了"Setup 造场景"**：录制在 Suite Setup 完成，各用例只做分析，
避免"用例之间抢着录制"的顺序依赖。

## 19.10 场景 9：响应时序一致性

**业务背景**：ECU 在会话响应里**声明** P2=50ms（最长响应时间）。实测超标会让诊断仪
误判超时 → 现场表现为"诊断仪连不上车"。

**关键技巧：多点采样**。时序问题往往是"偶尔慢"，单次测量会漏掉：

```robotframework
读数据响应时间应稳定在 P2 内（多点采样）
    @{samples}=    Create List
    FOR    ${i}    IN RANGE    ${SAMPLE_COUNT}
        ${ms}=    Measure Response Time    22 F187
        Append To List    ${samples}    ${ms}
    END
    ${max_ms}=    Evaluate    max($samples)
    ... （断言最大值 < P2）
```

> ⚠ 变量名故意叫 `${SAMPLE_COUNT}` 而不是 `${SAMPLES}`：**RF 的变量名大小写不敏感**，
> 会和列表 `${samples}` 撞车（报 `Expected number, got list`）。踩过这个坑。
>
> 另外 `max($samples)` 里的 `$samples`（无花括号）是 RF 引用"Python 对象"的语法 ——
> 写成 `${samples}` 会展开成多个参数而报错。

## 19.11 场景 10：冒烟回归集（Tag 分层）

**业务背景**：全量 62 个用例跑 70 秒；改代码后只想"快速确认没坏主要功能"。
用 **Tag** 分层：

```bash
python run_tests.py                                        # 全量
python -m robot --include smoke tests/robot/ scenarios/     # 冒烟（约 30 秒）
python -m robot --include negative ...                      # 只跑负向
python -m robot --exclude slow ...                          # 跳过慢用例
```

**冒烟集的选择原则**：覆盖"三条主链路"就够 ——
① 信号链（ECU → 总线 → 仪表）② 诊断链（会话 → 读 → 写+权限）③ 故障链（注入 → DTC → 灯）。

**这条用例抓到过一个"经典陷阱"**：

```robotframework
主链路_信号链应通
    Wait Until Signal In Range    EngineData    VehicleSpeed    58    62    timeout=20   # ★ 先等稳态
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    ${shown}=    Get Displayed Speed
```

> 🔴 第一版写的是等车速进入 50~70 就立刻比较 —— 结果**总线 50.25 vs 仪表 60.0**。
> 原因：`Wait Until` 在进入区间的**瞬间**就返回了，此时车速还在爬升，
> 两次读取的采样时刻不同，两个**动态值**必然对不上。
> **跨系统一致性测试必须先等系统进入稳态** —— 这是很值钱的一条经验。

## 19.12 从这十个场景提炼的写法清单

| 场景 | 可复用的写法 |
|---|---|
| 1、8 | 断言分三层：存在 → 范围 → **联动/周期** |
| 2、4 | 遍历式断言（精确指出是哪一个不满足） |
| 3 | **矩阵式覆盖**（用表格确认没漏象限） |
| 3、7 | 写操作后**回读**；用 **Teardown** 做用例隔离 |
| 5 | 时序需求验**变化**；用 NRC 差异作为状态证据 |
| 6 | 域隔离验证（A 域操作不该影响 B 域指标） |
| 7 | 失败路径 + **恢复性验证**（失败后能重来） |
| 8 | Setup 造场景 + 周期/抖动分析 + Trace 归档 |
| 9 | 时序测试**多点采样**取最差 |
| 10 | **Tag 分层**：冒烟 / 负向 / 长时分开 |

**三条最值钱的经验**（都在这 12 个场景里踩出来的）：

1. **跨系统比较前先等稳态**（场景 10）—— 动态值采样时刻不同会对不上
2. **同一份清单在多处实现必然不同步**（场景 2 的灯清单漏项）—— 遍历断言能抓出来
3. **用例隔离不做，失败只在连续跑时出现**（场景 7）—— 最难查的类型

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | 范围断言只能发现"值超界"；**联动断言能发现模型/参数错误**。例：转速系数写成 ×60（而非 ×80）时，转速仍在 0~8000 范围内 → 范围断言永远绿，联动断言立刻检出 |
| 2 | 两个维度：**会话**（默认/扩展/编程）× **安全访问**（未解锁/已解锁）。"复位后权限应失效"必测，因为**权限残留是安全隐患**（退出诊断后别人能直接接着写） |
| 3 | 要证明"**会变化**"而不是"当前状态"。证据 = 能区分两种情况的信号：**回退后报 0x7F**（会话不支持）vs 未回退报 0x33（权限不足） |
| 4 | 因为刷写状态（`flash_state`）会残留 → 下一个 0x34 撞 NRC 0x24。不隔离的现象：**单独跑能过、连续跑才挂**（最难查的一类失败） |
| 5 | "周期均值正常但个别帧晚了几十毫秒" → 接收方可能超时。测法：`Period And Jitter Should Be Within`（算最大间隔 − 最小间隔） |
| 6 | 因为时序问题往往是"**偶尔慢**"，单次测量会漏掉（真实发现过"第 3 次响应慢 80ms"的缺陷） |
| 7 | 因为车速还在爬升时，两次读取的**采样时刻不同** → 两个动态值必然对不上（场景 10 实测 50.25 vs 60.0）。要先等进入稳态（58~62）再比较 |
| 8 | 三条链路：**信号链**（ECU→总线→仪表）、**诊断链**（会话→读→写+权限）、**故障链**（注入→DTC→灯）。单独维护是因为全量 116 用例要 3 分钟，而改代码后需要在 30 秒内知道"主要功能没坏" |
