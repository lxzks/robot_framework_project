# 13 · 测试工程化：从"跑用例"到"可交付"

> 本章覆盖把测试从"我跑过了"提升到"能交付、能复现、能持续"的四个工程能力：
> **Trace 归档（CANoe 兼容）→ 交付报告 → 用例自动生成 → 覆盖率与 CI**。
>
> 全部工具都在项目根目录，可直接运行：
> `generate_testcases.py` / `generate_report.py` / `coverage_report.py` / `trace_matrix.py` /
> `link_requirements.py` / `test_spec_check.py` / `run_tests.py` / `.github/workflows/ci.yml`

---

## 13.1 为什么需要"工程化"

一个残酷的现实：**只跑用例的测试，价值很低**。测试主管/客户关心的三件事：

| 问题 | 没有工程化 | 有了工程化 |
|---|---|---|
| 测出问题了吗？ | "跑完了，好像还行" | 一份报告：**276 个用例**的通过/失败明细，附失败详情 |
| 出问题了怎么查？ | "我再看一遍" | 归档的 Trace 文件，谁都能回放分析 |
| 测全了吗？ | "应该覆盖了" | 覆盖率报告：UDS 17/17、信号 35/35、OBD 4/4 |
| 以后能重复吗？ | "在我机器上能跑" | CI 每次提交自动跑，产物可下载 |

**这一章就是把这四件事做成工具。** 加分点：这些能力**不是车电机密**，是通用测试工程能力——面试官问"你怎么保证测试可信"，你有具体答案。

## 13.2 Trace 归档：产出 CANoe 能打开的文件

### 13.2.1 为什么格式兼容重要

测试失败时最需要什么？**总线 Trace**——看"当时总线上到底发生了什么"。

但随便导出一份 CSV 是没用的：真实排故流程里，工程师拿到 Trace 会**用 CANoe/CANalyzer 打开、过滤、比对**。所以产出的文件必须是**行业通用格式**：

| 格式 | 类型 | 特点 | 用途 |
|---|---|---|---|
| **ASC** | Vector ASCII 文本 | 可读、可 diff、体积大 | 归档、code review、小数据量 |
| **BLF** | Vector 二进制 | 体积小、支持大数据量 | 实车路试、长时间录制 |

**面试话术**："我做的工具产出的 Trace 可以直接在 CANoe 里打开回放" —— 这一句就把"我录了报文"提升到"我的工具能进真实流程"。

### 13.2.2 实现要点

`simulators/trace_tools.py` 是核心，两个关键决策：

```python
# ASC 自己写（格式是文本，规范简单，手写可控）
def export_asc(frames, path, channel=1) -> int:
    # 格式：  0.100000 1  100             Rx   d 8 C4 09 80 0C 82 33 00 00
    #        <相对时间> <通道> <ID>     <方向> <d> <DLC> <数据>

# BLF 必须用成熟库（二进制格式手写必错）
def export_blf(frames, path) -> int:
    with can.BLFWriter(str(path), channel=1) as writer:
        for ts, aid, data, ext in recs:
            writer.on_message_received(can.Message(...))   # 注意方法名
```

**"测试的测试"**：导出器写错了在真实工作里很致命（Trace 打不开/内容缺失 → 现场问题无法回溯），所以我们对两类文件都做回读校验：

- ASC：自研解析器逐行校验（帧数 + 每行格式），并与录制数据交叉核对 ID 序列
- BLF：**用 python-can 的 BLFReader 回读**（工业库能读通 = 格式正确，这正是 CANoe 会做的事）

### 13.2.3 RF 里怎么用

```robotframework
录制总线并导出 Trace 文件（CANoe 兼容）
    Start Bus Recorder
    Drain Bus For    2
    Stop Bus Recorder
    ${n}=    Recorded Frame Count
    ${asc_n}=    Export Bus Trace    ${ROOT}/results/bus_trace.asc
    ${blf_n}=    Export Bus Trace    ${ROOT}/results/bus_trace.blf
    Trace Files Should Be Valid
    ...    ${ROOT}/results/bus_trace.asc    ${ROOT}/results/bus_trace.blf    ${n}
```

另外 `common.resource` 的 teardown 会**自动归档** `bus_trace_last.asc`——失败时一定有东西可分析。

### 13.2.4 抓包完整性：两个真实坑

**坑 1：UDP 接收缓冲**。默认 `SO_RCVBUF` 只有 64KB，报文突发时会静默丢帧（UDP 无重传）。解法：`bus.py` 创建总线后调大缓冲（4MB）。

**坑 2：多网卡组播回环**。本机有多个网络接口（真实网卡 + 虚拟网卡）时，同一帧会从每个接口各回环一份 → **Trace 帧数翻倍、周期均值变一半、抖动虚高**。识别特征：**周期均值 ≈ 理论值 / 接口数**。

解法（`bus.py` 接收端去重）：按 `(ID, 数据)` 在 5ms 窗口内去重。本工程最快报文周期 100ms，不会误杀真实帧。

> 这个坑的排查过程很典型：先怀疑缓冲区 → 加缓冲没用 → 对比"逐帧 recv"和"Notifier 后台线程"吞吐完全相同 → 说明发送端就这样 → 最后才想到数一下本机网卡数（3 个）。
> **排故要不断缩小假设范围，而不是反复试同一类方案。**

## 13.3 测试交付报告

`generate_report.py` 把三类产物合成一份 HTML 报告（Tier1 交付物形态）：

```
┌─────────────────────────────────────────────────────────┐
│ 车载自动化测试报告                    生成时间 / 项目    │
├─────────────────────────────────────────────────────────┤
│ 用例总数 276 │ 通过 276 │ 失败 0 │ 通过率 100% │ PASS   │  ← 概览卡片（示例；以本次运行为准）
├─────────────────────────────────────────────────────────┤
│ 套件明细表（01~20 + 生成用例 + 16 个场景，各自通过数/耗时/结果）│
├─────────────────────────────────────────────────────────┤
│ 失败用例清单（有则列出：用例名 + 失败信息）               │
├─────────────────────────────────────────────────────────┤
│ 总线活动分析（从 Trace 提取）                            │
│   0x100  19 帧  周期均值 ~105.8ms  抖动 2.1ms           │  ← 周期抖动是
│   0x200  10 帧  周期均值 ~203.2ms  抖动 11.0ms          │    总线健康度核心
│   0x300   3 帧  周期均值 ~508.1ms  抖动 2.4ms           │    指标，>20ms 标红
├─────────────────────────────────────────────────────────┤
│ 产物清单（log.html / output.xml / Trace / 仪表快照）      │
└─────────────────────────────────────────────────────────┘
```

> 以上数值来自一次真实运行（每次会有小幅浮动，以 `results/test_summary.html` 为准）。

**"总线活动分析"是这份报告的亮点**：它不满足于"用例通过"，而是从 Trace 里算出每个报文的**周期均值与抖动（Jitter）**——抖动 = 相邻帧间隔的最大差，超过 20ms 意味着总线时序不稳（真实排故必看）。

**注意周期均值要和设计值核对**：0x100 设计周期 100ms，报告显示约 106ms ✓ 合理（允许数毫秒抖动）。如果显示 52ms，那就是"每帧被收了两份"（多网卡回环），要去查而不是当成"总线正常"。

## 13.4 测试用例自动生成（与 APIGen 同一套思想）

> **这是本章和"测试开发"岗位最相关的一节。**
> 从"接口规范"自动生成测试用例：APIGen 从 OpenAPI 规范生成 API 用例，
> 本项目 `generate_testcases.py` 从 DBC（CAN 信号数据库）生成总线用例。
> 同一个方法论，两个不同协议的落地。

### 13.4.1 三步流水线

```
DBC 文件 ──①解析──► 信号模型 ──②生成测试点──► 用例矩阵 ──③组合优化──► .robot 文件
（35 个信号）        （范围/缩放/值表）  （边界值+等价类）    （pairwise）
```

**① 解析**：从 DBC 提取每个信号的类型、最小值/最大值、缩放、单位、值表（枚举）。

**② 生成测试点**：

| 信号类型 | 策略 | 产出 |
|---|---|---|
| 数值信号 | **边界值分析（BVA）**：min-1 / min / min+1 / 中点 / max-1 / max / max+1 | 7 点/信号 |
| 枚举信号 | **等价类**：值表每个取值各一条 | N 点/信号 |

**③ 组合优化**：多信号组合时用 **pairwise（两两覆盖）**——3 信号 × 3 值 = 27 组全组合，pairwise 优化到 **10~11 组**（贪心实现的结果会随集合迭代顺序略有浮动，以实际生成文件为准），覆盖所有"任取两个参数的任一取值组合"。

```
全组合 27 组 → pairwise 10~11 组（覆盖率不降）
依据：大部分缺陷由两参数交互触发，三参数及以上的交互概率显著下降
```

### 13.4.2 实测产出

```
$ python generate_testcases.py
生成完成: tests/robot/generated/generated_signals.robot
  信号 35 个（数值 31 / 枚举 4）
  边界值/等价类测试点: 208
  pairwise 组合: 3 信号 × 3 值 = 全组合 27 组 → 优化为 10~11 组
```

生成的 `.robot` **可直接跑**（我们把它们纳入了日常回归，11 个用例）：

```
$ python -m robot --outputdir results tests/robot/generated/
11 tests, 11 passed, 0 failed
```

### 13.4.3 生成器踩过的四个真坑（都值得知道）

1. **越界值无法编码**：DBC 信号位宽固定，负值/超量程值在编码阶段就被拒绝（`OverflowError`）——"发物理越界值"是伪命题。协议层能做的极限测试是**手工构造数据场**（把位域填满全 1），这也是真实台架的做法。
2. **RF 的 `[Template]` 只接受一个关键字名**：写成 `[Template] 关键字 参数` 会报 `accepts only one value`，参数必须放在每行数据里。
3. **RF kwargs 不支持带点的键**：`EngineData.VehicleSpeed=0` 不能被解析成命名参数，必须用短名（`VehicleSpeed=0`）。
4. **整数信号的中间值必须取整**：8 位信号 mid=127.5 → 编码后 round 成 128 → 读回 128 ≠ 127.5，断言必挂。

### 13.4.4 测试与总线冲突的解法（UDS 0x28）

自动生成的用例要"发一帧 → 读回来验证"，但 **ECU 每 100ms 也在周期发同一个报文**——读回的到底是谁的说不清。

**真实工程解法：用诊断服务暂停 ECU 周期发送**（`0x28 01 01` enableRxAndDisableTx），这正是刷写前必须做的事：

```robotframework
环境就绪并暂停 ECU 周期报文
    Start Vehicle Environment
    Enter Extended Session
    Suspend ECU Periodic Messages      # 28 01 01

恢复 ECU 周期报文并关闭环境
    Run Keyword And Ignore Error    Enter Extended Session
    Run Keyword And Ignore Error    Resume ECU Periodic Messages   # 28 00
    Stop Vehicle Environment
```

这个设计把"生成器可用性"和"真实诊断流程"连起来了——**测试手段本身也要符合被测系统的协议规范**。

## 13.5 覆盖率统计

`coverage_report.py` 从 RF 的实际执行结果里提取三个维度：

```
[UDS 服务]  17/17  (100.0%)      ← 实现的服务 vs 测试实际调用
[信号]      35/35  (100.0%)      ← DBC 信号 vs 用例覆盖
[DTC]       3/5    (60.0%)       ← 故障码目录 vs 测试验证过的
[OBD]       4/4    (100.0%)      ← OBD 服务（Wave2 新增，不计入综合分母）
综合覆盖率: 55/57 (96.5%)
```

> 以上是一次完整全量跑（主套件 + 场景）的结果；DTC 目录共 5 个，已覆盖 P0116 / P0562 / P0563。
> OBD 维度单独统计、不进综合分母（OBD 服务与 UDS/信号/DTC 是不同协议层，混算会失真）。
> 只跑主套件或只跑场景时数字会不同——覆盖率的正确用法是看**缺口清单**，不是看单一数字。

### 13.5.1 统计口径的三个讲究

1. **数据来源是"实际执行结果"**（`results/output.xml`），不是"用例里搜关键字"——搜索会算上被跳过的用例。
2. **库关键字要映射到隐含服务**：`Enter Extended Session` 其实就是 0x10、`Request Download` 是 0x34……否则会低估覆盖率。
3. **要解开关键字包装器**：`Run Keyword And Ignore Error    Send UDS Request    11 01` 的内层调用在 RF 结果树里是外层关键字的**参数**，不递归解析就会漏（我们真的漏过 0x11）。

### 13.5.2 为什么 DTC 覆盖只有 60% 不是问题

覆盖率的价值不是"追 100%"，而是**暴露测试盲区**：DTC 覆盖为 3/5，P0117（水温过低/传感器对地短路）和 P0135（氧传感器加热器开路，需手动注入）未被触发 —— 它们需要特殊工况。真实项目里这类条目会进入"待补测试"清单，由测试主管决定优先级。

**面试话术**："我会用覆盖率报告回答'测全了吗'，同时明确哪些未覆盖项是有意为之（需要特殊工况/硬件配合），哪些是遗漏。"

## 13.6 CI 集成

`.github/workflows/ci.yml`：每次 push/PR 自动跑，每晚 02:00（北京时间，cron 用 UTC 18:00）完整跑并归档。
一次完整全量约 **6 分钟**（本机实测 359~380s（多次实测）；CI 双版本矩阵无缓存约 8 分钟/版本，含安装与上传）。

```yaml
- name: 测试规范一致性校验（需求/自动化引用）
  run: python test_spec_check.py
- name: 生成测试用例（DBC → 边界值 / pairwise）
  run: python generate_testcases.py
- name: 运行测试（含交付报告 + 覆盖率 + 追溯矩阵）
  run: python run_tests.py --report
- name: 上传测试产物
  uses: actions/upload-artifact@v4
```

### 13.6.1 让测试"能在别的机器上跑"（跨平台的关键改造）

**CI 是 Linux，本地是 Windows**，几个必须做的改造：

| 问题 | 错误做法 | 正确做法 |
|---|---|---|
| 解释器路径 | 硬编码 `C:/Users/.../python.exe` | **变量文件暴露 `sys.executable`**（见下） |
| 文件路径 | 反斜杠、绝对路径 | `pathlib` + RF 的 `${CURDIR}` 相对路径 |
| 子进程 stdin | 不设 | 统一 `stdin=DEVNULL`（Windows 挂起防护，Linux 无害） |
| GUI | 必须装 PySide6 | **headless 模式**（不想起窗口/无显示环境也能跑用例；本项目 CI 实际仍会装 PySide6，只是用 `--headless` 运行） |

**解释器路径的最终解法**（`resources/env_vars.py`）——用过三种方案才找到对的：

```python
# env_vars.py —— RF 的 Variables 文件：模块级常量直接成为全局变量
import sys
PYTHON_EXE = sys.executable      # 永远等于"当前正在跑测试的解释器"
```

```robotframework
*** Settings ***
Variables        env_vars.py

*** Variables ***
${PYTHON}        ${PYTHON_EXE}
```

三种方案的教训：
1. 硬编码路径 → 换机器/CI 必挂；
2. 环境变量 → 直接 `python -m robot` 时取不到，落到 PATH 里没依赖的 python → **全部用例全失败**；
3. **库暴露变量** → 要用 `${库名.变量名}` 访问，别的地方引用不了；
4. **Variables 文件** → 模块级常量直接成全局变量 ✓ 任何启动方式都对。

### 13.6.2 统一入口 `run_tests.py`

```bash
python run_tests.py                    # 全部套件（主套件 198 + 场景 78 = 276）
python run_tests.py --suite 06         # 按名字过滤：命中 tests/robot/06 + scenarios/06
python run_tests.py --generate --report  # 生成用例 → 跑 → 出报告 + 覆盖率 + 追溯矩阵
```

它做的事：注入解释器变量、可选重新生成用例、跑 robot、串起交付报告、覆盖率与需求追溯矩阵（RTM）。**一个入口，本地和 CI 完全一致**——这本身就是测试工程化的基本原则（消除"环境差异"）。

> ⚠️ 如果 `--report` 阶段报 `ModuleNotFoundError: No module named 'yaml'`，说明依赖没装全：
> 在项目根目录执行 `pip install -r requirements.txt`（`trace_matrix.py` / `test_spec_check.py` 需要 PyYAML）。

| 1 | 因为 CSV **CANoe 打不开**，也没有向量格式的通道/时间戳语义。**ASC** = Vector 文本格式（可读、可 diff、体积大 → 适合归档和小数据量）；**BLF** = 二进制（体积小、支持大数据量 → 适合长时间录制） |
| 2 | 识别特征：**周期均值 ≈ 理论值 ÷ 接口数**（100ms 变成 ~52ms，本机 3 网卡）。修复思路：**接收端按 `(ID, 数据)` 在短时间窗内去重**（本项目用 5ms，远小于最快周期 100ms） |
| 3 | 保证：**任意两个参数的任一取值组合至少出现一次**（两两覆盖）。依据：大部分缺陷由**两参数交互**触发，三参数以上交互概率显著下降。3 信号 × 3 值：全组合 27 组 → **10~11 组**（贪心实现结果随集合顺序浮动，以生成文件为准） |
| 4 | 因为物理值超量程在**编码阶段就被拒绝**（信号位宽固定，编码会溢出）→ 根本发不出去。协议层极限测试应：**手工构造数据场**（把位域填满全 1），这也是真实台架的做法 |
| 5 | 用 **`0x28`（CommunicationControl）**：`28 01 01` 暂停 ECU 周期报文（保留诊断），测完 `28 00` 恢复 |
| 6 | 因为"用例文本搜索"会把**跳过的、没真正执行的**用例也算进去 → 数据虚高。只有**实际执行结果**（`output.xml`）才是真实执行的证据 |
| 7 | ①硬编码路径（换机器挂）②环境变量（直接跑 robot 取不到）③Library 变量（需库名前缀）④**Variables 文件** ✓ —— 模块级常量成为全局变量，`sys.executable` 永远等于当前解释器，任何启动方式都对 |
