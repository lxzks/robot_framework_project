## 1.1 整车电子架构：从"一个大脑"到"几个大脑"

传统汽车像这样——**分布式架构**：

```
        ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
        │ ECU1 │  │ ECU2 │  │ ECU3 │  │ ECU4 │   ......一辆车 50~100 个 ECU
        │发动机│  │ 车身 │  │ 气囊 │  │ 空调 │
        └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
           └─────────┴──── CAN 总线 ────┘
```

ECU（Electronic Control Unit，电子控制单元）就是**车载电脑**：一块带单片机/SoC 的电路板，跑着嵌入式软件，负责一块具体功能（管发动机、管车门、管气囊……）。

现代趋势是**域控制器（Domain Controller）**架构——把几十个 ECU 合并成几个"域大脑"：

| 域 | 管什么 | 代表产品 |
|---|---|---|
| 动力域 | 发动机、变速箱 | 发动机 ECU、VCU |
| 底盘域 | 转向、制动、悬架 | ESP、EPS |
| **座舱域** | **仪表、中控、HUD、娱乐** | **伟世通的主战场** |
| 自动驾驶域 | 感知、规划、决策 | 域控 + 传感器融合 |

**伟世通（Visteon）的核心业务就是座舱域**：数字仪表盘（Instrument Cluster）、中控信息娱乐（Infotainment）、HUD、以及把这些整合起来的座舱域控制器（SmartCore 类产品）。

你入职的"系统验证（System Validation）"，验证的就是这些座舱产品：**从 CAN 收到信号 → 仪表/HMI 正确显示；用户操作 → 功能正确响应；出故障 → DTC 正确记录、警告灯正确点亮。**

## 1.2 仪表盘（Instrument Cluster）是怎么工作的

你每天开车看到的方向盘后面那块屏幕/机械表，就是仪表盘。它的核心工作：

```
        CAN 总线信号                        仪表盘显示
   ┌────────────────────┐            ┌────────────────────┐
   │ 车速 60 km/h       │───────────►│ 车速表指针指到 60   │
   │ 转速 2400 rpm      │───────────►│ 转速表指针指到 2400 │
   │ 水温 95℃           │───────────►│ 水温表 + 正常(无灯) │
   │ 档位 D             │───────────►│ 中央显示 "D"        │
   │ 里程 12345 km      │───────────►│ 行程信息            │
   │ 警告灯位图(bitmap) │───────────►│ MIL/水温/安全带...   │
   └────────────────────┘            └────────────────────┘
```

### 1.2.1 车速是怎么"变成"指针的

这是一个**纯软件流水线**，用本教程的项目举例（对应 `dbc/vehicle.dbc`）：

1. **物理层**：发动机 ECU 通过 CAN 双绞线每 100ms 发出一帧报文，ID = `0x100`，8 字节数据，比如 `c4 09 80 0c 82 33 00 00`。
2. **解析（DBC）**：仪表盘的 CAN 驱动按 DBC 定义切分这 8 个字节：
   - 字节 0-1（`c4 09`）→ 车速原始值 `0x09c4` = 2500 → 乘以缩放因子 0.01 → **25.00 km/h**
   - 字节 2-3（`80 0c`）→ 转速原始值 `0x0c80` = 3200 → 乘以 0.25 → **800 rpm**
   - 字节 4（`82`）→ 水温原始值 130 → 减偏移 40 → **90℃**
3. **显示逻辑**：仪表应用拿到 25.00 km/h，换算成指针角度（比如表盘 270° 对应 0~240 km/h，则角度 = 25/240 × 270 = 28°），驱动 GPU/液晶把指针画在那个角度。

**测试要验证的就是这条链路的每一环**：报文发得对不对（01/02 章）、解析得对不对（07 章）、显示得对不对（09 章）。

### 1.2.2 警告灯（Telltale）——仪表盘的"报警台"

仪表盘上那些小灯，行业术语叫 **Telltale**。它们是**位图式**的：一帧报文里每个 bit 对应一个灯，0=灭 1=亮。本项目的 `0x300` 报文就定义了 12 个：

| bit | 信号名 | 灯 | 什么时候亮 |
|---|---|---|---|
| 0 | MilWarning | 发动机故障灯（MIL，长得像潜水艇） | 排放相关 DTC 确认 |
| 1 | OilPressureLow | 机油压力灯（像水壶） | 机油压力低 |
| 2 | CoolantTempHigh | 水温过高灯（像温度计插水里） | 水温 > 120℃ |
| 3 | BatteryLow | 蓄电池灯 | 电压 < 10.5V |
| 4~5 | AbsFault / AirbagFault | ABS / 气囊灯 | 对应系统故障 |
| 6 | SeatbeltWarning | 安全带未系 | 座位上有人没系带 |
| 8~9 | TurnLeft / TurnRight | 转向灯 | 拨杆 |
| 10~11 | HighBeam / LowBeam | 远/近光灯 | 灯光开关 |
| 12 | ParkBrake | 驻车制动 | 拉手刹 |

**关键点：警告灯和 DTC 是联动的**——ECU 检测到故障 → 记录 DTC → 通过报文告诉仪表"该亮灯了"。这套联动逻辑（故障注入→点灯→诊断仪确认→清除→灭灯）就是本教程 03/09 章实战的主线。

### 1.2.3 仪表盘软件栈（了解即可）

真实量产仪表盘（如伟世通产品）的软件分层：

```
┌─────────────────────────────────┐
│  HMI 应用层（Qt/QML 或 Android） │  ← 画表盘、动画、菜单
├─────────────────────────────────┤
│  仪表中间件（信号路由/报警管理）  │  ← 收 CAN 信号、管理 Telltale 策略
├─────────────────────────────────┤
│  AUTOSAR CP / QNX / Linux       │  ← 实时操作系统
├─────────────────────────────────┤
│  MCU + CAN 驱动 + 图形驱动       │  ← 硬件相关
└─────────────────────────────────┘
```

**QNX 是你可能接触的系统**（微内核实时 OS，车规安全认证 ASIL-D 可用，仪表/cluster 常用）；Android Automotive 用于中控大屏。你在 GM 外包项目里维护的 QNX 集群脚本工具，就是这个栈的"周边工具链"。

## 1.3 自动化测试在整车开发流程中的哪个位置

```
整车开发 V 模型（简化）：

需求                    系统集成测试        实车/台架验证
  │                          │                    │
  ▼                          ▼                    ▼
┌──┴──┐                  ┌───┴───┐            ┌───┴───┐
│ 需求 │ ───────────────►│ 系统测试│───────────►│ 验收  │
│ 设计 │                  │(你的岗位)│            │       │
└─────┘                  └───────┘            └───────┘
                              ▲
                    ┌─────────┴─────────┐
                    │ 单元测试  集成测试  │  （供应商/研发内部）
                    └───────────────────┘
```

**系统验证（System Validation）在 V 模型右侧**：产品集成完成后，你在台架（bench）或实车上，按测试规格（test specification）逐条验证功能是否符合需求。

### 1.3.1 测试类型地图

| 测试类型 | 验证什么 | 方法/工具 | 本项目对应 |
|---|---|---|---|
| **功能测试** | 信号→显示、操作→响应 | 台架操作 + 目视/截图 | 09 章 |
| **诊断测试** | UDS 服务、DTC 策略、安全访问 | CANoe/UDS 控制台、ODX | 03/04/08 章 |
| **总线测试** | 报文周期/错误帧/总线负载 | CANoe Trace、PCAN | 02/07 章 |
| **HMI/UI 测试** | 界面元素、动画、多语言 | 自研框架 + 图像识别 | 09 章 |
| **稳定性/压力** | 长时间运行、反复上下电 | 自动化循环 | 11 章挑战 |
| **Android 测试** | 应用安装/启动/交互/logcat | adb + uiautomator/Appium | 10 章 |

### 1.3.2 台架长什么样（想象图）

```
┌─────────────┐   CAN   ┌──────────────┐   HDMI   ┌──────────┐
│  CANoe/PC   │◄────────│  域控制器/    │◄────────│ 摄像头   │
│  (诊断仪)    │         │  仪表总成     │         │(拍屏幕)  │
└─────────────┘         └──────────────┘         └──────────┘
       │                                              │
       │                ┌──────────────┐              │
       └───────────────►│  测试工控机   │◄─────────────┘
                        │(跑你的 RF/Python 脚本)      │
                        └──────────────┘
```

- **CANoe/PCAN**：工业级 CAN 工具，能发报文、当诊断仪、录 Trace（行业标准，许可证很贵，学习阶段用我们的开源替代）。
- **摄像头拍屏幕 + 图像识别**：HMI 测试的常见手段（"仪表上水温灯亮没亮"用图像比对判断）。我们的 headless 仪表盘是"软件版摄像头"——直接把显示状态暴露成数据，比图像识别稳定得多。
- **测试工控机**：跑你的自动化脚本的地方。

## 1.4 你的技术栈地图

基于伟世通系统验证岗的常见技术栈，按**投入产出比排序**：

| 优先级 | 技能 | 用途 | 你的现状 |
|---|---|---|---|
| P0 | Python | 所有自动化的基础语言 | 入门中，需补数据结构 |
| P0 | Robot Framework | 系统验证岗常用框架（关键字驱动，非代码友好） | 本教程主攻 |
| P0 | CAN/UDS/DTC | 诊断测试核心三件套 | 本教程主攻 |
| P1 | CANoe（了解） | 行业标准工具，会看 Trace 会发报文 | 无许可证，用开源替代理解原理 |
| P1 | Linux/QNX 基础 | 台架环境、日志分析 | 有 QNX 脚本维护经验 |
| P2 | ADB/Android | 座舱大屏测试 | 本教程覆盖 |
| P2 | Git/CI | 脚本管理、 nightly 跑测 | 会用 |
| P3 | CAPL（CANoe 脚本语言） | 写 CANoe 自动化 | 入职后按需 |

**诚实评估**：伟世通系统验证岗日常大概率是"CANoe + Excel 测试用例 + 部分 Python 脚本"，Robot Framework 在车载圈不算主流（更常见于 API/系统测试），但**关键字驱动思想和测试架构是完全通用的**，且 RF 是学习"测试分层、关键字抽象、数据驱动"的绝佳载体——这些思想换任何框架都值钱。把本项目当成"车载测试 + 测试开发思想"的双修教材。

## 1.5 本项目（robot_framework）能证明什么

面试被问"你做过车载自动化吗"，你可以讲：

> "我在没有硬件的情况下，用 Python 搭了一套完整的车载仿真测试系统：
> - **车辆侧**：模拟了动力域 ECU——按 DBC 周期发送 CAN 报文（车速/转速/水温/档位/里程/警告灯），实现了 11 个 UDS 诊断服务，内置 DTC 状态机（pending→confirmed→aging 全生命周期）；
> - **座舱侧**：用 PySide6 做了两块屏——7 界面的座舱仪表（表盘/行程/媒体/导航/电话/设置/车辆信息）和 6 界面的安卓车机（桌面/媒体/导航/电话/空调/设置），通过 CAN 0x400/0x500 报文双屏联动；
> - **测试侧**：基于 Robot Framework 写了 4 个自定义关键字库和 61 个自动化用例，覆盖信号验证、诊断全流程（会话/安全访问/DID 读写/DTC 管理）、故障-点灯-清除闭环、ADB 车机流程；
> - **工程细节**：UDP 组播虚拟总线跨进程通信、ISO-TP 多帧传输、Windows 下 subprocess 句柄继承挂起等问题的定位与修复。"

这段话里每个点都能展开 10 分钟——因为都是你亲手写、亲手调出来的。

| 1 | **数字仪表盘**（Instrument Cluster）、**中控信息娱乐**（Infotainment/IVI）、**HUD 抬头显示**（外加座舱域控制器把三者整合） |
