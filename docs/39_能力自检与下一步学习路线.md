## 39.0 这章怎么用

> **默认前提**：扩展篇 **22~38 章已经学完**（至少每章对应的套件/模块跑过一遍）。
> 如果还没学完，本章不适合从头读——先去学完再回来做自检，否则每一行都会变成焦虑来源。

### 39.0.1 三个使用场景

| 场景 | 用哪节 | 用法 |
|---|---|---|
| **面试前 1~2 周** | 39.1 + 39.2 A 档 + 39.3 | 先用 39.2 A 档自测，答不上来的回到对应章节；再用 39.3 的结构把项目讲 3 遍（录音回听） |
| **入职前冲刺**（现在 ~ 入职） | 39.2 B 档 + 39.4 阶段 0/1 | 把 B 档里"完全没概念"的项列成清单，优先补：真实 CANoe 工程、台架流程、JIRA/DOORS、公司产品线 |
| **入职后 1 年** | 39.2 B/C 档 + 39.4 阶段 2/3 | 每季度打一次勾；勾不上的就是下一季度的成长目标，写进和主管的 1v1 |

### 39.0.2 三条使用原则

1. **"能讲 + 能举例"才算过。** 看着眼熟、能跟着教程跑一遍都不算。判据统一写成：
   *"不看资料，用自己的话讲清它是什么、为什么、本项目哪里能证明"*——讲不清就是没会。
2. **允许 ✅/🟡/⬜ 共存，不要追求全绿。** 没有任何个人项目能覆盖真实车载测试的全部。
   🟡（知道概念、能说清边界）和 ⬜（知道它存在、知道去哪学）本身就是专业度的一部分。
   面试官更看重你**知道自己不会什么**，而不是假装什么都会。
3. **每月重测一次。** 人的记忆衰减比想象快；入职后接触真实项目，很多 A 档题会"手生"。
   把 39.2 当成一张会折旧的体检表。

### 39.0.3 关于"数字"的说明

| 想知道 | 查哪里（不要背，以输出为准） |
|---|---|
| 当前用例数/通过率/耗时 | `python run_tests.py --report` |
| 需求覆盖率/孤儿用例 | `python trace_matrix.py` |
| 当前需求清单与编号 | `requirements/requirements.yaml` |
| 已知限制与待改进 | 项目根目录 [`KNOWN_ISSUES.md`](../KNOWN_ISSUES.md)（**本章所有 🟡/⬜ 以它为准**） |

> 本章宁可不写数字，也不写一个"下周就过期"的数字。
> 面试时被问规模，诚实回答"当前版本是 X"比背一个错数好——**面试官更在意你能不能现场给出准确答案**。

### 39.1.1 怎么读这张表

> 📌 **关于 Wave3 篇章（35~38 章 / 17~20 套件）**：它们是本轮（Wave3）新增内容。
> 如果你阅读时某个路径还不存在，说明该模块尚未合入——请以仓库实际为准；
> 本章的能力判断（✅/🟡/⬜）**只以"仓库里真实存在且能跑"为准**，不在的部分按 ⬜ 处理，别硬打勾。

- **✅ 是"面试可以当场演示"的**：随便挑一行，你能打开对应套件/模块跑给人看，并讲清关键断言。
- **🟡 是"能讲原理、能说清简化点"的**：面试官追问"真实台架也是这么测吗"时，你能明确回答
  "不是，真实情况是……，我项目里用……替代，差异在……"。**能主动说清差异，比假装做过更加分。**
- **⬜ 是"诚实边界"**：不要试图掩盖；正确说法是"这部分我没有条件做，但我知道它的输入、
  工具链和验证思路是……"。**边界清单就是 39.4 的学习路线表。**

### 39.1.2 三条"不要夸大"的红线（来自真实踩坑与 KNOWN_ISSUES）

1. **本项目验证的是"教学仿真器"，不是真实 ECU/台架**。CAN FD/SOME-IP/OBD/安全机制/Trace
   的"被测对象"都是我们自己的仿真器——它能证明**你的测试设计能力**，不能证明"你测过某量产件"。
2. **性能数字是本机基线，不是产品指标**。p95/负载/吞吐随机器、系统负载变化；面试引用时
   必须说明"本机、仿真、教学口径"。
3. **覆盖率 100% 是"需求-用例关联率"**，不等于"每条都测得够深"。详见 [KNOWN_ISSUES.md](../KNOWN_ISSUES.md) §四。
4. **项目里仍有已知的"测试有效性局限"**（个别用例是恒真/读回 echo/只断言正响应），
   清单在 KNOWN_ISSUES §四。这正是为什么 39.2 的判据强调"能证明断言有杀伤力"——
   能讲出"哪些用例我后来发现不够强、怎么补"，比只报覆盖率更加分。

## 39.2 岗位能力自检表（进阶版 · 三档 30+ 项）

> 用法：**能不看资料讲清 + 能举本项目/真实例子**才打勾。
> 打勾时在括号里写一句"证据"（哪个套件/哪份产物/哪次经历），写不出证据 = 没会。
> 三档不是"时间到了自然就会"，而是**能力半径**：A 档是求职门槛，B 档是独立干活，
> C 档是团队骨干。

### A 档 · 面试前就要能答（15 项）

- [ ] **A1 项目架构**：能画/讲清"仿真器 → 虚拟总线 → 关键字库 → RF 套件 → 需求追溯"的分层，
      并说明每层在真实 Tier1 里对应什么角色（台架/工具链/测试开发/测试执行）。
- [ ] **A2 CAN 帧与 DBC**：手画标准帧结构（SOF/仲裁/控制/数据/CRC/ACK/EOF），解释 DBC 的
      factor/offset/字节序/值表，能现场手算一帧 hex 的物理值（02 章的例子）。
- [ ] **A3 UDS 三格式**：请求 `SID+参数`、正响应 `SID+0x40`、负响应 `7F+原SID+NRC`；
      能默写 ≥6 个 NRC 的含义与典型触发场景（03 章）。
- [ ] **A4 会话/安全/刷写**：讲清 10/27 流程、S3 超时、0x34/0x36/0x37 + 0x31 FF00 的完整刷写链路，
      以及至少 4 条失败路径与对应 NRC（03 章 §3.5.12 / 06 套件 / [scenarios/07](../scenarios/07_flash_workflow.robot)）。
- [ ] **A5 DTC 状态机**：pending→confirmed→aging 的触发条件；8 个状态位；MIL latch 策略；
      能解释"为什么注入后不能立刻断言 DTC 存在"（04 章）。
- [ ] **A6 LIN**：主从调度表/槽位时基、PID 奇偶、经典 vs 增强校验和、睡眠/唤醒；
      能说清 CAN 与 LIN 的三个核心区别（23 章 / 08 套件）。
- [ ] **A7 DoIP**：ISO 13400 车辆识别/路由激活/诊断报文三类 payload；与 CAN 诊断的异同
      （"UDS 不变、运输层变"）；未激活发诊断为什么必须被拒（24 章 / 07 套件）。
- [ ] **A8 HMI 三条路线**：状态断言（headless JSON）/控件树（uiautomator/Appium）/视觉（golden），
      各自的优劣与适用场景；golden 管理与 mutation 防"恒真"（25 章 / 09 套件）。
- [ ] **A9 非功能口径**：为什么看 p95 不看平均；总线负载怎么估算；周期抖动/长稳分别防什么缺陷；
      "真实测量"与"按公式倒推"的区别（26 章 / 10 套件）。
- [ ] **A10 安全各一例**：信息安全能讲"27 02 绕过漏洞的修复"或"种子/重放/爆破防护"；
      功能安全能讲一个**安全机制验证**案例（E2E CRC+计数器 / 看门狗 / 失效降级之一，27/32 章）。
- [ ] **A11 证据链**：需求→规范→用例→执行→追溯→报告→缺陷单的闭环；
      能说清覆盖率/追溯矩阵**怎么算**、100% 的局限在哪里（13/20 章 / `deliverables/`）。
- [ ] **A12 诚实边界**：能主动、准确地说出 39.1 的 🟡/⬜ 与 KNOWN_ISSUES 里的 3 条以上限制，
      并解释"为什么项目这样取舍"。**面试官最爱问这题，答得好是加分项。**
- [ ] **A13 CAN FD**：能说清经典 CAN 与 CAN FD 的四个差异（数据段 0~64B、可变速率/BRS、
      ESI、CRC 与填充），能解释 DLC 映射与 float32 信号解码；说出 FD 在域控/ADAS 主干的作用
      （29 章 / `tests/robot/12_canfd.robot`）。
- [ ] **A14 SOME/IP / SOA**：能讲 Offer/Find/Subscribe 服务发现与 Method/Event/Field 的测试点；
      能说清 SOME/IP 与 CAN 信号模型（面向信号 vs 面向服务）的本质区别
      （30 章 / `tests/robot/13_someip.robot`）。
- [ ] **A15 OBD-II 与诊断进阶**：能区分功能寻址（0x7DF）与物理寻址（0x7E0）；
      能说出 OBD-II mode 01/03/04/09 的用途与 J1979/J2534 的关系
      （31 章 / `tests/robot/14_functional_addressing_obd.robot`）。

> A 档达标线：15 项里至少 12 项能脱稿讲、且每项都能打开对应套件/产物佐证。

### B 档 · 入职 3 个月内拿下（13 项 · 真实工作门槛）

- [ ] **B1 真实 CANoe 工程**：能打开/配置一个公司 CANoe 工程，加载 DBC、看 Trace、发报文、
      用诊断控制台发 UDS；能定位"丢帧/周期漂移/错误帧"（项目里用 recorder/ASC 是等价练习）。
- [ ] **B2 HIL/台架环境**：能按测试规范搭一次台架（电源 KL30/KL15、线束、诊断通道、IO 板），
      跑通一条需求并留下证据（见 38 章 HIL 抽象与 `tests/robot/20_hil_rack.robot` 的模拟版）。
- [ ] **B3 需求系统**：能在 DOORS/Jama 里读需求、查上下游、把用例挂到 Req ID（本项目用
      `requirements.yaml` + `trace_matrix.py` 等价练习）。
- [ ] **B4 缺陷管理**：能在 JIRA 提一个"开发愿意接"的缺陷单：现象/证据（Trace+日志+截图）/
      复现步骤/预期 vs 实际/影响范围；并跟进修复后回归。
- [ ] **B5 诊断一致性**：独立执行一个 ECU/座舱模块的诊断用例集（会话/安全/DID/DTC/刷写），
      能看懂 ODX/CDD 并定位参数问题（36 章 ODX 教学版是预演）。
- [ ] **B6 自动化落地**：把一条手工回归自动化（Python/CAPL/RF 均可），接入 CI 或 nightly，
      并让别人能不看你的电脑就复现结果。
- [ ] **B7 OTA 前健康检查**：独立完成 VIN/DTC/软件版本/电量/条件检查，能判断"这车能不能升"
      （35 章 OTA 链路 + `scenarios/14` 健康检查场景是预演）。
- [ ] **B8 电源/异常测试**：做一次欠压/过压/掉电/暗电流验证，能区分"产品缺陷"和"台架/工具问题"。
- [ ] **B9 非功能结论**：读懂总线负载/CPU/内存/启动时间等指标，写一份有结论的性能报告
      （不是只贴数字：要回答"是否达标、风险、下一步"）。
- [ ] **B10 ASPICE 证据**：按流程整理一次测试证据（计划/用例/结果/覆盖率/评审记录/追溯），
      能回答"审核员会看什么"（28 章 + 20 章模板）。
- [ ] **B11 沟通与评审**：能在评审会上讲清"测了什么、没测什么、风险是什么、建议是什么"，
      并接住开发/主管的追问。
- [ ] **B12 真实产品与业务**：说得清自己负责的模块在整车上的作用、上下游 ECU、失效后果
      （这是纯测试技能之外最值钱的部分）。
- [ ] **B13 Trace 与证据分析**：拿到一段 ASC/BLF 能独立算出总线负载、周期/抖动、
      定位丢帧与异常 ID，并写成缺陷单里的"证据段"（34 章 / `tests/robot/16_trace_analysis.robot`）。

> B 档达标线：入职 3 个月能做到 8 项以上，就算"站住了"；13 项全绿通常要 6~12 个月。

### C 档 · 入职 1 年内争取做到（10 项 · 从执行到负责）

- [ ] **C1 独立负责模块**：从需求分析→测试策略→用例设计→执行→报告→缺陷闭环，独立负责
      一个 ECU/域的测试包，不需要别人兜底。
- [ ] **C2 测试矩阵设计**：能针对一个模块设计正/负/边界/时序/异常/兼容矩阵，并能证明
      "覆盖不是凑数"（每条用例有明确杀伤力，见 39.1 的 mutation 思想）。
- [ ] **C3 台架自动化改造**：主导一次 HIL/台架自动化升级（接口无关层、真实 IO 替换、
      环境即代码），让回归从手工变成 nightly。
- [ ] **C4 工具/库沉淀**：建立或维护一个可复用资产（测试库、Trace 分析、报告生成、
      测试数据生成），团队里有人在用。
- [ ] **C5 风险决策**：在项目节点评审里解释"风险/取舍/缓解方案"，而不是只报"通过率"。
- [ ] **C6 带人**：能带一个新人跑通从环境到报告的完整链路（onboarding 材料、结对、评审）。
- [ ] **C7 前置评审**：参与需求/设计评审，提前指出"可测性/接口/诊断规范"问题（治未病）。
- [ ] **C8 审核支撑**：支撑一次 ASPICE/客户审核，能拿出完整证据链并回答过程问题（28 章）。
- [ ] **C9 现场问题**：跟进一次实车/现场问题复现，用"台架复现 + 日志 + Trace + 版本对比"定位。
- [ ] **C10 影响力**：形成自己的技术影响力：技术分享/文档沉淀/开源/专利/内部培训，任一即可。

> C 档达标线：1 年内做到 4~6 项，已经是团队里"能独立扛事"的人；
> 全绿通常需要 2~3 年，**不必焦虑，方向比速度重要**。

### 39.3.2 演示链路怎么选（按面试岗位三选一）

| 岗位侧重 | 推荐演示链路 | 为什么 |
|---|---|---|

3. **不要只讲成功**——主动讲一个"失败→定位→修复→方法论"的坑，比十个功能点更能证明真实动手。

## 39.5 常见职业问题 FAQ

**Q1：新人第一天/第一周应该做什么？**

> **第一天：先把"环境 + 人 + 规矩"摸清，别急着写代码。**
> ①拿到账号：邮箱/域账号/Git/SVN、JIRA、需求系统（DOORS/Jama）、CI 平台、台架预约系统；
> ②拿到工具：CANoe 许可、诊断仪、Trace 分析工具、办公软件；
> ③读材料：团队 wiki、产品手册、上季度测试报告、你的岗位 JD/绩效目标；
> ④认识人：导师（mentor）、直属主管、开发对接人、台架管理员、隔壁模块的测试同事；
> ⑤问清楚**安全规矩**（台架用电/上车/刷写权限）——这比技术重要。
>
> **第一周：跟着做，不抢活。** ①跟着前辈完整跟一次"需求→用例→执行→报告"；
> ②自己把项目环境（或同类仿真环境）跑起来；③问主管要一个"最小可交付任务"（如补一条用例、
> 复现一个已知缺陷）；④每天记 3 行笔记：今天学了什么黑话/工具/人。**第一周的目标不是产出，
> 是"下周一能独立接一个小任务"。**

**Q2：测试和开发怎么协作，怎么让开发愿意改 bug？**

> ①**先给证据，再下结论**：现象（时间/版本/台架）+ Trace/日志 + 最小复现步骤 + 预期 vs 实际；
> ②**分级定优先级**：阻塞/安全相关/一般/建议分开，让开发知道先修哪个；
> ③**对事不对人**：描述"系统行为"，不描述"你写错了"——"这条诊断在扩展会话下返回 0x7F，
> 预期应为 0x33，trace 见附件"比"你这里逻辑有问题"有效十倍；
> ④**闭环**：修复后你回归并回写结论；⑤**偶尔请开发喝咖啡**：先建立信任，再谈缺陷——
> 这是职场，不是代码评审。

**Q3：需求不清晰 / 自相矛盾怎么办？**

> ①**不要自己猜着测**：先记录问题（需求 ID、歧义点、两种理解的测试后果）；
> ②**带着方案去问**：不说"这条需求看不懂"，说"我理解有两种可能 A/B，如果按 A 我这样测，
> 按 B 那样测，影响是……，请确认"——这是测试工程师最值钱的动作之一；
> ③**留痕**：结论写进测试规范/评审记录（ASPICE 要求可追溯）；
> ④**时间盒**：一天内问不到答案，先按保守方案测并在报告里标注"需求待确认风险"，
> 不要因为等答复而停滞。

**Q4：线上/现场问题怎么复现和定位？**

> ①**收集三件套**：版本信息（软件/配置/数据库）、日志（DLT/logcat/系统日志）、总线 Trace
> （现场/售后一般能拿到）；②**在台架上复现**：还原电源/网络/ECU 状态，先确认"是不是真问题"；
> ③**二分定位**：按信号链路/时间线排除——物理层（供电/线束/终端电阻）→ 总线层（周期/错误帧/
> 负载）→ 协议层（UDS/ISO-TP）→ 应用层（功能逻辑）；④**对比法**：同版本好件 vs 坏件、
> 新旧版本、相同工况不同车；⑤**写清结论**：能不能复现、根因（产品/环境/操作）、
> 影响范围、修复建议——并归档到缺陷系统。

**Q5：如何做一次技术分享？**

> ①**选题**：讲你踩过的坑/做过的改进（有数据、有对比），不要讲"XX 协议概述"（网上都有）；
> ②**结构**：问题背景（1 分钟）→ 现象与影响（2 分钟）→ 分析过程（5 分钟，重点）→
> 解决方案与验证（3 分钟）→ 可复用的方法论（2 分钟）→ Q&A；
> ③**准备**：现场 demo 提前录屏兜底；一页一个观点；术语先解释再使用；
> ④**收尾**：把材料沉淀成文档/wiki，让没来的人也能看懂——**分享的价值在沉淀，不在讲台**。

**Q6：怎么评估自己"能独立干活"？**

> 三个可验证的标准，比"感觉"靠谱：
> ①**任务闭环**：给你一条需求/一个模块，不需要别人兜底也能走完"测试设计→执行→报告→缺陷闭环"；
> ②**问题兜底**：环境/工具出问题时，你能自己定位到"是谁的问题"（台架/工具/产品/需求）；
> ③**结论可信**：你写的"通过/不通过"别人敢直接用，不需要 double check。
> 达到这三条 = 独立；再往上"能带人、能改进体系"才是骨干（39.2 C 档）。

**Q7：入职后怎么避免"只会点按钮"？**

> ①**每做一件事问三个为什么**：为什么要测这个？不测会怎样？怎么证明测到了？
> ②**把重复劳动自动化**：哪怕只是一个小脚本，也比手点十遍有价值；
> ③**写下来**：测试笔记/踩坑记录/流程文档——写作是最快的深度思考；
> ④**主动接边界任务**：台架、工具、跨域联调，脏活里藏着最值钱的经验；
> ⑤**每年回顾一次 39.2**：能力半径有没有变大，而不是工龄有没有变长。
