# 16 · 调试技能：脚本跑不通怎么查

> 写脚本的时间只占 30%，**70% 的时间在调试**。
> 这一章教你用系统的方法定位问题，而不是"改一改再跑一遍"地瞎试。

---

## 16.1 最重要的工具：log.html

RF 每次跑完都会生成 `results/log.html` —— **这是你的调试主场**。
（跑的时候加 `--log log.html`，或者用 `python run_tests.py`）

打开它，你会看到用例的**每一步**：

```
✔ 车速信号应处于合理范围
  ✔ Read Signal From Bus    EngineData    VehicleSpeed
      收到 CAN 帧: ID=0x100 data=7017004b817f0000
      [VehicleBusLibrary] EngineData.VehicleSpeed = 60.0      ← 库的 info 日志
      ${speed} = 60.0                                          ← 返回值
  ✔ Should Be True    50 <= 60.0 <= 70
```

**三种信息**：
1. **每个关键字的入参**（我传了什么）
2. **返回值**（它给了我什么）
3. **库内部的日志**（它内部干了什么，如"收到 CAN 帧: ID=0x100 data=..."）

### 16.1.1 读 log.html 的三个技巧

| 技巧 | 做法 |
|---|---|
| 从**第一个 FAIL** 往下看 | 后面的失败往往是第一个的连锁反应 |
| 展开**嵌套关键字** | `Read DID As ASCII` 内部有 `Send UDS Request`，展开看实际发的 hex |
| 看**时间戳** | 某步耗时 3 秒 = 在等待/超时；某步耗时 4ms = 正常执行 |

### 16.1.2 加 `--loglevel DEBUG`

```bash
python -m robot --outputdir results --loglevel DEBUG my_test.robot
```

DEBUG 级别会记录**所有细节**（含库里的每次收发）。适合"明明应该收到响应却没有"这类问题。

## 16.2 错误类型速查

| 报错关键词 | 含义 | 排查顺序 |
|---|---|---|
| `No keyword with name 'X' found` | 关键字不存在 | ① 拼写/大小写 ② 库是否 `Resource` 引入 ③ 查速查表 |
| `Variable '${X}' not found` | 变量没定义 | ① 拼写 ② 作用域（套件变量 vs 用例变量）③ `${}` 花括号 |
| `Invalid argument type` / `Expected N arguments, got M` | 参数个数/类型不对 | 对着库关键字定义核对参数 |
| `Setting 'Template' accepts only one value` | `[Template] 关键字 参数` 写法错 | 参数移到数据行 |
| `3.0s 内没等到期望的数据` | **超时**（最高频） | 见 16.3 分层定位 |
| `Evaluating expression ... failed` | `Evaluate` 里的 Python 表达式错 | 先单独 `Log` 出参与运算的变量 |
| `AssertionError` 无信息 | 断言没带 `msg=` | 补上 msg（含期望/实际/怀疑方向） |
| `JSONDecodeError` / `PermissionError` | 状态文件读写竞争 | 重跑；持续出现查 06 章坑 12 |
| 套件 Setup 直接失败 | 被测环境没起来 | 看 `results/ecu_stdout.log`、`dashboard_stdout.log` |
| `Expected number, got list` | **RF 变量名大小写不敏感**：`${SAMPLES}` 与 `${samples}` 撞车 | 变量名取不同的词（如 `${SAMPLE_COUNT}`） |
| `List '${x}' used with invalid index` | 在 `Evaluate` 里写了 `${list}[i]`（被当成 RF 索引语法） | 用纯 RF 方案（`Sort List` + `Lists Should Be Equal`）或 `$list`（无花括号=Python 对象） |
| `does not contain 'X'` 但看着明明有 | 值里有空格/换行/隐藏字符 | 用 `[${value}]` 包起来看实际内容 |
| 跨系统比较差一点 | **动态值采样时刻不同**（还在变化中就比较） | 先等系统**进入稳态**再比较 |

## 16.3 分层定位法（超时的系统排查）

车载测试 80% 的失败是**超时**（"没等到"）。别急着改超时值——按层往下查：

```
① 物理层：进程活着吗？周期报文在发吗？
      ↓
② 协议层：请求发出去了吗？格式对吗？响应有回来吗？
      ↓
③ 应用层：响应回来了，但内容/时机不对？
```

### ① 物理层检查（先确认"车还在"）

```bash
# 看仿真进程的日志
tail -20 results/ecu_stdout.log
tail -20 results/dashboard_stdout.log
```

脚本里也能查：

```robotframework
检查环境是否健康
    ECU Should Respond                     # 诊断链路通不通
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Log    总线上的车速: ${speed}            # 周期报文在发吗
```

**如果这两个也超时** → 环境问题，不是你的脚本问题（查进程是否启动、端口是否被占）。

### ② 协议层检查（手动发一遍）

用 `uds_client.py` 手动发同样的请求，看 ECU 怎么答：

```bash
python simulators/uds_client.py
> 22 f187          # 手动发读零件号
   请求 22f187 → 正响应 SID=0x62 payload=f187...
```

**手动能通、脚本不通** → 你的脚本有问题（hex 拼错？会话没进？顺序不对？）
**手动也不通** → ECU/环境的问题（这一步就省了你半小时瞎改脚本）

### ③ 应用层检查（值不对但响应正常）

```robotframework
调试值不对的问题
    ${value}=    Read DID As ASCII    F187
    Log    实际读到: [${value}] 长度=${value.__len__()}     # 看实际值和长度
```

常见原因：
- **值里有空格/隐藏字符** → 用 `[${value}]` 包起来看
- **类型不同**（"60" vs 60）→ 用 `Should Be Equal As Numbers`
- **时序问题**（读早了）→ 换轮询等待

## 16.4 调试三板斧（动手顺序）

```bash
# 第一斧：只跑失败的用例，快速迭代（别每次跑全套件）
python -m robot --test "车速*" training/L1_first_case/exercise.robot

# 第二斧：开 DEBUG 日志 + 生成 log.html，看每一步
python -m robot --outputdir results --loglevel DEBUG my_test.robot
# → 打开 results/log.html，从第一个 FAIL 往下看

# 第三斧：手动复现（把脚本的动作在终端做一遍）
python simulators/ecu_sim.py --speed 60 --coolant 125    # 终端1：造场景
python simulators/uds_client.py                          # 终端2：手动发请求
```

**为什么"手动复现"这么重要**：它把"脚本 + 环境"的问题域切成两半——
如果手动能做通，问题 100% 在你的脚本里。

## 16.5 偶发问题（今天过、明天不过）

**偶发失败是车载测试最讨厌的问题**，也是最能体现水平的地方。

### 16.5.1 优先怀疑的三个原因

| 原因 | 特征 | 修法 |
|---|---|---|
| **用了 `Sleep` 猜时间** | 高负载时失败 | 换轮询等待（模式 2） |
| **超时值刚好卡在边界** | 大部分通过，偶尔失败 | 超时加大或改用轮询；查物理依据 |
| **测试间状态残留** | 连续跑失败、单独跑通过 | 加 Test Teardown 复位（模式 17） |

### 16.5.2 定位偶发的手段

```robotframework
捕获偶发现场
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Log    [${SUITE NAME}][${TEST NAME}] 车速=${speed} 时间=${...}    # 加时间戳和上下文
```

外部手段：
- **连续跑 N 次**（git bash / WSL）：`for i in 1 2 3 4 5; do python -m robot --test "X" tests/; done`
  PowerShell 写法：`1..5 | ForEach-Object { python -m robot --test "X" tests/ }`
  （跑 5 次都没复现 → 说明是低频问题，别急着改，先加日志等它复现）
- **看 Trace**：导出的 ASC 文件能回放"失败那一刻总线上发生了什么"（模式 19）

### 16.5.3 一个真实案例（本项目的偶发排查）

**现象**：仪表周期分析显示 0x100 的周期是 52ms，但设计值是 100ms。

**排查过程**：
1. 先怀疑抓包丢帧 → 调大 socket 缓冲区 → **没用**（还是 52ms）
2. 怀疑接收循环慢 → 换成 Notifier 后台线程 → **吞吐完全一样**
3. 说明发送端就只发了这么多 → 数一下本机网卡 → **3 个！**
4. 结论：**多网卡组播回环**，同一帧被收了两份 (100ms ÷ 2 = 50ms)

**教训**：当"修复方案不生效"时，**说明你的假设错了**，
要回头质疑假设（"周期真的是 100ms 吗？接收端真有问题吗？"），
而不是继续在同一个方向上试。

## 16.6 完整调试案例：从失败到定位

> 📌 **这是一个"复盘案例"**：它记录的是项目早期真实发生过的问题，
> **当前代码已经修复**（`_svc_read_did` 对未知 DID 会返回 NRC 0x31），
> 所以你现在照着重跑会直接 PASS。读这个案例的价值在**排查思路**，
> 而不是复现当年的失败。

**任务**：写一个"读取未知 DID 应返回 NRC 0x31"的用例。

**第一版（失败）**：

```robotframework
读取未知 DID 应返回参数超范围
    ${resp}=    Send UDS Request    22 F9 99
    Response Should Be Negative With NRC    0x31
```

运行结果：

```
失败: Expected NRC=0x31，实际: 正响应 SID=0x62 payload=f999...
```

**排查**：
1. 看 log.html → `Send UDS Request` 发的 hex 是 `22f999` ✓ 格式对
2. **手动复现**：`uds_client.py` 里发 `22 f999` → 也返回正响应！

→ **说明不是脚本问题，是 ECU 行为问题**（ECU 对未知 DID 没有拒绝）。
再查 `ecu_sim.py` 的 `_svc_read_did` → 果然：查不到 DID 时返回空数据而不是 NRC。

**修复**（改被测系统，而不是改测试）：

```python
# ecu_sim.py（历史修复示意）
def _svc_read_did(self, sid, p):
    did = (p[0] << 8) | p[1]
    if did not in DID_DATABASE:          # 常量名实际为 DID_DATABASE
        self._send_response(negative_response(sid, 0x31))   # ← 补上
        return
```

**这个案例的三个要点**：
1. **测试发现的第一个"bug"往往在被测系统里，不在测试里** —— 但要先证明不是测试的问题
2. **手动复现**是区分两者的最快手段
3. 测试用例写对了，它的价值就是**暴露了这个缺口**

## 16.7 调试清单（打印贴工位）

遇到失败，按顺序问：

1. 第一个 FAIL 在哪一步？展开 log.html 看**实际参数和返回值**
2. 是**超时**还是一开始就失败？
   - 超时 → 分层查（物理层 → 协议层 → 应用层）
   - 立刻失败 → 语法/变量/关键字问题（对照 16.2 表）
3. **手动能复现吗**？（能 → 脚本问题；不能 → 可能是偶发或环境）
4. 这个失败**单独跑也复现吗**？（单独过、连续挂 → 状态残留）
5. 上次改动是什么？（用 git diff 看）
6. 我改的是**测试**还是**被测系统**？（别把 bug 改成"测试能过"）
