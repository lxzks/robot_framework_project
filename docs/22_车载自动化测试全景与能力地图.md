> 📖 **零基础读法建议**
> - 🟢 **必读**：22.1 全景图、22.2 能力矩阵、22.3 学习路径 v2 —— 这三节回答"车载测试到底有多少东西、我现在在哪、接下来学什么"。

> 学完 00~21 再看这章，你会发现：不是项目太小，而是**车载测试本身太大** —— 大到没有任何一个项目能一次覆盖完。

## 22.0 为什么要读这一章

前 21 章 + `start_here/` 主线覆盖的是「**座舱域验证工程师的第一年**」：

- 一条 CAN 虚拟总线、一个动力域 ECU、一个仪表、一个安卓车机；
- 17 个 UDS 服务（14 核心 + 0x2F/0x23/0x3D）、DTC 状态机、刷写三件套；
- 需求 → 测试规范 → 用例 → 执行 → 追溯 → 报告 的交付链。

这套东西能让你**上岗后第一周就听得懂、第二周能接任务**。但真实车载测试的版图远不止此：
车身域（LIN）、底盘/动力高速总线（CAN FD）、车载以太网（DoIP / SOME-IP）、
OTA 与 Bootloader、诊断数据库（ODX/OTX）、HIL 台架、功能安全（ISO 26262）、
信息安全（ISO 21434）、产线 EOL、性能/长稳…… 每一项都是独立的知识块。

**本章的作用**：把这些能力块列成一张表，告诉你 ①它在行业里叫什么 ②本项目里用什么方式练（或为什么暂时练不了）③你的学习路线应该怎么排。

> ⚠️ **一个重要认知**：面试官/主管不会因为"你做过一个 276 用例的项目"就认为你会车载测试，
> 而是看你**能不能把新模块按同一套方法论快速学会**。所以本项目刻意做成"可扩展骨架"：
> 新增一个 LIN/DoIP 模块，走的是和 CAN 模块完全相同的结构（仿真器 → 关键字库 → 套件 → 教程 → 需求标签）。
> 你以后到公司接真实模块，干的也是这件事。

**读图方法**：从下往上，每一层都建立在下层之上。

- ②③是"能干活"的主战场（03/04/07/08/09/10 章 + 24/25 章）；
- ④⑤是"系统级验证"的分水岭（19 章场景 + 后续非功能/安全扩展）；
- ⑥⑦是"和普通测试拉开差距"的交付与流程能力（13/20 章 + 后续工具链扩展）。

## 22.3 学习路径 v2（按模块，而不是按章节）

> 00 章的 4 周计划是「**入职冲刺**」；下面是「**能力成长**」路线——入职后 3 个月到 1 年按这个走。

### M0 · 入门（已完成的 7 天主线）
- **目标**：能跑起仿真环境、写出第一个 RF 用例、理解"读值+断言+等待"。
- **材料**：`start_here/` D1~D7 + 05/14/15/16 章。
- **验收**：D7 跑完全量测试，能讲清一条用例从需求到报告的全过程。

### M1 · 总线与通信（W1~W2 深度）
- **目标**：看到 DBC/LDF 能读懂信号；能写周期/联动/边界/矩阵类用例；理解主从调度与睡眠唤醒。
- **材料**：02 章 → 07 章 → `01` 套件 → **23 章 LIN** → `08_lin_bus.robot` → `scenarios/08`。
- **动手**：给 LIN 调度表加一个从节点；把 CAN 抖动阈值从 20ms 收紧到 5ms 看会发生什么。
- **验收**：能不看资料讲清"CAN 与 LIN 的区别、各自典型场景"。

### M2 · 诊断与刷写（岗位核心）
- **目标**：能手发任意 UDS 请求、能写权限矩阵/负向/时序用例、能讲清刷写完整流程与失败路径。
- **材料**：03/04 章 → 08 章 → `02/03` 套件 → **24 章 DoIP** → `07_doip_diagnostics.robot` → `scenarios/03/04/05/07/09`。
- **动手**：用 `uds_client.py` 手动把所有服务发一遍；给 DoIP 模块加一条"DTC 读取"用例。
- **验收**：面试官随便说一个 UDS 服务/NRC，你能说出请求响应格式和典型测试点。

### M3 · 座舱与 HMI（差异化的实战经验）
- **目标**：能做状态断言 + 视觉断言；理解多屏一致性；能接 Android 车机。
- **材料**：09/10 章 → `04/05` 套件 → **25 章视觉自动化** → `09_hmi_vision.robot` → `scenarios/06`。
- **动手**：给视觉模块加一个"油量低报警灯"区域用例；用 ADB 真机替换 adb_sim 跑 04 套件。
- **验收**：能说清"HMI 自动化三种方式（状态/控件/视觉）的取舍"。

### M4 · 系统验证与交付（分水岭）
- **目标**：能把一个需求做成"需求 ID→规范→用例→追溯→报告→缺陷"的闭环。
- **材料**：17/19/20 章 + 13 章 + `training/L6` + `deliverables/`。
- **动手**：自己挑一条新需求（比如 LIN 雨量→仪表提示），走完整六环。
- **验收**：能在 15 分钟内讲清一个项目的"证据链"。

### M5 · 非功能与安全（高级能力，26~32 章，OTA 在 35 章）
- **目标**：会做性能/长稳/故障注入/模糊测试/安全机制验证。
- **材料**：26 章（性能/压力/长稳）+ 27 章（信息安全/Fuzz）+ 28 章（功能安全/ASPICE）+ 32 章（E2E/看门狗机制验证）+ `scenarios/11`。
- **动手**：跑 `10_nonfunctional_perf.robot` 看 p95/负载/吞吐；跑 `11_security.robot` 看模糊测试统计；给 26 章加一条"CPU 占用"类指标（需要激励接口）。
- **验收**：能设计一个"总线负载 80% 下诊断可用性"的测试方案并说明局限。

### M6 · 工具链与流程（和普通测试拉开差距）
- **目标**：会用/会说 CANoe、HIL、DOORS/Jama、JIRA、ASPICE 流程。
- **材料**：13 章 §13.6.3 工具链对照表 + 20 章 + 28 章（功能安全/ASPICE）+ 33 章（pytest/Docker/CI 接口）+ 37 章（Appium 真机 UI）+ 38 章（HIL 台架抽象）+ 39 章（能力自检）。
- **验收**：能解释"为什么 Tier1 要留证据链、ASPICE 审计看什么"。

## 22.6 常见误区（有基础再看）

| 误区 | 为什么错 | 正确认知 |
|---|---|---|
| "会用 CANoe 就是会车载测试" | CANoe 是工具，测试能力是"设计要求→测什么→怎么判" | 工具一周能学，测试设计要练一年 |
| "覆盖率 100% = 测全了" | 本项目需求覆盖率是 Tag 关联率，信号覆盖含构造覆盖 | 覆盖率是"发现盲区的工具"，不是 KPI |
| "自动化能替代手测" | HMI 主观体验、实车路试、异常恢复仍靠人 | 自动化做"重复+回归+可追溯"，人做"探索+判定" |
| "用例越多越专业" | 276 个用例在真实项目是零头，但盲目堆数量没意义 | 一条需求→一条能失败的用例，比十条恒真断言强 |
| "仿真台架没意义" | 台架是 Tier1 的日常，实车是最后一环 | 90% 的验证在台架/HIL 完成，实车只做确认 |
| "Flaky 重跑就行" | 偶发失败是真实缺陷的信号（时序/竞态/资源） | 必须定位根因，重跑只是临时绕过 |
