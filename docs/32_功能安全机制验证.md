## 32.1 为什么"功能正常"还不够：从 28 章到可跑代码

[28 章](28_功能安全与ASPICE测试过程.md) 讲的是**流程与标准**：ISO 26262 的危害分析（HARA）→
安全目标 → 安全需求 → 安全机制 → 验证。这一章把最后一步（**验证**）落到代码。

### 32.1.1 安全机制测试要回答的三个问题

对每一个安全机制（看门狗、E2E、范围检查、降级……），测试必须回答：

| # | 问题 | 反例（只做功能测试会发生什么） |
|---|---|---|
| ① | **能检测吗**（Detection） | CRC 实现写错，坏帧被当成好帧 —— 功能用例全绿，攻击/干扰随便进 |
| ② | **能反应吗**（Reaction） | 检测到了但没降级，执行器按坏数据动作 |
| ③ | **能恢复吗**（Recovery） | 故障消失后卡在安全状态，车"修好了"却动不了 |

**只验证"正常路径"是不够的**：功能测试证明"按设计输入时行为正确"，功能安全测试证明
"异常/故障发生时，系统仍处于安全状态"——这也是 ASIL 等级越高、越要求**故障注入**的原因
（28 章：**ASIL 越高，越要测异常，而不是多跑正常用例**）。

### 32.1.2 本章覆盖的三类安全机制

| 安全机制 | 真实项目形态 | 本项目实现 | 对应需求 |
|---|---|---|---|
| **E2E 端到端保护** | AUTOSAR E2E Library + SWC 配置：CRC + 计数器 | 8 字节 E2E Profile 1 教学帧（CRC8 + 0~14 计数器） | REQ-SAFE-001/002 |
| **看门狗** | 内部看门狗/外部硬件看门狗 + 任务喂狗 | 心跳任务 + 300ms 阈值 + SAFE_STATE | REQ-SAFE-003 |
| **降级/安全状态** | 故障管理（FiM/Dem）+ 降级策略 | NORMAL/DEGRADED/SAFE_STATE 状态机 + 故障标志 | REQ-SAFE-003/004 |
| **独立验证** | 独立测试工具/HIL 注入 | 测试端独立 CRC 实现 + 公开 check value + mutation | REQ-SAFE-005 |

## 32.2 E2E 保护：给通信加"端到端"的自我保护

### 32.2.1 总线上可能发生什么

CAN/LIN/以太网都**不保证**应用数据端到端正确。功能安全视角下的通信故障模式：

| 故障模式 | 例子 | 只靠功能测试能发现吗 |
|---|---|---|
| **位错误/篡改** | 干扰导致某位翻转；报文被恶意改写 | ❌ 数据"看起来"仍是合法值 |
| **丢帧** | 总线过载/节点重启，一段数据没收到 | ❌ 接收方可能一直用旧值 |
| **重复/重放** | 旧报文被重发（攻击或错误重传） | ❌ 接收方会再执行一次 |
| **乱序/延迟** | 报文晚到，执行器按过期数据动作 | ❌ 时序问题功能用例不管 |
| **伪装/错误源** | 另一个节点冒用 ID 发数据 | ❌ 接收方无法分辨 |

> **E2E（End-to-End）保护**就是在应用层给数据加"身份 + 序号 + 校验"，让**接收方自己**能判断
> "这帧数据可不可信"——不依赖总线/驱动层的错误检测（那只能防位错误，防不了丢帧/重放/错误源）。

### 32.2.2 为什么"只加 CRC"不够

- **CRC 防的是"数据被改"**：位翻转、篡改。
- 但攻击者/故障可以**重放**一帧完全合法的旧报文（CRC 也对！），或者**丢掉**中间的帧。
  接收方只看 CRC 会认为一切正常。

所以 E2E 至少需要三个要素：

```
dataId（我是谁/这是哪类帧） + counter（第几帧/顺序） + CRC（内容有没有被改）
```

这也正是 AUTOSAR E2E Profile 1 的基本思想（真实规范里还有 DataID 不进总线的变体、
窗口/超时监控等，见 32.12）。本章按**教学版**实现：DataId 直接放在帧里、CRC 覆盖
DataId+Counter+Data，便于逐字节讲解和独立验证。

### 32.2.3 真实项目里 E2E Profile 1/2/4/5/7 的区别（了解）

| Profile | 保护字段 | 典型场景 | 特点 |
|---|---|---|---|
| **1** | 4bit counter + CRC8 | 简单信号、周期报文 | 最轻量，本章教学版取自它 |
| 2 | 4bit counter + CRC8 | 与 Profile 1 类似但 CRC 计算范围不同 | 兼容老项目 |
| 4 | 16bit counter + CRC32 | 大数据/高安全等级 | 抗重放窗口 |
| 5 | 8bit counter + CRC16 | 兼顾开销与强度 | 商用常见 |
| 7 | 32bit counter + CRC32 | 大数据量（以太网） | 类 IPsec 风格 |

> 面试时能说出"Profile 1 是 4bit 计数器 + CRC8，最大计数器值 15 但 0~14 有效"就已经很加分。

## 32.3 E2E Profile 1 逐字节

### 32.3.1 帧格式（本教学版，8 字节）

```
  byte:   0     1     2      3     4      5       6       7
        +-----+-----+-----+-----+-----+-------+-------+-------+
        | dataId(2B) | ctr |   data(4B): 转向角 int16 | status|fault | CRC8 |
        +-----+-----+-----+-----+-----+-------+-------+-------+
         big-endian  0..14   0.1° 单位，大端        0/1/2   0/1/2   覆盖 0..6
```

| 字节 | 字段 | 取值 | 作用 |
|---|---|---|---|
| 0..1 | **dataId** | `0x5A01` 控制命令帧 / `0x5A02` 安全输出帧 | 区分帧类型；CRC 覆盖它 → 不同帧类型的 CRC 不可混用 |
| 2 | **counter** | 0~14 循环（15 非法） | 接收端靠它发现丢帧（delta>1）、重复/重放（delta=0） |
| 3..4 | **data: 转向角** | int16 大端，单位 0.1°（150 = 15.0°） | 安全节点透传给下游执行器的转向角 |
| 5 | **status** | 0=正常输出 1=安全值 2=无效 | 输出状态（供下游判断数据可用性） |
| 6 | **fault_level** | 0/1/2 | 故障等级，与状态机一致 |
| 7 | **CRC8** | CRC-8/SAE-J1850，覆盖 byte0..6 | 内容完整性（防位错/篡改） |

**一个真实的合法帧**（counter=0，转向角 15.0°，status=0，fault_level=0）：

```
5A 01 00 00 96 00 00 9E
│  │  │  └──┬──┘ │  │  └── CRC8 = 0x9E（下一节手算）
│  │  │     └ 0x0096 = 150 = 15.0°
│  │  └ counter = 0
└──┴ dataId = 0x5A01
```

### 32.3.2 counter 的语义：接收端怎么判

接收端每收到一帧，计算 `delta = (counter - last_counter) mod 15`：

| delta | 含义 | 接收端动作 | 本项目的处理 |
|---|---|---|---|
| **1** | 正常递增 | 接收数据、更新 last | 接受；若在 DEGRADED，累计恢复帧数 |
| **0** | 重复帧 / 重放 | 拒绝（可能是攻击或错误重传） | 拒绝，`replays++`，累计错误 |
| **2~3** | 丢了 1~2 帧（可容忍） | 接收最新数据 + 记录丢失帧 | 接受，`lost_frames += delta-1` |
| **>3** | 跳变超阈值（严重通信故障） | **立即降级**（不等连续 3 次） | 拒绝 + DEGRADED + `counter_errors++` |
| counter=15 | 非法值（4bit 只用 0~14） | 拒绝 + 计数 | 拒绝，`counter_errors++` |

> **为什么本项目是 0~14 而不是 0~15**：需求（E2E-SPEC-1.2）约定 4bit 计数器只使用 15 个值，
> 15 保留为"非法/复位"语义，校验到 counter=15 直接拒绝并计数。真实 AUTOSAR E2E Profile 1 的
> 计数器同样是 4bit，但**具体有效范围/回绕规则以项目的 E2E 配置与 ICD 为准**——测试要按 ICD 判，
> 而不是按教科书默认值（这也是功能安全测试"按需求验证"的体现）。
>
> **回绕**：换一圈回到 0 时 `delta = (0-14) mod 15 = 1`，接收端仍视为"正常递增"（不是丢帧）。
> 本章实测序列 `0,1,2,...,13,14,0` ✓ —— 所以"回绕点"是计数器实现最容易写错的地方之一。

### 32.3.3 接收端判定流程（伪代码）

```python
frame = recv()
if len(frame) != 8:            reject("bad_length")
if dataId != 0x5A01:           reject("bad_data_id")
crc_ok = (crc8(frame[0:7]) == frame[7])
delta  = (frame.counter - last_counter) % 15
last_counter = frame.counter          # 教学简化：格式合法帧都推进计数器
if not crc_ok:                 crc_errors++;      degrade_if_needed()
elif delta == 0:               replays++;          reject("replay")
elif delta > 3:                counter_errors++;   degrade_immediately()
elif delta in (2,3):           lost_frames += delta-1; accept()
else:                          accept(); if degraded: recovery_count++
```

> **教学简化要讲清楚**：真实 E2E 库只在 CRC 正确的帧上推进 counter 状态；本项目为了
> "连续注入 CRC 错后仍能恢复序列"（便于测试隔离）让所有格式合法帧都推进 counter。
> 差异写在 32.9.6，真实项目采用标准 E2E Library 的行为。

## 32.4 CRC-8/SAE-J1850：手算 + 独立实现

### 32.4.1 参数（背下来面试能加分）

| 参数 | 值 | 说明 |
|---|---|---|
| 宽度 | 8 bit | 结果一个字节 |
| **多项式 poly** | **0x1D** | x⁸ + x⁴ + x³ + x² + 1（SAE J1850 标准） |
| **初值 init** | **0xFF** | 全 1，避免全 0 数据 CRC 恒为 0 |
| **输出异或 xorout** | **0xFF** | 与初值配合，进一步增强检错 |
| refin / refout | false | 不反射，MSB first |
| 公开 check value | `crc8("123456789") = 0x4B` | **验证实现正确性的黄金标准** |

> 为什么选它：AUTOSAR E2E Profile 1 标准就用 CRC-8/SAE-J1850；8 位 CRC 对一个 8 字节
> 报文足够（能检出所有单/双比特错误、绝大多数突发错误），计算开销极小（适合 10ms 级报文）。

### 32.4.2 位运算实现（逐位模拟硬件）

```python
def crc8_sae_j1850(data: bytes) -> int:
    crc = 0xFF
    for byte in data:
        crc ^= byte
        for _ in range(8):            # 每个字节移 8 次
            if crc & 0x80:            # 最高位为 1 → 异或多项式
                crc = ((crc << 1) ^ 0x1D) & 0xFF
            else:
                crc = (crc << 1) & 0xFF
    return crc ^ 0xFF
```

### 32.4.3 手算示例：`5A 01 00 00 96 00 00` → CRC = 0x9E

逐字节计算（初值 0xFF）：

| 步骤 | 输入字节 | crc ^= byte（异或后） | 移 8 位后 |
|---|---|---|---|
| 初始 | — | — | 0xFF |
| 1 | 0x5A | 0xA5 | 0xC8 |
| 2 | 0x01 | 0xC9 | 0xC0 |
| 3 | 0x00 | 0xC0 | 0x35 |
| 4 | 0x00 | 0x35 | 0x23 |
| 5 | 0x96 | 0xB5 | 0x05 |
| 6 | 0x00 | 0x05 | 0x69 |
| 7 | 0x00 | 0x69 | 0x61 |
| 输出 | 异或 0xFF | 0x61 ^ 0xFF | **0x9E** |

所以完整帧就是 `5A 01 00 00 96 00 00 9E`。**建议自己用纸笔走一遍第 1、2 步**：
面试问"CRC 怎么算"时，能说清"初值、异或字节、左移判最高位、异或多项式、最后异或输出"
比背公式强得多。

### 32.4.4 两个"校验值"帮你确认实现

```text
crc8(b"")            = 0x00          # init 0xFF，没有数据 → xorout → 0x00
crc8(b"123456789")   = 0x4B          # CRC-8/SAE-J1850 的官方 check value
```

第一行能验证 init/xorout 有没有写对；第二行验证整条算法（含多项式方向）。

### 32.4.5 常见实现坑（两端不一致 = 永远校验失败）

| 坑 | 错误写法 | 现象 |
|---|---|---|
| 多项式方向写反 | 用 0x8F（反射版） | 永远对不上 |
| 初值/输出异或漏掉 | init=0x00 或没有 `^0xFF` | 部分帧偶然对上、多数失败 |
| 覆盖范围不一致 | 发送方覆盖 data，接收方含 dataId | 全部失败 |
| 用了别的 CRC8 变体 | CRC-8/ATM（poly 0x07，refin=true） | 全部失败 |
| 字节序不一致 | dataId 小端 vs 大端 | 全部失败 |

> **功能安全视角**：CRC 算法两端必须"逐参数一致"，所以真实的 E2E 项目会把算法/参数写在
> 接口控制文档（ICD）里并做**端到端集成测试**——本章的 `E2E Crc Should Be Valid` 就是这个角色。

## 32.5 看门狗：程序"还活着"的证据

### 32.5.1 为什么需要看门狗

ECU 软件可能"跑飞"：死循环、阻塞在某个驱动、任务被更高优先级饿死、内存踩踏后行为异常。
这时功能代码**不会主动报错**——车看起来"没反应"，但也没有任何故障码。

**看门狗（Watchdog）** 就是独立的"监控者"：被监控任务必须**周期性喂狗**（更新心跳）；
超时没喂 → 判定任务卡死 → 复位/降级/进入安全状态。

| 类型 | 规则 | 能抓的问题 |
|---|---|---|
| **简单看门狗** | 超过时间没喂 → 触发 | 卡死、死循环、任务不跑 |
| **窗口看门狗** | 喂狗**太晚或太早**都触发 | 加上"任务节奏异常"（如被异常唤醒后狂跑） |
| 外部硬件看门狗 | 独立芯片，MCU 挂死也能复位 | 软件完全失控 |

### 32.5.2 本项目的心跳机制

```
heartbeat 线程 ──每 50ms──▶ 更新 last_heartbeat（这就是"喂狗"）
watchdog+tx 线程 ─每 20ms─▶ 检查 now - last_heartbeat
                              │
                 > 300ms ? ────┴──▶ 进入 SAFE_STATE + fault_level=2 + WATCHDOG 故障标志
                                    （记录 reaction_ms = 触发时心跳年龄）
                 心跳恢复（年龄 < 150ms）──▶ 自动清 WATCHDOG、回到 NORMAL
```

参数：

| 参数 | 值 | 说明 |
|---|---|---|
| 喂狗周期 | 50ms | 内部任务心跳 |
| 巡检周期 | 20ms | 看门狗检查频率 |
| **超时阈值** | **300ms** | 需求规定；真实项目由安全分析（FTTI）决定 |
| 恢复条件 | 心跳年龄 < 150ms | 阈值×0.5，防止"喂了一拍就立刻恢复"的抖动 |

### 32.5.3 300ms 这个数字从哪来

真实项目里看门狗超时**不是随便定的**，它来自安全时间预算：

```
故障发生 → 检测（看门狗超时）→ 反应（降级/复位）→ 系统进入安全状态
└──────────────────── 必须在 FTTI（Fault Tolerant Time Interval）内完成 ────────────────────┘
```

例如"转向角数据失效 → 执行器必须在 500ms 内回正"，那看门狗超时 + 降级动作之和必须
小于 500ms，留出余量后取 300ms。**测试要验证的不是"300ms 这个数字"，而是"超时后确实
在预期时间内进入安全状态"**——所以 `Watchdog Should Trigger Degradation` 会断言节点
自报的反应时间 ≥ 阈值的 80%（太快说明判定条件写错了），并记录实际观测耗时。

### 32.5.4 看门狗怎么测（方法比实现更重要）

| 注入方法 | 模拟的故障 | 本项目命令 | 能验证什么 |
|---|---|---|---|
| **停止心跳** | 任务不再喂狗（卡死/饿死） | `Inject Heartbeat Stop` | 超时 → SAFE_STATE |
| 恢复心跳 | 任务恢复运行 | `Resume Heartbeat` | 自动恢复 NORMAL |
| 冻结线程 | 断点/暂停（HIL 上可用调试器） | （真实台架手段） | 与停止喂狗等价 |
| 喂狗过快 | 任务异常高频运行（窗口看门狗才管） | （本教学版无窗口看门狗） | 窗口看门狗特性 |

> **要点：测试端必须是"外部注入 + 外部观测"**。如果测试脚本调用被测代码里的
> `is_watchdog_ok()` 来判断，等于让被测对象自己出庭作证——见 32.8。

### 32.5.5 本模块看门狗实测

| 指标 | 实测 | 说明 |
|---|---|---|
| 触发时心跳年龄（节点自报 reaction_ms） | **≈301~322ms** | 阈值 300ms + 巡检/线程调度余量 |
| 注入命令 → 测试端观测到 SAFE_STATE | **≈310~330ms** | 含 UDP 往返与 20ms 轮询间隔 |
| 恢复心跳 → 回到 NORMAL | **≈21~42ms** | 心跳立即刷新，下一个巡检周期恢复 |
| SAFE_STATE 时输出 | `valid=false`、`steering_angle=null`、`mode=INVALID` | 不给执行器错误指令 |

## 32.6 降级与安全状态：状态机

### 32.6.1 状态机图

```
                   连续 3 条 E2E 错误
                  或计数器跳变超阈值
      ┌─────────┐ ─────────────────────▶ ┌────────────┐
      │ NORMAL  │                        │  DEGRADED  │
      │ 正常输出│ ◀───────────────────── │ 输出安全值 │
      └─────────┘  连续 3 条合法帧       │ (转向角=0) │
           │       或 Clear Fault        └────────────┘
           │                                  │
           │ 心跳停止 > 300ms                  │（优先级更高）
           ▼                                  ▼
        ┌─────────────────────────────────────────┐
        │              SAFE_STATE                 │
        │   输出无效（valid=false, mode=INVALID）  │
        │   心跳恢复 → 自动回 NORMAL               │
        └─────────────────────────────────────────┘
```

### 32.6.2 三个状态的行为对照

| 状态 | fault_level | 输出 | 触发条件 | 恢复条件 |
|---|---|---|---|---|
| **NORMAL** | 0 | 透传最新合法转向角，`mode=NORMAL` | 上电/复位 | — |
| **DEGRADED** | 1 | **安全值转向角=0**，`mode=SAFE_VALUE` | 连续 3 条 E2E 错误 / 计数器跳变超阈值 | 连续 3 条合法帧 / Clear Fault |
| **SAFE_STATE** | 2 | **输出无效**，`mode=INVALID` | 心跳停止超 300ms（严重故障） | 心跳恢复 |

> **降级 ≠ 安全状态**：DEGRADED 表示"我还能工作，但只输出预定义的安全值"；
> SAFE_STATE 表示"我不知道现在该输出什么，所以停止输出/交权给备份"。
> 两者对应不同的安全目标，**不能混为一谈**（面试常问）。

### 32.6.3 故障标志（DTC 风格 fault flag）

| 标志 | 置位时机 | 清除时机 |
|---|---|---|
| `E2E_CRC_ERROR` | 连续 3 条 CRC 错误 → DEGRADED | 恢复（连续合法帧 / Clear Fault） |
| `E2E_COUNTER_ERROR` | 计数器跳变超阈值 → 立即 DEGRADED | 同上 |
| `E2E_REPLAY` | 重复/重放累计到 3 次 → DEGRADED | 同上 |
| `WATCHDOG` | 心跳超时 → SAFE_STATE | 心跳恢复 / Clear Fault |

> 真实项目里 fault flag 会映射到 **DTC**（[04 章](04_DTC详解.md)），并通过 0x19 读取——
> 本模块用 JSON 状态里的 `fault_flags` 简化演示同一套"故障记忆"思想。

### 32.6.4 为什么是"连续 3 次"而不是一次

- **误报控制**：总线上偶发 1 帧位错误是正常现象，一次错误就降级会让系统太"敏感"（可用性差）；
- **持续故障才危险**：连续 3 条都错说明链路/发送端真的坏了；
- **恢复也要连续**：连续 3 条合法帧才恢复，防止"错误-正确-错误"的抖动导致状态反复切换；
- **阈值是需求**：具体数字（3 次、300ms）都应有安全需求支撑，测试要能在阈值附近验证
  （2 次不降级、3 次降级）。

## 32.7 故障注入矩阵（安全机制测试的"用例设计表"）

| 注入类型 | 构造方式 | 预期节点反应 | 对应用例 | 能抓的缺陷 |
|---|---|---|---|---|
| CRC 位翻转 | CRC 字节取反 | 拒绝 + `crc_errors++`，单次不降级 | ③ | CRC 没校验/校验范围错 |
| 连续 CRC 错 | 连发 3 帧坏 CRC | DEGRADED + 安全值 + 故障标志 | ④ | 无降级策略/阈值错 |
| 计数器跳变 | delta=5（丢 4 帧） | 拒绝 + `lost_frames=4` + 立即 DEGRADED | ⑤ | 无序列检测/跳变阈值错 |
| 轻微丢帧 | delta=2/3 | 接受数据 + 记录丢失帧（不降级） | （⑤ 的对照语义） | 把轻微丢帧误判成严重故障 |
| 重放旧帧 | 原样重发上一帧 | 拒绝 + `replays++`，序列不被破坏 | ⑨ | 无重放防护 |
| 心跳停止 | `stop_heartbeat` | 300ms 后 SAFE_STATE + fault_level=2 | ⑦ | 无看门狗/阈值错 |
| 心跳恢复 | `resume_heartbeat` | 自动回 NORMAL、清 WATCHDOG | ⑧ | 只能进不能出（卡死安全状态） |
| 坏长度/dataId | 非法帧 | 拒绝并计数，节点不崩 | （本套件未单列，节点已实现） | 协议健壮性 |
| 坏帧 mutation | 测试端独立校验坏帧 | 测试端**必须报错**（验证校验不恒真） | ⑩ | 测试自己恒真 |

> **真实项目对应手段**：CANoe/CAPL 发错误帧、HIL 继电器断线/短路、电源程控扰动、
> 软件故障注入 hook（AUTOSAR 的 FiM 触发）。注入的本质都是"让被测系统遇到真实故障"。

## 32.8 独立验证原则：安全机制不能"自己证明自己"

### 32.8.1 自证陷阱（本章最重要的方法论）

假设测试端这样写：

```python
# ❌ 错误做法：测试端 import 被测实现的 CRC
from simulators.safety_ecu import crc8_sae_j1850
assert crc8_sae_j1850(frame[:7]) == frame[7]
```

如果被测的 CRC 实现有 bug（比如多项式写错），测试端**用的是同一份错误实现**，
算出来依然"相等"——用例全绿，实际链路两端都算错。这就是**自证（self-fulfilling）**：

> 安全机制验证的价值 = 测试手段的**独立性**。测试工具/测试人员必须与被测实现独立，
> 否则测的是"两份同样的错误实现是否一致"，而不是"实现是否正确"。

28 章自检第 5 题"为什么看门狗的测试不能依赖被测的看门狗"就是同一个道理：
**用被测对象自己报告的状态来证明它自己正常，是循环论证。**

### 32.8.2 本项目的四条独立措施

| # | 措施 | 实现 |
|---|---|---|
| ① | **独立实现 CRC** | `libraries/SafetyLibrary.py` 里**重复实现** `crc8_sae_j1850`，不 import 被测模块 |
| ② | **公开 check value 自证** | `Crc8 Should Be` 断言 `crc8("123456789")==0x4B`——测试端实现本身也要被验证 |
| ③ | **双向交叉验证** | 测试端算的 CRC 被节点接受（发正常帧）；节点发回的帧被测试端独立重算（`E2E Crc Should Be Valid`） |
| ④ | **mutation 负向验证** | 坏 CRC 帧必须让测试端校验**失败**（`Run Keyword And Expect Error`），证明校验不是恒真 |

```robotframework
# ④ mutation 的写法：故意拿一帧坏 CRC，断言"校验必须报错"
${bad}=    Inject E2E Error    crc
Run Keyword And Expect Error    *CRC 校验失败*
...    E2E Crc Should Be Valid    ${bad}[frame]
```

> 这是"**测试的测试**"：如果 `E2E Crc Should Be Valid` 恒返回通过，这条用例就会红。
> 和 25 章视觉测试的 mutation 用例（故意改状态，比对必须失败）是同一个思想。

### 32.8.3 两个 CRC 实现的关系（刻意重复）

| 位置 | 用途 | 是否复用 |
|---|---|---|
| `simulators/safety_ecu.py::crc8_sae_j1850` | **被测实现**（节点校验/生成帧） | — |
| `libraries/SafetyLibrary.py::crc8_sae_j1850` | **测试端独立实现**（计算/重算） | ❌ 不 import 被测代码，只共享协议常量 |
| `Crc8 Should Be` | 用公开 check value 验证测试端实现 | ✅ 测试实现的自检 |

> 面试话术："我的安全测试框架里 CRC 有两份独立实现：被测节点一份、测试端一份，
> 测试端用 CRC-8/SAE-J1850 的公开 check value 自证，再和节点双向交叉验证 + 坏帧 mutation。
> 这样被测实现有 bug 时测试不会跟着一起错。"

## 32.9 本项目实现

### 32.9.1 架构

```
tests/robot/15_safety_mechanisms.robot     ← 10 条用例（声明式）
        │  关键字调用
        ▼
libraries/SafetyLibrary.py (SUITE scope)   ← 18 个关键字 + 独立 CRC 实现
        │  JSON over UDP 127.0.0.1:30600（端口可用 SAFETY_UDP_PORT 覆盖）
        ▼
simulators/safety_ecu.py（独立进程）       ← 被测安全节点
        ├─ UDP server 线程：收命令/回状态（ping/status/e2e_frame/stop_heartbeat/...）
        ├─ heartbeat 线程：每 50ms 更新心跳（被看门狗监控）
        └─ maintenance 线程：每 20ms 看门狗巡检 + 每 50ms 发 E2E 安全状态帧
```

为什么把安全节点做成**独立进程 + 独立 UDP 通道**：

1. 故障注入需要发送**任意非法字节**（坏 CRC/跳变计数器），独立通道可以精确构造；
2. 套件**不依赖 ECU/虚拟 CAN**，可独立进 CI（整个套件约 5 秒）；
3. 节点崩溃/卡死不会拖垮测试进程，测试端能继续观察/回收；
4. 真实项目中 E2E 帧跑在 CAN/CAN FD 上——**只把传输层换成 UDP，帧格式/状态机/算法完全一致**
   （8 字节正好是一帧经典 CAN 的数据场，见 32.12 的差异说明）。

### 32.9.2 关键字清单（18 个）

| 关键字 | 作用 | 返回 |
|---|---|---|
| `Start Safety Node` | 拉起安全节点进程 + 等就绪 + 复位 | — |
| `Stop Safety Node` | quit + 回收进程/端口（Teardown） | — |
| `Reset Safety Node` | 全量复位（用例隔离） | — |
| `Send Safety Frame` | 发一帧**合法** E2E 帧（测试端独立算 CRC） | dict（accepted/reason/counter/state） |
| `Inject E2E Error` | 注入 CRC 错 / 计数器跳变 / 重放帧 | dict（含 reason/lost_frames） |
| `Read Safety Status` | 读节点完整状态 | dict（状态/输出/E2E 统计/看门狗） |
| `Safety Status Should Be` | 轮询断言状态机（NORMAL/DEGRADED/SAFE_STATE） | 观测耗时 ms |
| `Safety Output Should Be Safe Value` | 断言 DEGRADED 输出安全值（转向角=0） | — |
| `Safety Output Should Be Invalid` | 断言 SAFE_STATE 输出无效 | — |
| `E2E Counter Should Advance` | 连续发 N 帧验证计数器递增/回绕 | 计数器序列 list |
| `E2E Error Counter Should Be` | 断言 crc/counter/replay/lost/total 错误计数 | — |
| `E2E Crc Should Be Valid` | 测试端独立重算 CRC（含 mutation 负向） | 解码后的帧字段 dict |
| `Crc8 Should Be` | 用公开 check value 验证独立 CRC 实现 | 计算值 |
| `Inject Heartbeat Stop` | 注入"任务卡死"（停止喂狗） | dict |
| `Resume Heartbeat` | 注入"任务恢复" | dict |
| `Watchdog Should Trigger Degradation` | 等待/断言看门狗触发 SAFE_STATE | 反应时间 ms |
| `Clear Fault` | 手动清故障（诊断仪 0x14 语义） | dict |
| `Fault Flag Should Be` | 断言故障标志置位/清除 | — |

### 32.9.3 节点状态机实现要点

- **状态推导**（`_recompute_state`）按优先级：`SAFE_STATE > DEGRADED > NORMAL`——
  看门狗故障优先级最高（任务卡死时 E2E 降级没有意义，系统已经不可信）；
- **降级触发**分两种：连续错误达阈值（CRC/replay）、严重计数器跳变（立即）；
- **恢复**：连续 3 条合法帧自动恢复；心跳恢复自动退出 SAFE_STATE；`Clear Fault` 手动清；
- **故障记忆**：错误计数**保留**（供测试断言"确实检测到了 N 次"），只有 fault_flags 在恢复时清除。

### 32.9.4 进程/端口管理（工程细节）

- 用 `sys.executable` 启动节点（与 robot 同一解释器，**不硬编码路径**）；
- 端口可用 `--port` 或环境变量 `SAFETY_UDP_PORT` 覆盖（默认 30600）；
- 节点 stdout/stderr 重定向到 `results/safety_ecu_stdout.log`（失败时可查）；
- `Stop Safety Node`：quit → 等 3s → terminate → kill，**必须回收干净**（否则下次端口占用）；
- 启动就绪用 `ping` 轮询（不是 sleep 猜时间）；
- **Windows UDP 坑**：向还没有进程监听的端口发 UDP，会收到 ICMP 端口不可达，
  下一次 `recvfrom` 抛 `ConnectionResetError(10054)` 而不是超时——本库把它翻译成
  "节点未就绪"由启动轮询重试兜住（Linux 无此问题）。

### 32.9.5 测试隔离

安全节点是**有状态**的（降级/计数器/故障标志）。不做隔离的典型现象是
"单跑能过、连跑挂"：上一个用例把节点降级了，下一个用例起点就不是 NORMAL。
本套件用 `Test Setup    Reset Safety Node` 保证每个用例从同一初始状态开始：

```
NORMAL / fault_level=0 / 计数器 last_rx=14（期望下一帧 0）/ 心跳恢复 / 错误计数清零
```

### 32.9.6 与真实项目的差异（主动说清边界）

| 项目 | 本仿真（教学版） | 真实项目 |
|---|---|---|
| 传输层 | UDP JSON + 8 字节帧 | CAN / CAN FD 帧（E2E 帧就是数据场） |
| E2E 库 | 自实现教学版 Profile 1 | AUTOSAR E2E Library（配置 DataID/MaxDeltaCounter 等） |
| DataID | 放在帧里并参与 CRC | Profile 1 中 DataID 通常**不传输**、仅参与 CRC 计算 |
| 计数器推进 | 格式合法帧都推进（便于故障注入后恢复） | 标准实现行为更严格（CRC 失败不更新序列状态） |
| 看门狗 | 心跳线程 + 软件巡检 | 硬件看门狗/窗口看门狗 + MCU 复位 |
| 故障标志 | JSON `fault_flags` | DTC（0x19 读）+ Dem/FiM 模块 |

> 面试时说清"教学简化点"比假装完整更可信——**方法、状态机、判据可以平移到真实 ECU**。

## 32.11 tests/robot/15 套件：10 条用例逐条讲

| # | 用例 | 需求 | 核心断言 |
|---|---|---|---|
| ① | 正常 E2E 帧应被接收且状态为 NORMAL | 001/002 | accepted + NORMAL + 输出 15° |
| ② | E2E 计数器应按 0~14 循环递增 | 002 | 序列 `0..14,0` |
| ③ | CRC 错误帧应被拒绝并计入 CRC 错误计数 | 001/005 | 拒绝 + crc_errors=1 + 不降级 |
| ④ | 连续 3 条 E2E 错误应进入 DEGRADED 并输出安全值 | 003/004/005 | DEGRADED + 安全值 + 标志 |
| ⑤ | 计数器跳变超阈值应立即判定丢帧并降级 | 002/003/005 | lost=4 + 立即 DEGRADED |
| ⑥ | 故障消失后应自动恢复 NORMAL，Clear Fault 可手动恢复 | 004 | 两条恢复路径 |
| ⑦ | 心跳停止超过 300ms 应进入 SAFE_STATE 并上报 WATCHDOG 故障 | 003/004 | SAFE_STATE + fault_level=2 |
| ⑧ | 心跳恢复后应自动退出 SAFE_STATE 回到 NORMAL | 003/004 | 自动恢复 + 输出有效 |
| ⑨ | 重复帧/重放帧应被拒绝（E2E 计数器语义） | 002/005 | replay 拒绝 + 序列不破坏 |
| ⑩ | 安全输出帧应通过测试端独立 CRC 重算（含坏帧 mutation 验证） | 001/005 | check value + 交叉验证 + mutation |

### 32.11.1 用例 1：正常 E2E 帧接收（基线）

```robotframework
${resp}=    Send Safety Frame    steering_angle_deg=15.0
Should Be True    ${resp}[accepted]
Should Be Equal    ${resp}[reason]    ok
Safety Status Should Be    NORMAL
${status}=    Read Safety Status
Should Be Equal As Numbers    ${status}[output][steering_angle_deg]    15.0
Fault Flag Should Be    E2E_CRC_ERROR    False
```

**测什么**：正路径基线——测端独立算的 CRC 被节点接受、节点进入 NORMAL、把转向角透传为输出。
后面所有负向用例都建立在这条基线上（如果正常帧都收不了，负向用例的失败没有意义）。

### 32.11.2 用例 2：计数器递增与回绕

```robotframework
${seq}=    E2E Counter Should Advance    16
Should Be Equal As Integers    ${seq}[0]    0
Should Be Equal As Integers    ${seq}[14]    14
Should Be Equal As Integers    ${seq}[15]    0     # 14 → 0 回绕
```

**测什么**：连发 16 帧，测试端发送计数器和节点接收计数器**逐帧一致**，且出现 `14→0` 回绕。
**为什么逐帧验证**：只发一帧对不能证明计数器逻辑正确（可能永远是 0）；必须是"序列 + 回绕"。

### 32.11.3 用例 3：CRC 错误被拒（单次不降级）

```robotframework
${resp}=    Inject E2E Error    crc
Should Not Be True    ${resp}[accepted]
Should Be Equal    ${resp}[reason]    crc_error
E2E Error Counter Should Be    crc    1
Safety Status Should Be    NORMAL        # 单次错误不降级
```

**测什么**：CRC 字节取反的帧必须被拒绝并计数；但**单次错误不降级**——安全机制要区分
偶发传输错误（可容忍）与持续故障（必须降级），否则可用性太差。

### 32.11.4 用例 4：连续 3 条错误 → DEGRADED + 安全值

```robotframework
FOR    ${i}    IN RANGE    3
    Inject E2E Error    crc
END
Safety Status Should Be    DEGRADED
Safety Output Should Be Safe Value        # 转向角=0，mode=SAFE_VALUE
Fault Flag Should Be    E2E_CRC_ERROR    True
```

**测什么**：错误阈值（3 次）生效，进入 DEGRADED、fault_level=1、输出安全值、故障标志置位。
**能抓什么缺陷**：没有降级逻辑、阈值写错、降级后仍输出旧值（执行器按坏数据动作）。

### 32.11.5 用例 5：计数器跳变超阈值

```robotframework
Send Safety Frame    steering_angle_deg=0.0       # 建立序列基线
${resp}=    Inject E2E Error    counter    jump=5  # delta=5 → 丢 4 帧
Should Be Equal    ${resp}[reason]    counter_jump
Should Be Equal As Integers    ${resp}[lost_frames]    4
Safety Status Should Be    DEGRADED               # 立即降级（不等 3 次）
```

**测什么**：跳变 delta=5 > 阈值 3 → 判定 counter_jump、丢 4 帧、**立即**降级。
与用例 4 的区别：CRC 错误要连续 3 次才降级，而"计数器跳变超阈值"一次就降级——
严重故障的判定条件本来就该更激进。

### 32.11.6 用例 6：两条恢复路径

```robotframework
# 路径 A：降级后连续 3 条合法帧 → 自动恢复
Safety Status Should Be    DEGRADED
FOR    ${i}    IN RANGE    3
    Send Safety Frame    steering_angle_deg=5.0
END
Safety Status Should Be    NORMAL
Fault Flag Should Be    E2E_CRC_ERROR    False

# 路径 B：再次降级 → Clear Fault 手动恢复（诊断仪 0x14 语义）
Clear Fault
Safety Status Should Be    NORMAL
```

**测什么**：故障消失后**必须能恢复**（自动 + 手动两条路径）。只测"能降级"不测"能恢复"
是功能安全测试最常见的缺口——卡在安全状态的车同样不可用。恢复后输出也要恢复为最新合法值。

### 32.11.7 用例 7：看门狗 → SAFE_STATE

```robotframework
Inject Heartbeat Stop
${reaction_ms}=    Watchdog Should Trigger Degradation    timeout=2
Safety Output Should Be Invalid
Fault Flag Should Be    WATCHDOG    True
Should Be Equal As Integers    ${status}[fault_level]    2
Should Be True    ${reaction_ms} >= ${WATCHDOG_TIMEOUT_MS} * 0.8
```

**测什么**：停止喂狗后 300ms 内进入 SAFE_STATE、fault_level=2、输出无效、WATCHDOG 标志置位；
节点自报反应时间必须 ≥ 阈值×0.8（太快说明判定条件写错）。**这是"任务卡死"的核心安全机制验证。**

### 32.11.8 用例 8：心跳恢复 → 自动恢复

```robotframework
Inject Heartbeat Stop
Watchdog Should Trigger Degradation
Resume Heartbeat
Safety Status Should Be    NORMAL    timeout=2
Fault Flag Should Be    WATCHDOG    False
```

**测什么**：任务恢复运行后，看门狗自动清除故障回到 NORMAL、输出重新有效。
**恢复也必须是自动的**——真实 ECU 卡死被复位后，系统要能自愈，不能要求人工干预。

### 32.11.9 用例 9：重放帧被拒

```robotframework
${first}=    Send Safety Frame    steering_angle_deg=10.0
${replay}=    Inject E2E Error    replay       # 原样重发上一帧
Should Not Be True    ${replay}[accepted]
Should Be Equal    ${replay}[reason]    replay
E2E Error Counter Should Be    replay    1
# 重放不应破坏序列：下一帧正常报文仍应被接受
${next}=    Send Safety Frame    steering_angle_deg=12.0
Should Be True    ${next}[accepted]
```

**测什么**：E2E counter 的"重复检测"语义——旧帧重放必须被拒绝，且不能破坏计数器序列。
**为什么功能安全也管重放**：重放旧数据可能让执行器按过期指令动作；信息安全与功能安全
在这一层是交叉的（[27 章](27_信息安全测试入门.md) 的 UDS 重放防护同理）。

### 32.11.10 用例 10：独立 CRC 重算 + mutation

```robotframework
Crc8 Should Be    313233343536373839    0x4B        # ① 测试端实现自证
Send Safety Frame    steering_angle_deg=15.0
Sleep    0.15s
${status}=    Read Safety Status
${decoded}=    E2E Crc Should Be Valid    ${status}[e2e][last_tx_frame]
...    expected_data_id=0x5A02                       # ② 节点输出帧独立重算
Should Be Equal As Numbers    ${decoded}[steering_angle_deg]    15.0

${bad}=    Inject E2E Error    crc
Run Keyword And Expect Error    *CRC 校验失败*
...    E2E Crc Should Be Valid    ${bad}[frame]       # ③ mutation：坏帧必须报错
```

**测什么**：REQ-SAFE-005 的完整落地——独立实现自证 → 双向交叉验证 → mutation 证明不恒真。
**能抓什么缺陷**：测试端 CRC 实现写错（check value 抓）、节点输出帧 CRC 错（交叉验证抓）、
校验函数恒返回 True（mutation 抓）。

## 32.12 真实项目怎么接

### 32.12.1 AUTOSAR E2E Library / SWC

真实项目里 E2E 不是"自己写个 CRC"，而是用 **AUTOSAR E2E Library**（或 OEM 封装），
在 SWC 的 RTE 端口上配置参数：

| 配置项 | 含义 | 本章对应 |
|---|---|---|
| `DataID` | 每类帧的唯一 ID（参与 CRC 计算） | byte0..1 的 dataId |
| `MaxDeltaCounter` | 允许的计数器最大跳变（丢帧容限） | delta 2~3 可容忍；>3 降级 |
| `WindowSize` | 接收窗口（Profile 2/4） | 本教学版无窗口，线性计数 |
| `Offset` | 计数器偏移（多路复用） | 未实现 |
| `E2E_StateMachine` | E2E 状态机：OK/REPEATED/WrongSequence/... | 本项目的 NORMAL/DEGRADED/SAFE_STATE（简化） |

**测试要点**：拿 ICD/DBC 里的 E2E 配置，逐参数构造合法/非法帧；用 E2E Library 的
状态机接口读接收状态，并在**功能层**验证降级动作（不能只看 E2E 状态）。

### 32.12.2 真实 CAN 上的 E2E 与工具链

- E2E 帧就是普通 CAN 帧：8 字节数据场里放 `dataId+counter+data+CRC`（Profile 1 变体）；
  或者 Profile 4/5 用更长帧；
- **CANoe/CANalyzer**：配置 E2E 解析插件（AUTOSAR E2E）直接看每帧 CRC/计数器是否 OK；
  失败帧在 Trace 里红色高亮；
- **CAPL 脚本注入**：构造 CRC 错帧/跳变帧写到总线（注意：很多 CAN 卡默认会重算 CRC，
  需要底层发送 API 或"错误帧注入"能力）；
- **HIL 台架**：继电器断线模拟丢帧、电源扰动模拟欠压、CANoe 模拟多节点。

### 32.12.3 HIL 台架上的故障注入手段

| 手段 | 模拟的故障 | 对应本章 |
|---|---|---|
| CANoe/CAPL 发坏帧 | 位错误/CRC 错/重放 | `Inject E2E Error` |
| 继电器断开总线 | 丢帧/断线 | 轻微丢帧（delta 2~3） |
| 电源程控降压 | ECU 复位/降级 | 未覆盖（见 [scenarios/11](19_十六个场景脚本实战.md)） |
| 调试器冻结任务 | 任务卡死、不喂狗 | `Inject Heartbeat Stop` |
| 关闭任务调度 | 心跳停止 | `Inject Heartbeat Stop` |
| 修改发送周期 | 计数器/周期异常 | 未覆盖（可扩展） |

### 32.12.4 看门狗测试与 FTTI / 证据链

真实项目测看门狗要留三类证据：
1. **触发证据**：注入卡死后，看门狗计数/复位原因寄存器/日志；
2. **时间证据**：从故障注入到进入安全状态的**实测时间** ≤ FTTI 预算（本章的 reaction_ms）；
3. **恢复证据**：复位/恢复后功能可用、故障不残留（本章用例 8）。

> 面试话术："看门狗测试我会记录三个时间点：注入时刻、看门狗触发时刻、系统进入安全状态时刻，
> 并对照 FTTI 预算判断是否达标；同时验证恢复路径，避免卡在安全状态。"

### 32.12.5 CI 与回归

- 本章套件约 5 秒，**可以进每次提交的 PR 门禁**（E2E/看门狗是回归高发区）；
- 把 E2E 错误计数、看门狗触发次数、降级次数**入库做趋势**——错误计数突然上涨说明
  通信质量/时序变了；
- 长稳：真实项目把 E2E 监控挂在 8h+ soak 上（配合 [26 章非功能](26_非功能测试实战.md) 的 soak）。

### 32.12.6 本模块测不到什么（主动说清边界）

| 验证项 | 本模块 | 说明 |
|---|---|---|
| 真实 CAN 上的 E2E 工具链 | ❌ | 需要 CANoe + E2E 插件 + 真实 CAN 卡 |
| 硬件看门狗/复位原因 | ❌ | 软件仿真无 MCU/复位电路 |
| FTTI 级硬实时测量 | ⚠️ 近似 | UDP + Python 调度，精度 ms 级；真实台架用硬件时间戳 |
| 电源/EMC 类故障 | ❌ | 需要 HIL 电源程控与 EMC 暗室 |
| 多 ECU 级 E2E 端到端 | ⚠️ 单节点 | 本章是"一个发送端 + 一个安全节点" |
| 信息安全攻击面 | ❌ | 重放只是安全的一小部分，见 [27 章](27_信息安全测试入门.md) |

## 32.13 本章自检

1. 功能测试全绿为什么还不能证明"功能安全"？安全机制测试要回答哪三个问题？
2. E2E 保护里的 dataId/counter/CRC 各防什么故障？为什么"只加 CRC"不够？
3. E2E 计数器为什么在本项目取 0~14（而不是 0~15）？`delta=(0-14) mod 15` 等于多少、代表什么？真实项目应以什么为准？
4. 接收端看到 delta=0、delta=2、delta=5 时分别应该怎么处理？为什么"轻微丢帧"可以容忍而"跳变超阈值"必须立即降级？
5. CRC-8/SAE-J1850 的参数是什么（poly/init/xorout）？`crc8("123456789")` 的公开校验值是多少？这个校验值有什么用？
6. 手算 `5A 01 00 00 96 00 00` 的 CRC（写出前两步），最终 CRC 是多少？
7. 看门狗的原理是什么？简单看门狗和窗口看门狗的区别？300ms 阈值应该由什么决定？
8. 测试看门狗时，为什么"停止心跳"可以模拟任务卡死？为什么不能用被测节点自己上报的状态来证明看门狗有效？
9. DEGRADED 和 SAFE_STATE 的区别是什么？分别输出什么？为什么"降级≠安全"？
10. 为什么降级要"连续 3 次"错误、恢复也要"连续 3 条"合法帧？只用 1 次会有什么问题？
11. （独立性）假设测试端直接 `from simulators.safety_ecu import crc8_sae_j1850` 来做校验，会有什么风险？本章用了哪四条措施保证独立？

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | 功能测试证明"按设计输入时行为正确"；安全机制测试证明"异常时仍安全"。三个问题：**能检测吗（detection）/ 能反应吗（reaction）/ 能恢复吗（recovery）** |
| 2 | dataId=防串帧/错误源（区分帧类型）；counter=防丢帧/重复/重放；CRC=防位错/篡改。只加 CRC 防不了**重放完全合法的旧帧**和**丢帧**——所以需要 counter |
| 3 | 本项目需求约定 4bit 计数器只用 0~14（15 保留为非法/复位值）。`delta=(0-14)mod15 = 1` → **正常递增**（回绕不算丢帧）。真实项目以 **ICD/E2E 配置**为准，不照搬教科书默认值 |
| 4 | delta=0 → 重复/重放，拒绝并计数；delta=2 → 丢 1 帧，接受数据 + 记录丢失（可容忍）；delta=5 → 超阈值，**立即降级**（严重通信故障，等 3 次太慢） |
| 5 | poly=**0x1D**、init=**0xFF**、xorout=**0xFF**、不反射；check value=**0x4B**。用途：验证测试端/被测端实现有没有写错——尤其是"独立实现"的正确性 |
| 6 | 初值 0xFF → XOR 0x5A=0xA5 → 移 8 位=0xC8 → XOR 0x01=0xC9 → 移 8 位=0xC0 → ……最后 0x61 ^ 0xFF = **0x9E** |
| 7 | 被监控任务周期喂狗，超时未喂 → 判定卡死 → 复位/降级。简单看门狗只看"太晚"；窗口看门狗"太晚/太早"都触发。阈值来自**安全时间预算（FTTI）**，由安全分析决定 |
| 8 | 停止喂狗等价于任务卡死（不再有"我还活着"的信号）。用被测自报状态是**循环论证/自证**——被测实现有 bug 时它也会说"我正常"；必须外部注入 + 外部观测 |
| 9 | DEGRADED：还能工作但只输出**预定义安全值**（转向角=0，valid=true）；SAFE_STATE：**输出无效**（valid=false，不给执行器任何指令）。降级≠安全：降级仍有输出，安全状态交权/停机 |
| 10 | 防抖：偶发 1 次错误是正常的，一次就降级可用性差、还会抖；持续 3 次说明真故障。恢复也要连续 3 条，防止"错-对-错"反复切换状态 |
| 11 | 风险：被测 CRC 有 bug 时测试也用同一份错误实现 → **自证全绿**。四条措施：①独立实现 CRC（不 import）②公开 check value 自证 ③双向交叉验证 ④坏帧 mutation 必须报错 |
| 12 | 注入：CAPL/CANoe 发坏帧（CRC/跳变/重放）、继电器断线（丢帧）、调试器冻结任务（不喂狗）、电源扰动（复位）。观测：E2E 状态机/Trace/复位原因寄存器/安全状态输出。证据：注入时刻、触发时刻、进入安全状态时刻 + FTTI 对照 + 恢复记录 |
