# 04 · DTC 详解：故障码的一生

> DTC（Diagnostic Trouble Code，诊断故障码）是仪表盘"检查发动机"灯背后的主角，
> 也是诊断测试的核心对象。本章讲清楚：一个故障码长什么样、有哪些状态位、
> 从产生到消失的完整生命周期、以及测试怎么验证它。
>
> 代码对应：`simulators/dtc_manager.py`（纯逻辑，无依赖，建议边读边跑 `python dtc_manager.py`）。

## 4.1 DTC 的结构：5 个字符的编码学

一个标准 DTC 长这样：**P0116**。5 个字符，翻译成 3 字节存储在 ECU 里：

### 4.1.1 首字母：故障域

| 字母 | 域 | 典型故障 |
|---|---|---|
| **P** | Powertrain 动力域 | 发动机、变速箱、排放（最常见） |
| **B** | Body 车身 | 空调、座椅、灯光、门锁 |
| **C** | Chassis 底盘 | 制动、转向、悬架 |
| **U** | Network 网络 | CAN 通信丢失、总线关闭 |

### 4.1.2 数字：4 位编码

```
P 0 1 1 6
│ │ │ └─┴─ 第3、4位：具体故障（十六进制 00~FF）
│ └─┴──── 第1、2位：子系统（十六进制 00~FF）
└──────── 域
```

- 第 2 位是 **0 还是 1 有行业惯例**：`0` = SAE 统一定义的标准码（所有车企含义相同）；`1` = 厂商自定义码。
- 例：`P0116` = 动力域 / 01=燃油和进气测量 / 16=冷却液温度传感器范围/性能故障（全球统一）。
- 例：`P1A3F` 里的 `1` = 这是 OEM 自定义码，含义要查该车型的手册。

### 4.1.3 3 字节 BCD 编码（手算）

存储格式（SAE J2012）：**首字母 2 bit + 4 个数字各占 4 bit（BCD）**，第 3 字节保留：

```
P0116:
  P = 00 (bit7-6 of byte1)
  0 = 0000 (bit5-4 of byte1)
  1 = 0001 (bit3-0 of byte1)
  1 = 0001 (bit7-4 of byte2)
  6 = 0110 (bit3-0 of byte2)
  → byte1 = 0x01, byte2 = 0x16, byte3 = 0x00  →  01 16 00
```

验证（本项目自测里有）：

```python
from uds_lib import string_to_dtc, dtc_to_string
string_to_dtc("P0116")          # (0x01, 0x16, 0x00)
dtc_to_string(0x01, 0x16, 0x00) # 'P0116'
```

**这就是 `19 02` 响应里 DTC 的存储形态**：每个 DTC = 3 字节编码 + 1 字节状态。

> 开发踩坑记录：本项目第一版把后 4 位按"2 位一字节"编码（0x01 0x01 0x06），自测立刻抓到。BCD 是"一位数字 4 bit"，不是两位拼一字节——这个错误在真实解析工具里会导致 DTC 全部错位。

## 4.2 状态位：1 字节里的 8 个开关

每个 DTC 带 1 字节状态（status byte），8 个 bit 各有职责：

| bit | 掩码 | 名称 | 含义 |
|---|---|---|---|
| 0 | 0x01 | testFailed | 当前检测失败（最新一次自检没过） |
| 1 | 0x02 | testFailedThisOperationCycle | **本操作周期内**失败过 |
| 2 | 0x04 | pendingDTC | **疑似故障**（出现了，还没确认） |
| 3 | 0x08 | confirmedDTC | **已确认故障**（警告灯点亮的依据） |
| 4 | 0x10 | testNotCompletedSinceLastClear | 上次清除以来检测没跑完 |
| 5 | 0x20 | testFailedSinceLastClear | 上次清除以来失败过 |
| 6 | 0x40 | testNotCompletedThisOperationCycle | 本周期检测未完成 |
| 7 | 0x80 | warningIndicatorRequested | **请求点亮警告灯** |

**什么叫"操作周期（operation cycle）"？** 对整车 ECU 通常是"一次上电到熄火"；对本项目的仿真，`advance_cycle()` 调用一次 = 一个周期（500ms）。这是诊断状态机的时钟。

## 4.3 生命周期：一个故障码的一生

以本项目 `P0116`（水温 > 120℃）为例，完整走一遍：

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 循环1: 水温飙到 125℃                                          │
 │   testFailed=1, testFailedThisCycle=1,                       │
 │   pendingDTC=1, testFailedSinceLastClear=1                   │
 │   status = 0x27   （怀疑，先记着，不点灯）                      │
 └──────────────────────────────────────────────────────────────┘
                          │ 故障持续
                          ▼
 ┌──────────────────────────────────────────────────────────────┐
 │ 循环2: 水温仍 125℃（pending 满 2 个循环 → 确认）              │
 │   + confirmedDTC=1, + warningIndicatorRequested=1             │
 │   status = 0xAF   （确认！水温灯亮）                           │
 └──────────────────────────────────────────────────────────────┘
                          │ 故障消失（水温回 90℃）
                          ▼
 ┌──────────────────────────────────────────────────────────────┐
 │ 循环3+: testFailed=0                                          │
 │   非保持型灯（水温灯）→ 立即熄灭（warningIndicator 清）        │
 │   confirmed 还在 → aging 计数 +1                               │
 └──────────────────────────────────────────────────────────────┘
                          │ 40 个无故障循环
                          ▼
 ┌──────────────────────────────────────────────────────────────┐
 │ aging 完成（healing）                                          │
 │   confirmedDTC 自动清除 → 故障码"自愈"                         │
 └──────────────────────────────────────────────────────────────┘
                          │
        任意时刻 0x14 清除 ─┴─► 全部状态归零（人工干预，不等 aging）
```

### 4.3.1 pending → confirmed：为什么要"连续 2 个循环"

**防误报**。瞬时干扰（电压波动、插接件瞬断）会造成单周期检测失败。要求"连续 N 个周期失败才确认"（N 通常 1~3，各家标定不同）能过滤掉绝大多数误报。本项目 `confirm_threshold=2`。

### 4.3.2 aging：40 个循环的自愈

故障消失后，confirmed 的 DTC 不会立刻清除——**要连续 40 个无故障周期**才自动清除（healing/aging）。为什么？防止"故障闪一下消失"把维修线索抹掉；也让"清了码看还亮不亮"的维修习惯有观察窗口。

### 4.3.3 灯的 latch（保持）策略

哪些灯"故障消失就灭"、哪些"保持亮"？本项目建模：

| 灯 | 策略 | 理由 |
|---|---|---|
| 水温/电压/机油灯 | **非保持**：故障消失即灭 | 属于"即时状态显示" |
| **MIL（发动机故障灯）** | **保持**：故障消失仍亮，直到 0x14 清除或 aging 完成 | 法规要求（OBD-II）：排放故障必须亮到维修清除，防止"抖一抖就好" |

这个区分在 03 套件测试里能观察到：`P0135`（MIL）注入后即使撤销，灯依然亮，必须 `14 FF FF FF`。

## 4.4 快照（Snapshot / 冻结帧）：故障现场的照片

DTC 被确认时，ECU 会拍一张"现场照片"存起来——**freeze frame**：

```
故障时刻的：车速、转速、水温、电压、里程、时间戳……
```

维修价值：师傅读 DTC 时会看"这码是什么工况下触发的"，比码本身更有信息量。用 `19 03`（ReadDTCSnapshotRecord）读取。

本项目的实现（`dtc_manager.py` 的 `inject_fault` 记录 + `ecu_sim.py` 的 0x19 0x03 分支）：快照 DID 0x9001 存故障时车速。03 套件有对应用例。

## 4.5 DTC 与仪表盘的联动：完整闭环

把 03/04 章串起来，这就是系统验证的日常主线：

```
① 注入故障        水温 125℃（真实车：传感器坏了/冷却液不足）
        │
② ECU 诊断监控    每 500ms 跑一轮检测 → testFailed
        │
③ 状态机推进      pending → confirmed（2 循环）→ warningIndicator
        │
④ 总线通知        ECU 发 0x300，CoolantTempHigh bit=1
        │
⑤ 仪表点灯        仪表盘收到 → 水温灯亮（GUI 可见 / headless 可断言）
        │
⑥ 诊断仪确认      19 02 08 → 返回 [P0116, 0xAF]
        │
⑦ 维修动作        14 FF FF FF 清除
        │
⑧ 灯灭            warningIndicator 清（非保持型）→ 灯灭
```

**测试要验证的，就是这条链上每一环**。03 套件（`tests/robot/03_dtc_workflow.robot`）把这个闭环做成了 7 个自动化用例。

## 4.6 常见 DTC 分析思路（故障排查 checklist）

工作中拿到一个 DTC，按这个顺序问自己：

1. **什么域？** P/B/C/U 决定找哪个系统的同事。
2. **confirmed 还是 pending？** pending 多为偶发/误报；confirmed 是实打实。
3. **testFailed 当前是 1 还是 0？** 1 = 故障还在；0 = 历史故障（已消失，等 aging）。
4. **快照什么工况？** 高速? 冷车? 低电压? —— 直接缩小怀疑范围。
5. **伴随 DTC？** 网络故障（U 码）常伴随多个 P/B/C 码——上游通信断了，下游全报警。
6. **能复现吗？** 用 0x31 例程/强制 IO 控制触发，验证故障是否可复现。

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | 编码规则见 **4.1.3**（要点：**每个十进制数字单独占 1 个"半字节"**，即一个字节存 2 位数字 → 所以 P0116 的字符能塞进 2 字节，第 3 字节留给状态）。**动手算一遍比背结论有用** |
| 2 | 灯亮不亮看 **`warningIndicatorRequested`（0x80）** 和 **`confirmedDTC`（0x08）**；"当前还在不在"看 **`testFailed`（0x01，本轮检测到）** 和 **`testFailedThisOperationCycle`（0x80 之外的周期位）** —— 完整 8 位表见 4.2 |
| 3 | pending = 本轮检测到但**还没确认**；confirmed = **连续 N 个循环都异常**，正式记录。连续 2 个循环是**防误报**（传感器偶尔跳一下不点灯） |
| 4 | aging 到 40 会**自动清除**该 DTC。需要这机制是因为：故障已消失（比如修好了），不能永远占着故障记录 → 自愈 |
| 5 | MIL 是**保持型**（故障消失也不灭，要清码/跑够循环）；水温灯通常是**非保持型**（故障消失就灭）。法规动机：**排放相关故障必须留痕**（防止车主"灭灯就当年检过"） |
| 6 | 快照 = DTC 记录时**把当时的关键数据存下来**（车速/水温/转速…），像"故障现场的照片"。对维修的用处：技师看快照就知道"故障发生那一刻车在什么状态" |
| 7 | 完整状态转换图见 **4.3**（含 pending→confirmed→aging→清除，以及每条 `0x14` 清除路径） |
