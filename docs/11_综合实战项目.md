## 11.2 任务 A：灯光测试例程全链路（推荐第一个做）

**目标**：用 RF 用例验证 0x31 例程的完整效果——产线终检的标准动作。

**需求描述**：
1. 进入扩展会话；
2. 启动灯光测试例程（`31 01 0301`）→ 正响应；
3. 2 秒内仪表 12 个警告灯**全部点亮**；
4. 例程结束（2 秒）后**全部熄灭**；
5. 中途用诊断仪读一次 DTC 数量（确认例程不污染 DTC）。

**用到的关键字**（都已存在）：

```robotframework
*** Test Cases ***
灯光测试例程应点亮全部警告灯并自动恢复
    Enter Extended Session
    Start Light Test Routine
    All Telltales Should Be Lit    timeout=5
    All Telltales Should Be Off    timeout=8
    ${count}=    Read DTC Count
    Should Be Equal As Integers    ${count}    0
```

**预期结果**：直接能跑通（库和 ECU 都实现了）。**但你的任务是搞懂每一行为什么这么写**，然后向自己解释：
- 为什么 `All Telltales Should Be Lit` 的 timeout 只要 5s，而 `Off` 要 8s？
- 例程期间读 DTC 数量，ECU 的例程状态机在干什么？
- 如果 ECU 的例程执行到一半被复位，灯的最终状态应该是什么？（思考题）

## 11.3 任务 B：里程精度测试（信号数学验证）

**目标**：验证里程累积的数学正确性——比"单调不减"更严格的精度测试。

**需求**：
1. 车速稳定 60 km/h（`Start Vehicle Environment speed=60` + 等待稳定）；
2. 记录里程 O1，精确等待 5 秒，记录 O2；
3. 理论增量 = 60 × 5/3600 = **0.0833 km**；
4. 断言 `|(O2-O1) - 0.0833| < 0.01`。

**坑点预警**：
- Odometer 信号是 **24 位整数、单位 km、无小数**——5 秒只累积 0.083 km，四舍五入后可能是 0！**整数分辨率不够，要拉长时间窗**（如 60 秒）或改用"两次读数的差 ≥ 1 km"。
- 真实 ECU 的里程可能有滤波/死区——这就是为什么要和信号矩阵文档核对累积系数。

**这个任务教你**：**测试设计前先算清楚被测量的量纲和分辨率**。分辨率不够时，"单调性测试"是务实选择，"精度测试"是理想选择——能说清这个权衡，就是资深测试的思维。

## 11.4 任务 C：故障-诊断-恢复全场景剧本（重头戏）

**目标**：模拟一次完整的"客户投诉→台架复现→定位→修复验证"流程。

**剧本**：

```
场景：客户投诉"水温灯偶尔亮，去4S店清了码，过几天又亮"
台架复现与定位：
  ① 注入故障：coolant=125
  ② 等待灯亮（Telltale Should Be Lit）
  ③ 读 DTC + 状态位（确认 confirmed，记录快照）
  ④ 模拟4S店维修：清除 DTC
  ⑤ 验证灯灭、数量归零
  ⑥ 保持故障环境，验证 DTC 重建、灯复亮（定位结论：真故障，非误报）
  ⑦ 模拟修复：coolant=90
  ⑧ 验证灯灭，且 aging 计数开始（可选：读 40 个循环后自愈——太久，写清楚预期即可）
```

**交付物**：一个 `.robot` 文件（自己命名，放 tests/robot/ 下），一条命令跑完。要求：
- 每个步骤带 `[Documentation]` 写"验证意图"；
- 用 `Wait Until ... timeout=` 而非 `Sleep` 硬等；
- 结尾清理（清除 DTC），不影响其他套件。

**这个任务就是面试项目介绍的脚本**：能跑、能讲、有真实工程逻辑。

## 11.5 任务 D：接真硬件（终极挑战）

**目标**：让系统跳出"纯软件仿真"。

**选项 1（CAN 硬件）**：买 CANable/CANalyst（约 100-300 元）
- 把 `bus.py` 增加一个 `interface="serial"` 选项（CANable 用 slcan 协议：`can.Bus(interface="serial", channel="COM3", bitrate=500000)`）；
- 用示波器/另一路 CAN 抓包验证你发的帧真的上了物理总线；
- **成就**：你的 ECU 模拟器 = 一个真实的 CAN 节点。

**选项 2（真安卓设备）**：旧安卓手机即可
- 装 platform-tools，`AdbLibrary.py` 的 `ADB_PREFIX` 改 `["adb"]`；
- 用 `Get Prop`、`Install APK`、`Current Focus Should Contain` 在真机上跑通 04 套件思路的用例；
- **成就**：你的测试框架同时覆盖"CAN 世界"和"安卓世界"。

**选项 3（树莓派 + AAOS）**：谷歌官方支持树莓派 4B 跑 Android Automotive
- 刷镜像 → adb connect → 跑真实车机系统；
- 成本最高但含金量最高：**"我在树莓派上跑通过 Android Automotive 并用 RF 测试"** 是简历上罕见的一条。

## 11.6 面试项目介绍模板（3 分钟版）

> 按"背景→架构→难点→成果"讲，数字要具体：

"这是一个车载自动化测试学习项目，背景是我要入职伟世通做系统验证，但手上没有 CAN 硬件和台架，所以我用纯软件仿真搭了一整套环境。

**系统三部分**：车辆侧模拟了动力域 ECU——python-can 的 UDP 组播做虚拟总线，多个进程像真实 ECU 一样挂在总线上；ECU 按 DBC 周期发车速/转速/水温/档位信号，实现了 14 个 UDS 诊断服务（含刷写 0x34/0x36/0x37）和 DTC 状态机（pending/confirmed/aging 全生命周期）。座舱侧做了两块屏：**7 界面的仪表盘**（主页表盘/行程电脑/媒体/导航/电话/设置/车辆信息）和 **6 界面的安卓车机**（桌面/媒体/导航/电话/空调/设置），两块屏通过新增的 CAN 0x400/0x500 报文联动——车机上点歌、开导航、调空调，仪表立即同步显示。测试侧基于 Robot Framework 写了 4 个关键字库和 116 个用例。

**技术上比较有讲究的点**：一是 UDS 的 ISO-TP 多帧传输，我实现了 FF/CF/FC 的拆帧重组和序号校验，读 VIN 这种 20 字节响应就是走多帧；二是 DTC 状态机，按 ISO 14229 的 8 个状态位实现了全生命周期，还建模了 MIL 灯的保持策略；三是**座舱多屏一致性**——两块屏共用"状态文件 + CAN 广播"同一数据源，我用 `Broadcast Headunit State To Bus` 关键字做确定性驱动（不依赖子进程定时器的隐式活性），把这套链路做成了 6 个自动化用例；四是调试中定位并修复了 21 个真 bug，包括 cantools 枚举信号返回不可哈希对象导致 GUI 崩溃、Windows 下 os.replace 撞文件锁导致 JSON 解析失败、GUI"状态同步逻辑误伤主动操作"导致点击失效等——每个都写了根因分析。

**成果**：116 个用例全绿（62 主套件 + 54 场景），一条命令 `start_cockpit.py` 拉起完整座舱；项目里沉淀的测试方法论——信号测试的存在性/范围/联动/状态四模式、诊断测试的六维矩阵、HMI 自动化的状态外置、**座舱多屏一致性测试**——可以直接迁移到真实工作。"
