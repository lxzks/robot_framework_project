# 17 · 从需求到脚本：拿到一句话怎么变成用例

> 真实工作里，没人给你"请写一个验证车速的用例"这种明确指令。
> 你拿到的是**一句话需求**（来自测试规范/需求文档/口头交代），
> 要自己判断"这要测什么、怎么测、测到什么程度"。
>
> **这一章教这个转换过程 —— 这是从"会写脚本"到"能独立干活"的分水岭。**

---

## 17.1 三步转换法

```
① 拆测试点          ② 定数据与断言          ③ 写脚本
"这句话要验证       "用什么值测、          "套用模式库里的
 哪几件事？"        期望什么结果？"          哪个模式？"
```

### ① 拆测试点：把一句话拆成"可验证的断言"

**关键问句**：这句话里**每一个名词和动词**，都能验证吗？

需求："**水温超过 120℃ 时**，**仪表点亮水温报警灯**并**记录 DTC**"

| 名词/动词 | 可验证吗 | 怎么验证 |
|---|---|---|
| 水温超过 120℃ | ✅ | 造场景（`coolant=125`） |
| 仪表点亮水温报警灯 | ✅ | `Telltale Should Be Lit` |
| 记录 DTC | ✅ | `DTC List Should Contain    P0116` |

→ 3 个测试点。**如果某个词无法验证，就是需求模糊，要问。**

### ② 定数据与断言：正向 + 负向 + 边界

一条需求通常要测**三类**：

| 类型 | 例子 | 为什么 |
|---|---|---|
| **正向** | 125℃ → 灯亮 | 基本功能 |
| **负向** | 90℃（正常） → 灯**不**亮 | 防止"灯永远亮着"也算通过 |
| **边界** | 119℃/120℃/121℃ | 阈值是 120 还是 121？差一度行为就变 |

### ③ 写脚本：套用模式库

拆完测试点，剩下的就是**选模式**（[15 章](15_车载脚本模式库.md)）：

| 测试点 | 模式 |
|---|---|
| 造故障场景 | 模式 11（Setup 参数化） |
| 等灯亮 | 模式 2（轮询等待） |
| 诊断确认 | 模式 9（等 DTC） |
| 正向+负向 | 模式 5/6 |

## 17.2 五个实战示例

### 示例 1（简单）：验证车速显示

> **需求**：仪表应正确显示 ECU 发送的车速信号。

**拆测试点**：
1. CAN 上的车速信号 = 60（目标值）
2. 仪表显示的车速与 CAN 信号一致

**写脚本**：

```robotframework
仪表显示车速应与总线信号一致
    [Documentation]    跨系统一致性：同一个事实在 CAN 层和 HMI 层都要对
    ${bus_speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    50    70    timeout=20
    ${shown}=    Get Displayed Speed
    ${diff}=    Evaluate    abs(${bus_speed} - ${shown})
    Should Be True    ${diff} <= 2
    ...    msg=仪表显示 ${shown} 与总线 ${bus_speed} 相差 ${diff}（应 ≤2）
```

**灰色地带（要问的）**：
- "正确显示"的容差是多少？（本项目用 ≤2，真实项目由显示精度决定）
- 要不要验证**指针角度**而不只是数值？（GUI 视觉测试的范围）

---

### 示例 2（中等）：水温报警 + DTC 闭环

> **需求**：水温超过 120℃ 时，仪表点亮水温报警灯并记录 DTC。

**拆测试点**：
1. 正向：125℃ → 灯亮、DTC 记录（P0116，confirmed）
2. 负向：90℃ → 灯灭、无 DTC
3. 闭环：清除后故障仍在 → 应重新记录
4. 边界：119/120/121℃ 的行为（可选，成本高）

**写脚本**（正向+闭环摘录，完整见 L6 练习）：

```robotframework
*** Settings ***
Suite Setup      Start Vehicle Environment    coolant=125

水温超限应点亮水温报警灯并记录 DTC
    Telltale Should Be Lit    CoolantTempHigh    timeout=25
    Wait Until Keyword Succeeds    15x    1s    DTC List Should Contain    P0116

清除后故障仍在应重新记录
    Clear DTC
    Telltale Should Be Off    CoolantTempHigh    timeout=5
    Wait Until Keyword Succeeds    20x    1s    DTC List Should Contain    P0116
```

**灰色地带**：
- P0116 的状态位要求？（pending 就算，还是要 confirmed？）
- 灯是"保持型"还是"非保持型"（故障消失就灭）？

---

### 示例 3（权限矩阵）：读能读，写要授权

> **需求**：诊断仪应能读取零件号，且只有安全解锁后才能写入应用数据。

**拆测试点**（这是**矩阵**，两个维度）：

| 操作 | 默认会话 | 扩展会话未解锁 | 扩展会话已解锁 |
|---|---|---|---|
| 读零件号 | ✅ 应成功 | ✅ 应成功 | ✅ 应成功 |
| 写应用数据 | ❌ NRC 0x7F | ❌ NRC 0x33 | ✅ 应成功 |

**写脚本**（三个关键用例）：

```robotframework
默认会话下读取零件号应成功
    ${pn}=    Read DID As ASCII    F187
    Should Be Equal    ${pn}    HW-IC-2026-001

默认会话下写数据应被拒绝
    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x7F     # 会话不支持

未解锁时写数据应被拒绝
    Enter Extended Session
    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x33     # 权限不足

解锁后写数据应成功且可回读
    Enter Extended Session
    Security Unlock
    Write DID    F1A0    56332E302E30
    ${ver}=    Read DID As ASCII    F1A0
    Should Be Equal    ${ver}    V3.0.0
```

**灰色地带**：
- 默认会话读 DTC 允许吗？（很多 OEM 允许，要看规范）
- 写失败后 ECU 内部有没有副作用？（重试一次确认状态没坏）

### 示例 4（状态机时序）：S3 超时回退

> **需求**：非默认会话下若 5 秒内无诊断请求，ECU 应自动回退到默认会话。

**拆测试点**（时序类需求，**必须验"变化"而不是"状态"**）：

1. 进扩展会话 → 确认在扩展会话（写操作能成功）
2. 静默 6 秒（**不发任何请求**）
3. 再试写操作 → 应被拒（已被踢回默认会话，NRC 0x7F）
4. 保活对照：静默期间每 2 秒发 `3E 00` → 不应回退

**写脚本**：

```robotframework
静默超过 S3 时间后应回退默认会话
    [Documentation]    S3 = 5 秒。静默 6 秒后敏感操作应失败（会话已回退）
    Enter Extended Session
    Security Unlock
    Sleep    6s                                    # 故意静默（这里 Sleep 是需求本身）
    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x7F   # serviceNotSupportedInActiveSession

TesterPresent 保活可保持会话
    [Documentation]    对照用例：静默期间保活 → 会话应保持
    Enter Extended Session
    Security Unlock
    FOR    ${i}    IN RANGE    3
        Sleep    2s
        Send UDS Request    3E 00
        Response Should Be Positive
    END
    Write DID    F1A0    5A5A
    Response Should Be Positive
```

> 💡 注意这里是**唯一该用 `Sleep` 的场景** —— 因为"静默 6 秒"**就是需求本身**，
> 不是"猜时间"。写脚本时要能讲清这个区别。

**灰色地带**：
- S3 时间具体是 5 秒还是 ECU 声明的其他值？（本项目声明的 P2*=5000ms）
- 回退后安全访问也失效吗？（本项目：失效。要与需求确认）

### 示例 5（异常/降级）：信号丢失怎么办

> **需求**：车速信号丢失时，仪表应保持最后有效值（不跳回 0）。

**拆测试点**（**异常场景**类需求）：

1. 正常行驶（车速 60）→ 仪表显示 60
2. **制造信号丢失**（停 ECU / 暂停发送）
3. 仪表应**保持 60**（而不是跳 0）
4. 恢复发送 → 仪表恢复跟随

**写脚本**：

```robotframework
车速信号丢失时仪表应保持最后值
    [Documentation]    异常降级验证：信号丢失 ≠ 显示归零
    ...               真实场景：CAN 线瞬断时，跳 0 会让驾驶员误判
    ${speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    50    70    timeout=20
    Suspend ECU Periodic Messages              # 制造信号丢失（模式 20）
    Sleep    2s
    ${shown}=    Get Displayed Speed
    Should Be True    ${shown} >= 50
    ...    msg=信号丢失后仪表跳到 ${shown}（应保持 ≥50，不该归零）
    Resume ECU Periodic Messages               # 恢复
```

**灰色地带**：
- "保持"多久？真实规范常有"丢失超过 N 秒后显示 --"
- 要不要同时记录通信故障 DTC（U 类码）？
- 恢复时是"立即跟随"还是"渐变"？

## 17.3 信息不全时问什么（真实工作的关键能力）

上面每个示例都有"灰色地带"。**不要自己猜**，按这个清单问需求方：

| 维度 | 要问的问题 |
|---|---|
| **精度/容差** | "显示正确"允许多大误差？ |
| **状态判定** | DTC 是 pending 就算，还是要 confirmed？ |
| **时序** | 超时阈值是多少？从哪个时刻开始算？ |
| **权限** | 哪些会话/解锁状态下允许？ |
| **异常** | 信号丢失/超时/畸形数据时的期望行为？ |
| **边界** | 阈值点（120℃）本身算超限吗？ |
| **恢复** | 异常消失后多久恢复正常？ |

**话术示例**：

> "这个需求我拆出 5 个测试点。有一处想确认：水温 120℃ 本身算不算超限？
> 这会影响边界用例的期望值。另外 DTC 的状态要求是 pending 还是 confirmed？"

**为什么这很重要**：面试官问"你怎么保证测试覆盖到位"，答案不是"我写了 100 个用例"，
而是"我会把需求拆成可验证的断言，**模糊的地方主动澄清而不是猜**"。

## 17.4 测试点覆盖检查表

拿到任何需求，套这五问（**每次都用，形成肌肉记忆**）：

- [ ] **正向**：正常输入 → 期望输出？
- [ ] **负向**：应该被拒绝的输入 → 真的拒绝了？（NRC/不响应/不动作）
- [ ] **边界**：阈值上下（119/120/121）？最小/最大？
- [ ] **异常**：信号丢失、超时、畸形数据、总线故障？
- [ ] **恢复**：异常消失后系统能回到正常？

能答完这五问，用例就基本覆盖到位了。**能答但没条件测的，写进测试报告的"未覆盖项"**——
这比假装测过诚实得多。

## 17.5 本章自检

1. "三步转换法"是哪三步？
2. 需求"车速超 120 时应报警"——拆出至少 4 个测试点（含负向和边界）。
3. 为什么时序类需求要"验变化"而不是"验状态"？
4. 示例 4 里为什么 `Sleep` 是对的，而其他地方是错的？
5. 测试点覆盖五问是哪五个？
6. 拿你手上的任何一个需求（或 L6 练习的场景），写出"要问的 3 个问题"。
