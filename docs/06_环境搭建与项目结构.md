### 6.1.2 创建虚拟环境并安装依赖

**先解释一句"为什么要 venv"**：虚拟环境是给这个项目单独装依赖的"隔离盒子"，
不污染你系统的 Python。新手直接 `pip install` 到全局也能跑，但以后项目多了必然打架。

```bash
# ① 在项目根目录创建虚拟环境（.venv 是约定俗成的名字，放项目里最省心）
python -m venv .venv

# ② 激活它 —— 三种终端的命令不同，选你在用的那个：
source .venv/Scripts/activate          # Git Bash
.venv\Scripts\activate                 # Windows CMD
.venv\Scripts\Activate.ps1             # PowerShell

# 激活成功的标志：命令行前面出现 (.venv)

# ③ 安装依赖
pip install -r requirements.txt

# ④ 验证（关键一步）
python training/check_all.py           # 看到「12/12 个练习的参考答案通过」就说明环境好了
```

## 6.3 系统架构：三个进程 + 一条虚拟总线

```
┌─────────────────────────── 你的电脑（同一台机器）───────────────────────────┐
│                                                                             │
│   ┌──────────────┐   UDP组播   ┌──────────────┐   ┌──────────────────────┐  │
│   │  ecu_sim.py  │◄───────────►│ 虚拟 CAN 总线 │◄─►│   uds_client.py      │  │
│   │  (动力域ECU)  │  0x100/200  │ 233.255.0.1  │   │   (诊断仪, 手动用)    │  │
│   │              │  0x300      │  :30000      │   └──────────────────────┘  │
│   │  周期发报文   │  0x7E0/7E8  │              │                            │
│   │  UDS服务      │             │              │   ┌──────────────────────┐  │
│   │  DTC状态机    │             │              │◄─►│  dashboard.py        │  │
│   └──────────────┘             │              │   │  (仪表盘)             │  │
│                                │              │   │  GUI: 人看            │  │
│   ┌──────────────────────┐     │              │   │  headless: 写JSON     │  │
│   │ robot (RF 测试进程)   │◄────┴──────────────┼───│  simulators/dashboard │  │
│   │  VehicleBusLibrary   │◄────┐               │   │  _state.json         │  │
│   │  DiagnosticLibrary   │◄────┤ 同一进程内    │   └──────────────────────┘  │
│   │  DashboardLibrary    │◄────┘ 两个库实例    │                            │
│   │  AdbLibrary          │────subprocess────►┌──────────────────────┐      │
│   └──────────────────────┘                   │  adb_sim.py          │      │
│                                              │  (安卓车机mock)       │      │
│                                              └──────────────────────┘      │
└─────────────────────────────────────────────────────────────────────────────┘
```

**关键设计**：
- ECU/仪表/诊断仪是**独立进程**（像真实 ECU 各自独立），通过 UDP 组播模拟的"总线"通信；
- RF 测试进程内的库也加入同一个组播组——所以测试进程既是"诊断仪"又是"总线监控者"；
- **headless 仪表盘不画 UI，把显示状态写 JSON 文件**，DashboardLibrary 读文件做断言——这是 HMI 自动化的核心思想（把"看到的"变成"可断言的"）。

## 6.5 开发排坑记录（21 个真 bug）

> 这些坑全部在开发本项目时真实踩过。按"现象→根因→修复→教训"记录。**建议读完后把自己的理解讲一遍**——面试讲"我踩过 X 坑并这样解决"非常有说服力。

### 坑 1：DTC BCD 编码错误
- **现象**：`string_to_dtc("P0116")` 返回 `(0x01, 0x01, 0x06)`，`19 02` 读出的 DTC 变成 "P010106"。
- **根因**：以为"4 位数字 = 2 字节各 2 位"。实际编码是 **首字母 2 bit + 第 1 位数字 2 bit + 后 3 位数字各 4 bit = 16 bit**（BCD 的本意是"一个数字占一个半字节"，但第 1 位只可能取 0~3，所以只需 2 bit；把它也当成 4 bit 会得到 18 bit，超出 DTC 的 16 bit 字段）。
- **修复**：`b1 = (p<<6)|(d1<<4)|d2; b2 = (d3<<4)|d4`。
- **教训**：**协议细节必须写自测验证**，不能靠"看起来对"。

### 坑 2：cantools `strict=False` 不填充缺失信号
- **现象**：`encode_message("TelltaleStatus", {"CoolantTempHigh": 1})` 抛 `KeyError: 'MilWarning'`，ECU 崩溃。
- **根因**：cantools 要求报文内**所有信号显式提供**；`strict=False` 只跳过"值域校验"，**不会用 0 填充**。
- **修复**：先铺全 0 字典 `{s.name: 0 for s in msg.signals}` 再置 1。
- **教训**：第三方库的"宽松参数"往往只宽松一个维度，读文档要看全。

### 坑 3：NamedSignalValue 不可哈希
- **现象**：`GEAR_NAMES.get(decoded["GearPosition"])` 抛 `TypeError: unhashable type`；仪表盘进程直接死。
- **根因**：DBC 里 `VAL_` 枚举信号，cantools 解码返回 `NamedSignalValue` 对象（部分版本既不可哈希也不能 `int()`）。
- **修复**：所有 `decode_message` 加 `decode_choices=False`。
- **教训**：**库的返回类型永远要 print 出来看一眼**，别信类型注解。

### 坑 4：流控帧 FC 方向发反
- **现象**：多帧请求（如 9 字节的 2E）发出去，永远等不到 FC，3 秒超时。
- **根因**：ECU 收到多帧首帧 FF 后，把 FC 发到了**请求 ID 0x7E0**（发回给 Tester 的方向才对——应该发响应 ID 0x7E8）。方向搞反，Tester 在 0x7E8 上永远等不到。
- **修复**：`send_frame(ID_UDS_RESPONSE, build_flow_control(...))`。
- **教训**：**传输层协议先画"谁发给谁"的箭头再写代码**。UDS/TP 的 req/resp ID 方向是重灾区。

### 坑 5：两个线程竞争同一个 socket
- **现象**：客户端收包线程和"等 FC"的主线程同时 `recv` 同一个总线，FC 帧被收包线程吃掉丢弃，主线程死等。
- **根因**：一个 socket 只能有一个消费者，两个线程 recv = 报文随机分配。
- **修复**：重构为**单线程收包 + 收件箱队列**（`_rx_loop` 是唯一 recv 者，所有等待从队列取）。
- **教训**：并发模型先设计再写。"谁拥有资源"必须唯一。

### 坑 6：console 线程初始化竞态
- **现象**：ECU 的交互控制台（`status`/`quit` 命令）完全失灵，stdin 命令无人应答。
- **根因**：`console()` 循环条件是 `while self._running`，而 `_running` 初始 False，console 线程启动时主循环还没置 True → 线程直接退出。
- **修复**：循环改 `while True`，靠 quit/EOF 退出。
- **教训**：**线程启动时序依赖是经典竞态**。`Thread.start()` 不代表线程体立刻执行，更不代表共享状态已就绪。

### 坑 7：Windows stdin 句柄继承挂起
- **现象**：RF 跑 adb 用例，第二个命令起全部 `TimeoutExpired: 15 秒`。
- **根因**：RF 启动 ecu_sim 时 stdin 继承自测试进程；ecu_sim 的 console 线程持有该管道句柄。后续 `subprocess.run` 起的孙进程继承了同一 stdin 句柄，在 Windows 上导致挂起。
- **修复**：`Start Process ... stdin=DEVNULL` + `subprocess.run(..., stdin=subprocess.DEVNULL)`。
- **教训**：**自动化框架调外部命令，永远显式指定 stdin**。这是通用最佳实践，与车载无关。

### 坑 8：环境就绪竞态（假就绪）
- **现象**：偶发第一个诊断用例超时（3s 没响应）。
- **根因**：Suite Setup 用"状态文件存在/新鲜"判断仪表盘就绪，但**上一个套件残留的新鲜文件会骗过检查**——本套件的 ECU 其实还没 import 完 cantools。
- **修复**：加 `ECU Should Respond`（发 3E 00 等到正响应）作为**功能性就绪检查**。
- **教训**：**就绪检查要用业务行为验证，不能用间接信号**（进程在 ≠ 服务在）。

### 坑 9：teardown 进程残留
- **现象**：偶发"仪表盘状态过期"，且发现多个 dashboard 进程在写同一个 JSON。
- **根因**：`Terminate Process kill=True` 之后没有确认退出，下一个套件的进程已启动，两个进程交替写状态文件互相覆盖。
- **修复**：terminate 后 `Wait For Process timeout=5s` + `Sleep 0.5s`；teardown 每步包 `Run Keyword And Ignore Error` 防止一步失败断掉整链。
- **教训**：**进程生命周期管理要"确认死亡"，不能"发了终止信号就算完"**。

### 坑 10：`Wait Until Keyword Succeeds` 误用
- **现象**：`Wait Until ... Read Signal ...` 立即“成功”，随后的范围断言失败（读到 24 km/h）。
- **根因**：该关键字只检测异常，**返回值超范围不算失败**。
- **修复**：值域等待下沉为库关键字 `Wait Until Signal In Range`。
- **教训**：**框架原语有精确语义，用前读文档**。“重试直到成功”≠“重试直到值满足条件”。

### 坑 11：座舱测试的隐式时间依赖（05 套件）
- **现象**：05 套件偶发失败；日志显示 android 子进程运行十几秒后静默停止（offscreen Qt 在 RF 子进程树里的环境特异性，无任何异常输出）。
- **根因**：测试依赖"android_gui 子进程的周期定时器还活着"这种**隐式假设**。
- **修复**：① IVI 核心逻辑抽成无 Qt 的 `ivi_backend.py`；② RF 库加 `Broadcast Headunit State To Bus` 关键字，用例**显式驱动**"状态→CAN→仪表"链路；③ 值域断言全部改成轮询关键字（`Navi Distance Should Be Below` 等）。
- **教训**：**测试不要依赖长生命周期子进程的隐式活性，能显式驱动的就不要靠等**。这也是"确定性测试（deterministic testing）”的核心。

### 坑 12：Windows 文件锁竞态（JSONDecodeError / PermissionError）
- **现象**：仪表盘 headless 每 100ms 写 `dashboard_state.json`，RF 每 100ms 读。偶发 `JSONDecodeError: Expecting value: line 1 column 1` 或 `PermissionError: [Errno 13]`。
- **根因**：两个不同的竞态——
  ① `write_text` 先 truncate 再写，读取方撞见"空文件窗口"→ JSON 解析失败；
  ② **Windows 特有**：`os.replace` 需要目标文件的 DELETE 权限，而 Python `open()` 读默认**不共享 DELETE**，原子替换撞上读取方的打开句柄 → PermissionError。
- **修复**：三保险——① 写入方原子写（temp + `os.replace`）且 PermissionError 让步重试 8 次；② 写入方单轮失败不杀循环（warning 后下轮重试）；③ 读取方对 JSONDecodeError/PermissionError/OSError 都重试 5 次。
- **教训**：**多进程共享文件必须处理“写原子性”和“平台文件锁语义”两件事**。Linux 上 rename 语义友好，Windows 上必须显式设计——写跨平台测试框架时这是必修课。

### 坑 13：GUI 点击无反应（状态同步逻辑误伤主动操作）
- **现象**：用户反馈“安卓车机界面图标点了根本没有反应”——桌面图标、Home/Back 键全部失效，像卡死在桌面。
- **根因**：`launch_app` 的路径是 `set_focus()`（内部把 `_last_focus` 更新成新焦点）→ `_sync_focus()`。而 `_sync_focus` 开头有“焦点没变就 return”的判断——此时新旧焦点已相等，**直接 return，界面不切换**。“状态同步”逻辑（轮询发现外部变化才切页）被误用在了“主动操作”路径上。
- **修复**：`launch_app` 直接按 APPS 注册表 `setCurrentIndex` 切页，不绕 `_sync_focus`。
- **验证**：`simulators/test_android_gui_click.py`——offscreen 模式下 `button.click()` 会真实走信号连接逻辑，27 项点击断言全覆盖（桌面 5 图标/底部 3 键/媒体 6 按钮/导航/电话/空调/刷新可见性）；仪表 GUI（`cluster_gui.py`）目前由 `simulators/test_cluster_e2e.py` 做整链联调（9 条断言），tab/按钮点击测试尚未补齐（可作为扩展练习）。
- **教训**：**“同步”和“主动操作”是两条路径，不能复用同一套“变化检测”逻辑**。主动操作必须直接作用于目标；变化检测只服务于外部变更的观察。这个原则适用于所有事件驱动 UI（不止 Qt）。

### 坑 14：子进程日志写 stderr 导致线程阻塞
- **现象**：UDS 刷写套件（06）大面积超时——"周期报文还在发，但所有诊断请求石沉大海"，且 ECU 日志里什么都看不到。
- **根因**：ECU 的 `logging` 默认输出到 **stderr**，而 RF 的 `Start Process` 只重定向了 **stdout** → stderr 管道无人消费 → 缓冲写满（4KB）→ **ECU 的监听线程阻塞在写日志上** → 不处理任何诊断请求。
- **修复**：`logging.basicConfig(..., stream=sys.stdout)`（CI/测试环境通常只重定向 stdout，走 stderr 必丢日志）。
- **教训**：**子进程的日志输出必须走"有人消费"的管道**。另外：监听线程要包异常装甲（`_handle_request_safely`），否则一次异常就静默失能。

### 坑 15：ISO-TP 流控声明与实现不一致
- **现象**：66 字节的长请求（刷写数据块）发出去永远等不到响应，短请求（≤7 字节）正常。
- **根因**：ECU 的流控帧**声明 BS=8**（"每 8 个连续帧回一个 FC"），但接收端实现是"一次收完"——**发送端按声明发满 8 帧后等新 FC，ECU 永远不发** → 死等超时。同时发送端还把 BS 硬编码成 8，没解析 ECU 的真实声明。
- **修复**：ECU 声明 `BS=0`（不限量，与实现一致）；发送端改为**从 FC 帧解析 BS**，不再硬编码。
- **教训**：**声明的协议参数必须与实际实现能力一致**；解析方永远以"对方声明的"为准，不要硬编码。

### 坑 16：RF 结果树的三个遍历陷阱
- **现象**：覆盖率统计全 0；修了之后 0x11 仍未覆盖；同时刷出大量 `robot.result.If.kwname is deprecated` 警告。
- **根因**：三个独立的坑——
  ① RF 的 `ExecutionResult` 是**懒加载**的，必须显式访问 `suite.tests` / `suite.suites`，只遍历 `body` 什么都拿不到；
  ② **`setup`/`teardown` 是独立属性**（不在 body 里），套件环境和用例的 Test Teardown 里的关键字必须显式取；
  ③ `IF`/`FOR` 等**控制结构节点不是关键字调用**，混进来会触发弃用警告。
- **修复**：显式遍历 tests/suites + 分别取 setup/teardown + 用 `type(node).__name__` 过滤控制结构节点。
- **教训**：用框架的**结果模型 API** 时，先搞清"哪些信息挂在哪个属性上"，别假设 body 包含一切。

### 坑 17：解释器路径的四种解法（最后一种才对）
- **现象**：把 `common.resource` 里硬编码的 Python 路径改成环境变量后，**全部用例全失败**（直接 `python -m robot` 时取到 PATH 里没依赖的 python）。
- **四种方案对比**：
  1. 硬编码路径 → 换机器/CI 必挂；
  2. 环境变量 `%{PYTHON_EXE=python}` → 直接跑 robot 时取不到 → 全挂（本坑）；
  3. `Library` 暴露模块级变量 → 要用 `${库名.变量名}` 访问，引用于 `${PYTHON}` 会 "Variable not found"；
  4. **Variables 文件（`resources/env_vars.py`）** → 模块级常量直接成为全局变量，`sys.executable` 永远等于"当前跑测试的解释器" ✓
- **教训**：**消除环境差异是测试工程化的第一原则**——配置要"跟着执行环境自动走"，而不是让人记住"要传哪个参数"。

---

### 坑 18：UDP 组播的"自发自收"让节点永远无法睡眠
- **现象**：实现网络管理（NM）后，ECU 熄火后应用报文停发了、NM 报文也按周期发了，
  但**永远不进入睡眠** —— "总线静默判定"始终不成立，总线上一直有帧。
- **根因**：`python-can` 的 `udp_multicast` 接口**不支持 `receive_own_messages` 过滤**
  （传 `True` 会直接抛 `CanInterfaceNotImplementedError`，传 `False` 也不真正过滤）。
  于是 ECU **收到了自己发出的 NM 帧**，把"总线活动时间"不断刷新 → 静默条件永不满足。
- **修复**：在监听线程里显式忽略"本节点自己发送的 ID 集合"（`SELF_TX_IDS`）——
  这在 CAN 语义上是正确的：**同一个 ID 只会有一个发送者**，收到自己发的 ID 就是回环。
- **教训**：**仿真环境的传输层语义 ≠ 真实总线语义**。真实 CAN 控制器不会把自己发的帧
  当成"总线活动"，调试这类问题时要先问"这个现象在真车上会发生吗？"
  （注：本项目更早还踩过它的兄弟坑——多网卡组播回环导致同一帧被收两份，见 13 章）

### 坑 19：录制前不清缓冲，录到"开始前"的历史帧
- **现象**：电源管理用例里，"IGN OFF 后应用报文应停发"断言失败——
  录制到的 2 秒里有 7 帧 0x100；手动验证 ECU 明明已经停发了。
- **根因**：RF 不调用 recv 时，帧会一直**堆积在 socket 接收缓冲里**。
  `Start Bus Recorder` 只是清空 recorder 列表，**没有清 socket**，
  于是"开始录制前"的旧帧被录了进来 —— 看起来就像"熄火后还在发报文"。
- **修复**：`Start Bus Recorder` 先调 `drain_rx()` 把缓冲抽干（并打印丢了多少帧）。
- **教训**：任何"开始观测"的动作都要**先清历史状态**，否则数据是脏的。
  这条在真实台架上也成立（CANoe 开始记录前要确认 trace 是空的）。

### 坑 20：测试入口漏了目录，导致覆盖率"凭空变低"
- **现象**：加了 `scenarios/` 目录（78 个用例）后跑统一入口 `run_tests.py --report`，
  需求覆盖率从 87% 掉到 **77.8%** —— 用例变多了覆盖率反而降了。
- **根因**：`run_tests.py` 的默认目标只写了 `tests/robot`，**漏了 `scenarios/`**。
  执行结果里没有场景套件 → 追溯矩阵统计不到那些用例 → 覆盖的需求凭空"消失"。
- **修复**：默认目标改成 `[tests/robot, scenarios]` 两个目录；`--suite` 筛选也同步支持。
- **教训**：**统计类工具的输入范围要和真实测试范围一致**。
  看到"数字异常"时先怀疑"统计口径"而不是"结果本身"—— 这和坑 17（解释器路径）
  属于同一类问题：**工具链的隐性配置错误，比代码 bug 更难发现**。

### 坑 21：清码后立刻读数量 —— 与 ECU 重新检测的竞态
- **现象**：DTC 生命周期场景的"清除后记录应归零"用例**偶发失败**（单独跑能过、全量跑偶挂），
  报"清除后 DTC 数量应为 0，实际 1"。
- **根因**：该套件的故障条件（水温 125℃）**持续存在**，而 ECU 每 500ms 跑一轮 DTC 检测。
  `Clear DTC` 与 `Read DTC Count` 之间只要跨过一个检测周期，故障就被**立即重新记录** ——
  断言里的"0"变成了"1"。**是测试逻辑自身有竞态，不是产品缺陷。**
- **修复**：清除前先用 **`85 02` 暂停 DTC 检测**，清完读数量，再 `85 01` 恢复 ——
  这也正是产线/台架的真实做法（清码前先暂停检测，避免动作互相污染）。
- **教训**：**只要被测系统"一直在动"，任何"读瞬时状态"的断言都可能踩竞态**。
  消除竞态的正确姿势不是加大 `Sleep`，而是**用手头的能力把系统"定住"**
  （暂停 DTC 检测 / 暂停周期报文 / 停发信号），让断言发生在确定的状态里。
  这类问题最阴险的地方是**偶发** —— 它会潜伏到你做全量回归那天才冒出来。

## 6.6 常见问题 FAQ

**Q：UDP 组播在 Linux/macOS 能用吗？**
A：能，python-can 的 udp_multicast 是跨平台的。注意 macOS 防火墙可能拦组播，需要放行 Python。

**Q：能接真实 CAN 硬件吗？**
A：能。买一个 CANable/CANalyst（几十到两百块），把 `bus.py` 的 `interface` 从 `udp_multicast` 改成 `socketcan`（Linux，`channel="can0"`）或 **`slcan`**（CANable 的 slcan 固件：`channel="COM3"`、`bitrate=500000`），上层代码零改动。这就是"总线抽象"的价值。

**Q：能接真的安卓手机/车机吗？**
A：能。手机开"开发者模式+USB 调试"，把 `AdbLibrary.py` 的 `ADB_PREFIX` 改成 `["adb"]`，装好 platform-tools，用例零改动。

**Q：RF 用例能在 CI（Jenkins/GitLab CI）跑吗？**
A：这就是 RF 的强项。`python -m robot --outputdir results --xunit xunit.xml tests/robot/` 产出 JUnit 格式报告，CI 直接消费。台架上配 nightly job 即可。

**Q：为什么不用 CANoe？**
A：CANoe 许可证数千欧元/年，是行业标准但学习门槛在钱。用开源栈把**协议原理**学会（CAN/UDS/TP 的位级别行为我们都实现了），入职后摸 CANoe 只是界面学习。而且——本项目所有概念和 CANoe 一一对应（Trace=我们的 recorder，诊断控制台=uds_client，测试模块=RF 套件）。
