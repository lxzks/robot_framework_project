# 14 · 从零写第一个车载用例（手把手）

> **这一章假设你从没写过自动化脚本。** 我们从一个**空白文件**开始，
> 一行一行写出一个能跑的车载测试用例，并且**故意让你看到它怎么失败、怎么修好**。
>
> 配套练习：[training/L1_first_case](../training/L1_first_case/README.md)
> （先读完本章再做题，或者边读边做）

---

## 14.0 动手之前：两步准备（约 3 分钟）

### 第 1 步：确认环境正常

在**项目根目录**打开终端（后面所有命令都在这里执行），跑：

```bash
python training/check_all.py
```

看到最后一行 `结果：6/6 个练习的参考答案通过` 就说明环境是好的。
如果报"找不到模块 / ModuleNotFoundError"，说明依赖还没装 —— 回到
[06 章 6.1 节](06_环境搭建与项目结构.md) 建虚拟环境并安装依赖。

### 第 2 步：先让"车"动起来（很重要，别跳过）

写脚本之前，先花 1 分钟**看一眼你要测的东西长什么样**。
再开一个终端（同样在项目根目录），分别跑：

```bash
python simulators/ecu_sim.py --speed 60      # 终端1：模拟一辆车（ECU 在周期发报文）
python simulators/dashboard.py               # 终端2：数字仪表盘（能看到指针动）
```

你会看到一个仪表盘窗口，**车速表指针从 0 慢慢爬到 60** —— 这就是你的被测对象。

> 💡 **窗口打不开怎么办**：说明 PySide6 没装好。不影响学习 ——
> 把第二条命令换成 `python simulators/dashboard.py --headless`，
> 仪表会以"无界面"模式运行并把状态写进 `simulators/dashboard_state.json`。
> 你也可以直接打开这个 JSON 文件，看 `speed_kmh` 从 0 涨到 60。

> 💡 **为什么要先做这一步**：你后面写的脚本，做的就是仪表盘背后那件事
> （从总线上读车速）。**先看见实物，代码就不抽象了。**
>
> 看完可以 Ctrl+C 关掉这两个终端（后面的例子会自己拉起环境，不冲突）。

## 14.1 先理解：车载脚本在做什么

在写代码之前，先把"车载自动化测试"这件事翻译成一句话：

> **给车发点东西 / 从车读点东西 / 检查结果对不对。**

```
                 ┌─────────────────────────────────┐
                 │        你的测试脚本              │
                 └────────────┬────────────────────┘
                              │ CAN 总线（本仿真用 UDP 组播模拟）
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │  ECU     │   │  仪表盘   │   │  车机     │
        │ (发信号)  │   │ (显示)   │   │ (娱乐)   │
        └──────────┘   └──────────┘   └──────────┘
```

你的脚本可以：
1. **读** ECU 发的信号（车速 60、水温 90…）→ 断言对不对
2. **发** 报文去模拟别的节点 → 看 ECU/仪表怎么反应
3. **发诊断请求**（UDS）→ 看 ECU 怎么回答

**第一个用例，就练最简单的第 1 种。**

## 14.2 从空白文件开始

### 14.2.1 第一个文件

新建文件 `my_first.robot`，**放在项目根目录**
（和 `resources/`、`simulators/`、`docs/` 同级 —— 放别处会报
"Resource file not found"，因为教程里的路径都是相对根目录写的）：

> ⚠️ **全库通用规则**：本教程所有命令都默认**在项目根目录执行**。
> 这是新手最常踩的坑 —— 命令报"找不到文件"时，先检查你现在在哪个目录。

（RF 的测试文件后缀是 `.robot`。）输入：

```robotframework
*** Test Cases ***
车速应处于合理范围
    Log    你好，车载测试
```

**跑它**：

```bash
python -m robot --outputdir results my_first.robot
```

你会看到：

```
============================================================
My First
============================================================
车速应处于合理范围                                          | PASS |
------------------------------------------------------------
My First                                                    | PASS |
1 test, 1 passed, 0 failed
```

**已经跑通一个"测试"了**——虽然它什么都没测。RF 的最小结构就是：

```
*** Test Cases ***        ← 声明下面是"用例区"
用例名                       ← 一行一个用例
    步骤（缩进 4 空格）      ← 用例的每一步
```

### 14.2.2 加断言：让它"真的测点什么"

```robotframework
*** Test Cases ***
车速应处于合理范围
    ${speed}=    Set Variable    60
    Should Be True    ${speed} > 50
```

两个新东西：
- `${speed}=    Set Variable    60` —— **变量赋值**：把 60 存进 `${speed}`
- `Should Be True    ${speed} > 50` —— **断言**：条件成立则 PASS，不成立则 FAIL

### 14.2.3 让它失败一次（重要！）

把断言改成 `Should Be True    ${speed} > 100`，再跑：

```
车速应处于合理范围                                          | FAIL |
Evaluating expression '60 > 100' failed.
```

**你要习惯看失败信息** —— 未来 90% 的时间你都在和失败信息打交道。
所以写断言时永远带上 `msg=`：

```robotframework
Should Be True    ${speed} > 100    msg=车速 ${speed} 太低了，应该大于 100
```

失败信息就变成：`车速 60 太低了，应该大于 100` —— **一眼知道发生了什么、该查什么**。

> 好的失败信息是给"三个月后的自己"看的。那时候你已经忘了这个用例在干什么。

## 14.3 连上"车"：读真实信号

刚才读的是自己设的假值。现在读**真的从总线上来的数据**。

### 14.3.1 引入环境和库

车载脚本不可能自己造一辆车 —— 需要：
1. **被测环境**（ECU、仪表进程）—— 用 `Start Vehicle Environment` 拉起来
2. **操作总线的关键字** —— 由 `common.resource` 提供的库

所以文件开头要加 `*** Settings ***`：

```robotframework
*** Settings ***
Resource         resources/common.resource
Suite Setup      Start Vehicle Environment    speed=60
Suite Teardown   Stop Vehicle Environment
```

逐个解释：

| 行 | 含义 |
|---|---|
| `Resource  resources/common.resource` | 引入共享资源（里面有库和环境管理关键字） |
| `Suite Setup` | **套件开始前**执行：启动 ECU + 仪表 |
| `Suite Teardown` | **套件结束后**执行：关掉它们（**必须写**，否则进程残留） |
| `speed=60` | 传给环境启动关键字的参数：ECU 以 60km/h 为目标 |

### 14.3.2 读一个信号

```robotframework
*** Test Cases ***
车速应处于合理范围
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Log    读到的车速是 ${speed} km/h
    Should Be True    50 <= ${speed} <= 70    msg=车速 ${speed} 不在 50~70
```

`Read Signal From Bus    EngineData    VehicleSpeed` 做了什么：

1. 等在总线上收到一帧 **EngineData** 报文（CAN ID 0x100）
2. 按 DBC 定义把那 8 个字节**解码**成一个个信号
3. 取出 **VehicleSpeed** 的物理值（×0.01 缩放后）返回

**这两个参数从哪来**（新手必问）：
- `EngineData` 是**报文名** —— DBC 文件给 CAN ID `0x100` 起的名字
- `VehicleSpeed` 是**信号名** —— 该报文里的一个字段（单位 km/h）

它们都定义在 `simulators/dbc/vehicle.dbc` 里。**你不用背** ——
常用清单见 [速查表](../training/cheatsheet.md)（搜"常用信号"），
完整定义和原理见 [02 章 2.4 节](02_车载网络基础.md)。

**你不需要关心字节、缩放、字节序** —— 库和 DBC 帮你处理了。
这就是"用 DBC + 库"的威力，也是真实项目的做法。

### 14.3.3 跑一下（它会失败，这是设计好的）

```bash
python -m robot --outputdir results my_first.robot
```

**先放心：这次失败不是你写错了。** 这是车载测试的一个特点 ——
信号是**物理量**：ECU 启动后车速从 0 开始**爬坡**（每秒涨 8 km/h），
而你读到的是"当前瞬间值"：

```
车速 6.66 不在 50~70
```

> ⚠️ **你跑出来的数字可能不是 6.66** —— 可能是 5、9、12……
> 取决于"ECU 启动有多快"和"你机器上环境起得多快"。
> **数字不重要，重要的是理解**：脚本读得太早，车还没加速到 50 以上。
> （如果你读到正好在 50~70 之间，说明环境起得慢、车已经跑起来了，也算正常。）

**这不是脚本的错，是"时机"的错** —— 14.3.4 就教你正确的解法。

**为什么？** 因为 ECU 启动后车速是**从 0 爬升**的（每秒涨 8 km/h），
你读到的是"当前瞬间值"，此时车才刚起步。

这正是车载测试与普通软件测试最大的不同：**信号是物理量，需要时间**。

### 14.3.4 第一个"错误"的修法（笨办法）

```robotframework
    Sleep    8s
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
```

等 8 秒（60 ÷ 8 ≈ 7.5 秒爬到位），再读。能过，但**这是笨办法**：

- 机器慢一点 → 8 秒不够 → **偶发失败**（最讨厌的 bug：今天过明天不过）
- 机器快 → 白等 8 秒（100 个用例就白等 13 分钟）

**正确做法**在 [15 章·模式 2](15_车载脚本模式库.md) 和 L2 练习里，
现在先记住：**"猜时间"是车载脚本的头号反模式**。

## 14.4 完整的第一版脚本

```robotframework
*** Settings ***
Documentation    我的第一个车载测试脚本
...              验证 ECU 启动后车速信号是否正常
Resource         resources/common.resource
Suite Setup      Start Vehicle Environment    speed=60
Suite Teardown   Stop Vehicle Environment

*** Test Cases ***
车速信号应处于合理范围
    [Documentation]    ECU 以 60km/h 目标启动，读到的车速应落在 50~70
    Sleep    8s
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Should Be True    50 <= ${speed} <= 70
    ...    msg=车速 ${speed} 不在 50~70 范围内

水温信号应为数值
    [Documentation]    水温读回来必须是个数字
    ${coolant}=    Read Signal From Bus    EngineData    CoolantTemp
    Should Be True    ${coolant} > -40
    ...    msg=水温 ${coolant} 异常
```

跑通它：`2 tests, 2 passed, 0 failed` ✓

## 14.5 新手最常犯的 8 个错

按"出现频率"排序 —— 每一个我都见过（或犯过）：

| # | 错误 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | 断言用精确值 `Should Be Equal  ${speed}  60` | 偶发失败 | 用范围：`50 <= ${speed} <= 70` |
| 2 | 用 `Sleep` 等信号 | 偶发失败/白等 | 轮询等待（`Wait Until Signal In Range`） |
| 3 | 忘了写 `Suite Teardown` | 进程残留，下次跑端口冲突 | 永远配对写 Setup/Teardown |
| 4 | 断言不带 `msg=` | 失败只报"AssertionError" | 永远带 msg，含实际值 |
| 5 | 缩进用 Tab 或 2 空格 | "unexpected indent" | **统一 4 空格** |
| 6 | 关键字名拼错/大小写错 | "No keyword with name" | 查 [速查表](../training/cheatsheet.md) |
| 7 | 变量写了 `$speed`（少花括号） | "Variable not found" | RF 变量是 `${speed}` |
| 8 | 一个用例干太多事 | 挂了不知道哪步 | 一个用例一个验证点 |

## 14.6 第一次跑通之后，做什么

1. **跑 L1 练习**（[training/L1_first_case](../training/L1_first_case/README.md)）
   —— 不看答案自己写一遍
2. **故意让它失败**：改断言、改信号名、删 Teardown，看报错长什么样
   （**主动制造失败**是学得最快的方式）
3. **打开 `results/log.html`**：找到你的用例，点开每一步，看
   `Read Signal From Bus` 的**实际参数和返回值** —— 这个页面以后是你的主要工具
4. 进入 [15 章 · 模式库](15_车载脚本模式库.md)：把"能写一个"变成"会写一类"

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | 三个区域：`*** Settings ***`（配置）/ `*** Test Cases ***`（用例）/ `*** Keywords ***`（自定义关键字）。`Suite Setup` = **套件开始前执行一次**（这里用来拉起 ECU + 仪表环境） |
| 2 | 调 `Read Signal From Bus` 关键字；第一个参数是**报文名**（EngineData）、第二个是**信号名**（VehicleSpeed）；返回值存进 `${speed}` |
| 3 | 车速是**物理量**（有噪声、爬坡中、量化误差）→ 精确相等几乎不可能 → 偶发失败。应改成范围：`50 <= ${speed} <= 70` |
| 4 | 差别很大：不写 `msg=` 只显示 "AssertionError"；写了就显示 **"车速 9.17 不在 50~70"** —— 一眼看到实际值和排查方向 |
| 5 | "猜时间"不可靠：机器慢/ECU 启动慢 → 8 秒不够 → **偶发失败**（今天过明天不过）；机器快 → 白等。正确做法是**轮询等待** |
| 6 | ①每个关键字的**入参** ②**返回值** ③库内部的**日志**（如 "读到 CAN 帧 ID=0x100 data=..."） |
