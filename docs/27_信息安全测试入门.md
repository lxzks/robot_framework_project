## 27.0 一句话：信息安全测试测什么

功能测试问的是：**"该工作时它工作吗？"**
信息安全测试问的是：**"不该工作时（异常输入、未授权、攻击者操作）它还能被守住吗？"**

```
功能测试：  正常诊断仪 → 0x27 种子/密钥 → 解锁 → 写 DID ✅
信息安全：  攻击者     → 不取种子直接发密钥 → ???        ← 这就是我们要测的
            攻击者     → 抓包重放旧密钥       → ???
            攻击者     → 穷举错误密钥           → ???
            攻击者     → 300 条畸形帧轰炸       → ECU 会崩吗？
```

本项目在 UDS 诊断服务上做信息安全测试，是因为**攻击者进入车辆的第一站往往就是诊断口（OBD-II）**：
物理接触 OBD 口 → 发 UDS 请求 → 读写数据 / 刷写固件 / 解锁安全访问。
所以 UDS 的权限模型（会话 + 安全访问）本质上是**车端的第一道门**。

## 27.1 为什么车载信息安全要单独测（ISO 21434 / UN R155）

### 27.1.1 法规背景：从"功能安全"到"信息安全"

| 维度 | 功能安全 | 信息安全 |
|---|---|---|
| 关注点 | 系统**故障**时的行为（随机硬件失效、软件缺陷） | 系统**被攻击**时的行为（恶意输入、越权、篡改） |
| 核心标准 | ISO 26262（功能安全）/ ISO 21448（预期功能安全 SOTIF） | **ISO/SAE 21434**（道路车辆信息安全工程） |
| 法规 | — | **UN R155**（信息安全 CSMS + 车型批准）、**UN R156**（软件升级 SUMS） |
| 分析方法 | HARA / ASIL 等级 | **TARA**（威胁分析 TARA + 风险评估） |
| 典型产物 | 安全目标、安全机制验证报告 | 威胁清单、攻击路径、渗透/模糊测试报告、漏洞管理记录 |
| 本项目对应 | 故障注入、DTC、降级（见 [19 章](19_十六个场景脚本实战.md) 场景 11） | **本章：UDS 安全访问攻击面 + 模糊测试** |

> **UN R155 为什么重要**：2022 年起欧盟要求新车企必须建立 **CSMS（网络安全管理体系）**，
> 2024 年起车型必须通过信息安全批准才能上市。也就是说，"信息安全测试"不是加分项，
> 是**法规准入门槛**。Tier1/Tier2 的测试岗位 JD 里越来越常见"渗透测试/模糊测试/ISO 21434"字样。

### 27.1.2 信息安全测试的两种典型工作

1. **渗透测试（Penetration Test）**：站在攻击者视角，手工寻找绕过路径（抓包重放、改协议字段、越权访问、拒绝服务）。本章 ③④⑤⑥ 条用例就是"把已知攻击手法固化成自动化测试"。
2. **模糊测试（Fuzzing）**：把大量随机/半随机/变异输入灌给被测系统，观察它**是否崩溃、是否丢响应、是否能恢复**。本章 ⑧⑨⑩ 条用例就是最小可用版模糊测试。

> 💡 一个常见误区：**"功能都测过了，安全自然也测过了"**。
> 反例就在本项目里：`0x27` 的"正常解锁"功能完全正常（02 套件 13 条用例全绿），
> 但攻击者可以**跳过种子**直接解锁 —— 功能测试永远不会发现这个，因为正常诊断仪永远按流程走。

## 27.2 UDS 安全访问（0x27）机制：种子-密钥

### 27.2.1 正常时序

```
诊断仪 (Tester)                             ECU
     │  27 01  (RequestSeed)                 │
     │ ──────────────────────────────────────>│  生成随机 nonce（本项目 4 字节）
     │  67 01 <seed 4B>                       │  记下：当前挑战 = seed
     │ <──────────────────────────────────────│
     │  本地算 key = f(seed)                  │  f 是 OEM 保密算法
     │  27 02 <key 4B> (SendKey)              │
     │ ──────────────────────────────────────>│  校验 key == f(seed)？
     │  67 02  (正响应 = 解锁成功)             │  成功：置 unlocked，作废 seed
     │ <──────────────────────────────────────│  失败：7F 27 35 (invalidKey)
     │  2E F1 A0 ...（受保护服务，现在可用）   │
```

本项目教学版的 `f` 是 `key = seed XOR 0x5A5A5A5A`（真实 OEM 用 CRC/查表/时间窗，但**流程完全一致**）。
`0x5A5A5A5A` 这个常量出现在 `simulators/ecu_sim.py` 的 `SECURITY_XOR_KEY`，CLI 的 `unlock` 命令也用同一个公式。

### 27.2.2 安全访问相关 NRC（否定响应码）

| NRC | 名称 | 在本项目里的触发场景 |
|---|---|---|
| `0x13` | incorrectMessageLengthOrInvalidFormat | `27 02` 没带 4 字节密钥 / payload 超长；`27 01` 带多余参数 |
| `0x12` | subFunctionNotSupported | `27 05` 等非法子功能 |
| `0x24` | requestSequenceError | **没发 27 01 就直接发 27 02**（本次修复的关键点） |
| `0x35` | invalidKey | 密钥算错 |
| `0x36` | exceedNumberOfAttempts | 连续错 3 次后，锁定期间的任何安全访问 |
| `0x7F` | serviceNotSupportedInActiveSession | 默认会话下直接发 0x27（本项目权限模型：0x27 只在扩展/编程会话开放） |
| `0x33` | securityAccessDenied | 会话对了但没解锁，去调 0x2E 写 DID |

> 📌 NRC 的完整列表见 [03 · UDS 协议详解](03_UDS协议详解.md) 3.3 节。安全测试有个通用技巧：
> **不必每条都手工试**，写一张"请求 × 期望 NRC"的表，数据驱动跑一遍就是安全用例矩阵。

## 27.3 攻击面拆解：0x27 能被怎么打

### 27.3.1 攻击 ①：绕过（Bypass）—— 不取种子直接发密钥

**原理**：如果 ECU 实现里"没有种子"时使用了**默认种子**（常见错误是 0 或全 F），
那么攻击者不需要请求种子，直接按默认种子算出密钥就能解锁。
**本项目历史版本就是这个问题**（见 27.4）。

**正确实现**：`27 02` 前没收到 `27 01` → NRC `0x24`。

### 27.3.2 攻击 ②：重放（Replay）—— 抓到一次就能永久用

**原理**：如果种子是固定值，或者密钥/种子可以重复使用，攻击者只要抓一次
"种子 + 密钥"这一对，就能在任意时间重放解锁（甚至用同一对反复解锁）。

**正确实现**：
- `27 01` 每次都返回**新随机种子**（nonce 语义）；
- 密钥校验成功后**种子一次性作废**，同一密钥不能再用；
- 会话切换/ECU 复位/S3 超时后种子也作废。

### 27.3.3 攻击 ③：爆破（Brute Force）—— 穷举密钥

**原理**：4 字节密钥空间是 2³²，但如果 ECU **没有失败次数限制**，攻击者可以持续尝试；
更糟的是若密钥算法可逆（本项目 `key = seed XOR 常量`，从 key 反推 seed 很容易），
配合固定种子时爆破成本会进一步降低。

**正确实现**：连续错误密钥计数，超过阈值（本项目 3 次）→ 锁定（本项目 5 秒）→
期间所有安全访问返回 `0x36`。真实 ECU 通常还有指数退避/永久锁定+售后解锁流程。

### 27.3.4 攻击 ④：固定种子 / 弱随机

**原理**：如果 `27 01` 永远返回同一个种子（比如写死 `00 00 00 00` 或时间戳低 4 字节），
攻击者可以离线预计算密钥表，重放/爆破都变得容易。

**正确实现**：用密码学安全的随机数（本项目教学版用 `random.randbytes(4)`；
真实车端应该用 HSM/TRNG + 每 ECU 唯一密钥）。测试侧用"连续两次种子不同"做最低限度检查。

### 27.3.5 越权与权限矩阵

安全测试不只盯 0x27，还要验证**整个权限矩阵**：同一服务在不同会话、不同解锁状态下行为必须不同。
本项目的 ECU 权限模型（`simulators/ecu_sim.py` 的 `_check_session_for_service`）：

| 服务 | 默认会话 | 扩展会话（未解锁） | 扩展会话（已解锁） | 编程会话（已解锁） |
|---|---|---|---|---|
| 0x10/0x11/0x3E | ✅ | ✅ | ✅ | ✅ |
| 0x14/0x19/0x22（读） | ✅ | ✅ | ✅ | ✅ |
| 0x27（安全访问） | ❌ 0x7F | ✅（要解锁就是这个入口） | ✅ | ✅ |
| 0x2E（写 DID） | ❌ 0x7F | ❌ 0x33 | ✅ | ✅ |
| 0x31/0x28/0x85 | ❌ 0x7F | ✅ | ✅ | ✅ |
| 0x34/0x36/0x37（刷写） | ❌ 0x7F | ❌ 0x7F | ❌ 0x7F | ✅（未解锁 → 0x33） |

> 💡 **越权用例的设计公式**：`服务 × 会话 × 解锁状态` 的二维/三维矩阵，
> 每个格子都要有正向+负向用例。现有回归：[02 套件](../tests/robot/02_uds_diagnostic.robot)（会话/安全/写 DID 边界）、
> [scenarios/03](../scenarios/03_diag_permission_matrix.robot)（权限矩阵场景）。

## 27.4 本项目的真实漏洞与修复（重点阅读）

### 27.4.1 缺陷：不请求种子即可解锁（CVSS 视角：高危）

体检（代码审计）时发现 `simulators/ecu_sim.py` 的 0x27 处理里有这样一段：

```python
elif sub == 0x02:  # 发送密钥
    key = p[1:5]
    if len(key) != 4:
        self._send_response(negative_response(sid, 0x13))
        return
    expected = compute_key(getattr(self, "_seed", b"\x00" * 4))   # ← BUG
    if key == expected:
        self.security_unlocked = True
```

问题出在 `getattr(self, "_seed", b"\x00" * 4)`：
如果攻击者**没有先发 27 01**，`_seed` 不存在 → 默认 seed = `00 00 00 00`
→ 期望密钥恒等于 `compute_key(00000000) = 0x5A5A5A5A`。

**攻击方式（一条请求）**：

```
10 03                 → 进扩展会话
27 02 5A 5A 5A 5A     → 67 02 解锁成功（完全绕过种子/密钥流程）
2E F1 A0 ...          → 为所欲为
```

这是一个教科书级的**安全访问绕过**：正常流程完全正常（所以功能测试全绿），
但攻击者可以跳过挑战直接拿到权限。

### 27.4.2 修复：状态机 + 一次性种子 + 计数锁定

修复后 `_svc_security_access` 的行为（对应代码里的注释就是设计文档）：

| 请求 | 条件 | 响应 |
|---|---|---|
| `27 01` | 未锁定 | `67 01 <新随机 seed>`（每次都是新种子） |
| `27 01` | 锁定中 | `7F 27 36` |
| `27 02 <key>` | **未请求种子** | `7F 27 24` requestSequenceError ← 修复点 |
| `27 02 <key>` | 密钥正确 | `67 02`，置 unlocked、**seed 一次性作废** |
| `27 02 <key>` | 密钥错误（1~2 次） | `7F 27 35` invalidKey，计数 +1 |
| `27 02 <key>` | 第 3 次错误 | `7F 27 36`，锁定 5 秒（期间 27 01 也拒绝） |
| `27 xx` | 锁定 5 秒后 | 计数归零，可重新 `27 01` |
| `27 02` | payload 长度 ≠ 5 | `7F 27 13`（截断/超长统一按格式错处理） |

新增的 ECU 状态（`simulators/ecu_sim.py`）：

```python
SECURITY_MAX_ATTEMPTS = 3          # 连续错误次数上限
SECURITY_LOCKOUT_SECONDS = 5.0     # 超限后锁定时间

self._seed: bytes | None = None    # 当前挑战种子；None = 未请求种子
self._failed_key_attempts = 0      # 连续错误计数
self._security_lock_until = 0.0    # 锁定截止时刻（time.monotonic）
```

并补齐了三个"种子作废"边界（真实 ECU 同样要求）：

```python
# 会话切换（0x10）：旧种子作废，不能跨会话重放
self._seed = None
# ECU 复位（0x11）：种子作废 + 爆破计数/锁定归零
self._seed = None; self._failed_key_attempts = 0; self._security_lock_until = 0.0
# S3 超时回默认会话：旧种子同样作废
self._seed = None
```

> ⚠️ 教学版仍保留的简化（真实项目要更严）：
> ① 密钥算法是 XOR（可逆）；② 锁定只有 5 秒（真实项目指数退避/永久锁定）；
> ③ 随机数用标准库 `random`（真实车端必须用 TRNG/HSM）。
> 这些简化不妨碍学习**流程与测试方法**，但面试时要说清区别。

### 27.4.3 修复的验收：把漏洞变成"永久回归项"

修完代码容易，**防止回归**才是测试工程师的价值。我们在
[11 套件](../tests/robot/11_security.robot) 里用一条专门用例锁死它：

```robotframework
未请求种子直接发送密钥应被拒绝
    [Tags]    security    REQ-SEC-001    REQ-SEC-002
    Bypass Attempt Should Fail                       # 断言 NRC 0x24
    Send Raw Request    2E F1 A0 4841434B
    SecurityLibrary.Response Should Be Negative With NRC    0x33
```

以后任何人改动 0x27 的处理，只要绕过漏洞重新出现，这条用例立刻失败 ——
这正是"缺陷 → 回归用例"的闭环，也是 [20 章](20_测试规范与验证交付物.md) 缺陷管理的实践。

## 27.5 信息安全测试方法

### 27.5.1 三类用例设计

| 类型 | 例子 | 判定标准 |
|---|---|---|
| **正常路径**（基线） | 27 01 → 27 02 正确密钥 → 写 DID 成功 | 正响应 + 后续操作生效 |
| **攻击/负向** | 绕过、重放、错误密钥、爆破、畸形帧 | 被**明确拒绝**（特定 NRC），绝不能"静默通过" |
| **健壮性/模糊** | 300 条随机 UDS、畸形 payload | 不崩溃、无响应率低于阈值、之后可恢复 |

> 🔑 安全测试最重要的判定原则：**"没有响应"不是"安全"**。
> 如果 ECU 对畸形帧直接静默（不回 NRC），既说明实现不健壮、也让攻击者无法判断边界；
> 更糟的情况是 ECU 崩溃 —— 这时"拒绝攻击"变成了"自己倒下"（拒绝服务 DoS）。
> 所以 11 套件的第 ⑨ 条专门断言"畸形帧必须回明确 NRC 而不是无响应"。

### 27.5.2 模糊测试（Fuzzing）：随机 vs 基于语法

```
随机 fuzzing（dumb fuzzing）
    随机 SID + 随机 payload 灌进去
    → 优点：实现简单、能撞到实现者想不到的输入
    → 缺点：绝大多数请求在协议第一层就被 NRC 拒掉，覆盖率低

基于语法/变异的 fuzzing（smart fuzzing）
    拿合法请求模板，按协议字段做变异（改长度、改边界值、删字节、换枚举）
    → 优点：能深入状态机/业务逻辑，覆盖率高
    → 缺点：需要协议模型（本项目就是"UDS 服务/子功能表"）

工业级工具：
    AFL/AFL++、libFuzzer  → 通用二进制/库 fuzzing（有编译插桩做覆盖率反馈）
    Peach / boofuzz       → 协议 fuzzing（基于数据模型/语法）
    自研脚本（本条）      → 车载诊断场景常用：python-can 直接发 UDS 帧
```

本项目的 `Fuzz UDS Requests` 采用**混合策略**（也是真实项目常见做法）：

```python
# SecurityLibrary.Fuzz UDS Requests 的核心（简化）
if rng.random() < 0.4:
    req = random.choice(LEGAL_TEMPLATES)      # 40% 合法模板（保证有正响应）
else:
    sid = random.choice(FUZZ_SIDS)            # 60% 随机 SID + 随机 payload
    req = bytes([sid]) + random_bytes(rng)
```

**可复现性**：模糊测试必须能复现！所以随机种子是**参数**（默认 20261028），
同一个种子每次生成同一批请求 —— 出了缺陷才能拿着 seed 重放定位。
（真实 AFL 会把触发 crash 的输入存成独立文件，本项目是把它固化成关键字参数。）

### 27.5.3 判定指标

| 指标 | 本项目阈值 | 说明 |
|---|---|---|
| `no_response` | ≤ 20 / 300 | 无响应不能为 0（`3E 80` 抑制正响应是**正确静默**），但过高说明丢帧/卡死 |
| `positive` | ≥ 20 | 合法模板必须仍有正响应，否则说明状态机被打坏 |
| `alive` | True | 模糊后发 `3E 00`，确认 ECU 还活着（诊断线程没死） |
| 恢复性 | 读 VIN < 500ms | 复位一次后 `22 F1 90`（20 字节，ISO-TP 多帧）要在合理时间内回正响应 |

本项目实测（300 条随机请求，2 次连跑结果一致）：

```
{'total': 300, 'positive': 111, 'negative': 186,
 'no_response': 3, 'alive': True, 'elapsed_s': 7.7}
```

> 3 条无响应是什么？大概是随机命中了 `3E 8x`（抑制正响应的 TesterPresent）——
> 这是 ECU 的**正确行为**，不是缺陷。这就是为什么阈值不是 0。

```

libraries/SecurityLibrary.py   安全测试仪：种子/密钥/攻击/模糊测试关键字（SUITE 作用域）
tests/robot/11_security.robot  10 条用例：正基线 + 4 类攻击 + 模糊 + 畸形帧 + 恢复性
resources/common.resource      环境生命周期（启动 ECU + headless 仪表，套件结束回收）
docs/27_信息安全测试入门.md    本章
```

### 27.6.2 SecurityLibrary 关键字一览

| 关键字 | 作用 | 返回 |
|---|---|---|
| `Open Security Session` | 进扩展会话（0x27 的前提）；会话切换会重新锁定 | — |
| `Request Seed` | 发 `27 01`，断言正响应 | seed hex |
| `Send Key` | 发 `27 02 <4B key>`，不断言（便于负向用例接断言） | 响应描述 |
| `Unlock Sequence Should Succeed` | 正基线：取种子 → 算 key → 发送 → 断言成功 | `[seed, key]` |
| `Seed Should Be Random` | 连续 3 次取种子，至少 2 个不同（nonce 检查） | seeds 列表 |
| `Send Wrong Key For Seed` | 对给定种子发"翻转 1 bit"的必定错误密钥 | 响应描述 |
| `Bypass Attempt Should Fail` | **漏洞回归**：不取种子直接发 `27 02 5A5A5A5A` → 必须 NRC 0x24 | — |
| `Failed Attempts Should Lock Access` | 连续 3 次错误 → 0x35/0x35/0x36，且锁定中 `27 01` 也被拒 | — |
| `Replay Key Should Fail` | 换新种子后用旧密钥 → NRC 0x35（带种子碰撞保护） | — |
| `Send Raw Request` | 发任意裸 UDS 请求 | 响应描述 |
| `Security Access Should Fail With NRC` | 断言上一条响应是指定 NRC | — |
| `Response Should Be Positive` | 断言上一条响应是正响应（与 DiagnosticLibrary 同名，套件里用 `SecurityLibrary.` 前缀消歧） | — |
| `Reset Security State` | 用例隔离：复位 ECU + 重进扩展会话 | — |
| `Fuzz UDS Requests` | 发 N 条随机/半随机请求 | 统计 dict |
| `ECU Should Stay Alive` | 模糊后确认 ECU 仍在线（3E 00，带重试） | — |
| `Malformed Frame Should Be Rejected` | 畸形帧必须回**指定 NRC**（无响应 → 失败） | — |
| `Measure Response After Fuzz` | 模糊后测一次响应耗时并断言正响应 | 毫秒 |
| `Close Security Tester` | 停收包线程 + 释放虚拟总线（Teardown） | — |

> 💡 为什么 `11_security.robot` 里有些关键字要写 `SecurityLibrary.Response Should Be Positive` 全名？
> 因为 `resources/common.resource` 还会加载 `DiagnosticLibrary`，它也有同名关键字
> → Robot 发现两个同名关键字会要求"给出完整库名"。这是 RF 多库工程的正常操作。

### 27.6.3 11 套件逐条讲（10 条）

| # | 用例 | 标签 | 验证点 |
|---|---|---|---|
| ① | 正常种子密钥握手应解锁成功 | REQ-SEC-001 | 正基线：解锁后 `2E F1 A0`（6 字节值，走 ISO-TP 多帧）成功 |
| ② | 两次请求的种子应不同 | REQ-SEC-002 | nonce：固定种子 = 重放温床 |
| ③ | 未请求种子直接发送密钥应被拒绝 | REQ-SEC-001/002 | **漏洞回归**：0x24；且随后写 DID 仍 0x33 |
| ④ | 错误密钥应被拒绝 | REQ-SEC-001 | 翻转 1 bit 的确定性错误密钥 → 0x35 |
| ⑤ | 连续 3 次错误密钥应触发锁定并自动恢复 | REQ-SEC-003 | 0x35/0x35/0x36；锁定中 27 01 → 0x36；5 秒后恢复 |
| ⑥ | 重放旧密钥应失败 | REQ-SEC-002 | 旧 key + 新 seed → 0x35；写 DID 仍 0x33 |
| ⑦ | 解锁后复位应重新锁定权限 | REQ-SEC-001 | 11 01 → 会话回默认、权限失效（2E → 0x7F） |
| ⑧ | 300 条随机 UDS 不应打崩 ECU | REQ-SEC-004 | no_response ≤ 20、alive、之后 22 F187 正常 |
| ⑨ | 畸形帧应返回明确 NRC 而不是无响应 | REQ-SEC-005 | 截断/超长/非法子功能 → 0x13 / 0x12 |
| ⑩ | 模糊测试后 ECU 状态应可恢复 | REQ-SEC-004/005 | 复位一次 → 读 VIN（多帧）< 500ms → 普通诊断正常 |

**几个设计细节（面试可讲）**：

1. **④ 的错误密钥为什么是"翻转 1 bit"而不是随机？**
   —— 确定性。随机密钥有极小概率刚好等于正确密钥（2⁻³² 的假失败），
   翻转 1 bit 保证"必然错误、且不依赖运气"。
2. **⑤ 锁定期间为什么要用 `3E 00` 保活？**
   —— 等 5 秒锁定期间如果什么都不发，ECU 的 S3 定时器（5 秒）会把会话回退到默认，
   下一个请求就变成"默认会话不支持 0x27（0x7F）"，断言会误判。
   这是"安全测试也要处理会话时序"的典型细节。
3. **⑥ 重放测试怎么保证不比错？**
   —— `key = seed XOR 常量` 可逆，所以能从旧 key 反推出旧 seed；
   重新取新种子后，先确认新 seed ≠ 旧 seed，再发旧 key —— 排除天文概率的假失败。
4. **⑨ 为什么"无响应"要单独判失败？**
   —— `Malformed Frame Should Be Rejected` 内部把 TimeoutError 转成
   `AssertionError("畸形帧无响应（应按协议回 NRC…）")`。
   安全测试里"请求被吞掉"和"ECU 崩了"都可能是严重缺陷，不能让用例静默通过。
5. **⑧ 和 ⑩ 为什么分开？**
   —— ⑧ 证明"轰炸时不崩"，⑩ 证明"轰炸后能恢复"。真实 DoS 缺陷常见两种：
   立即崩溃，或"看起来活着但状态机卡死" —— 后者只有恢复性用例能抓到。

## 27.7 真实项目怎么接

### 27.7.1 工具链对照

| 场景 | 真实项目工具 | 本项目替代 |
|---|---|---|
| 诊断请求手工构造/发包 | **CANoe / CANape 诊断控制台**、ODX 诊断数据库 | `SecurityLibrary.Send Raw Request`（python-can 直发 UDS） |
| 抓总线 + 重放 | CANoe Trace + 重放、vTESTstudio、ecu.test | `VirtualCanBus` 录制/回放 + 脚本（[13 章](13_测试工程化与CI.md) Trace 归档） |
| 协议模糊测试 | **Peach Fuzzer / boofuzz**、AFL/AFL++（二进制） | `Fuzz UDS Requests`（混合随机+模板，可复现种子） |
| 安全测试框架 | 商用渗透工具、开源 Scapy（构造任意帧） | `python-can` + 自研库（本模块） |
| 威胁分析 | **TARA**（ISO 21434）、攻击树、CVSS 评分 | 27.3 攻击面清单（简化版 TARA） |
| 漏洞管理 | JIRA 缺陷单 + 漏洞跟踪、修完补回归 | `deliverables/defect_report_template.md` + ③ 用例 |

> 如果公司有 CANoe：安全测试日常就是"在 CANoe 诊断控制台里手打攻击序列"，
> 找到可复现的绕过路径后，再写成自动化回归（Python/capl）。
> 本项目用 python-can 把两步都做了 —— **协议层完全一样，只是传输从硬件 CAN 换成 UDP 组播**。

### 27.7.2 一份最小安全测试报告的骨架

```
1. 测试对象与版本     ECU 诊断软件 vX.Y / 安全访问实现
2. 参考标准           ISO 21434 TARA 条目、UN R155 附件 5 要求
3. 测试环境           仿真台架 / HIL / 实车；诊断接口（CAN 0x7E0/0x7E8）
4. 攻击面与用例矩阵   绕过 / 重放 / 爆破 / 固定种子 / 畸形帧 / 模糊
5. 结果               每条：预期 NRC vs 实际；通过/失败；证据（Trace/日志）
6. 风险评级           未修复项的 CVSS 分值 + 影响（如"可未授权写 DID → 高危"）
7. 修复建议与回归     修复版本 + 回归用例编号（如 11 套件 ③⑥⑤）
8. 结论               是否满足放行门槛
```

### 27.7.3 安全测试 vs 功能测试的工程差异

- **安全用例必须有"负向预期"**：不仅断言"能做"，还要精确断言"不能做，并且给的是哪个 NRC"。
- **安全结果要可复现**：模糊测试的随机种子、发包序列、ECU 版本都要记录。
- **安全测试往往跨团队**：测试发现 → 开发修 → 安全团队评风险 → 回归 → 更新 TARA。
- **安全测试会做"破坏性"操作**（复位、刷写、爆破锁定），所以环境隔离/恢复用例必不可少
  —— 本项目每条用例前 `Reset Security State`，⑩ 专门验证恢复性。

## 27.8 自查题（先想 30 秒再看要点）

1. **0x27 的种子-密钥流程里，哪一步最容易实现错、导致安全漏洞？为什么？**
   > 要点：`27 02` 的"前置校验"（是否真的收过 27 01）和种子的生命周期。默认种子/复用种子/成功后不清种子都会导致绕过或重放。
2. **为什么功能测试发现不了本项目 27 02 的绕过漏洞？**
   > 要点：功能测试只走正常流程（27 01→27 02），绕过是"不走正常流程"的攻击路径，必须靠攻击用例/代码审计/渗透测试。
3. **NRC 0x24 / 0x35 / 0x36 在安全访问里分别代表什么？什么时候出现？**
   > 要点：0x24 序列错误（没取种子就发密钥）；0x35 密钥错误；0x36 失败次数超限（锁定中，连 27 01 都拒）。
4. **固定种子有什么危害？测试上怎么用最低成本发现它？**
   > 要点：可离线预计算/重放；测试：连续请求两次种子，断言不同（本项目 ② 用例）。
5. **模糊测试为什么不能只看"有没有崩溃"？**
   > 要点：还要看响应率、是否吞帧、状态机是否卡死、能否恢复；本项目用 no_response 阈值 + alive + 恢复性读 VIN 三层判定。
6. **随机 fuzzing 和基于语法的 fuzzing 各自优缺点？本项目为什么混合？**
   > 要点：随机简单但覆盖率低；语法/变异深入业务但需要协议模型。混合兼顾广度（随机）和深度（合法模板保证正响应/状态切换）。
7. **安全测试为什么需要"复位/恢复"类用例？**
   > 要点：爆破/畸形帧等攻击会留下锁定/异常状态；必须证明 ECU 能回到正常工况（防 DoS 残留在现场）。
8. **如果让你把本项目安全模块接进 CI，你会加哪些门禁？**
   > 要点：11 套件全绿 + 02 回归全绿；漏洞回归用例必须存在；fuzz 统计进日志归档；要求需求标签 REQ-SEC-* 进追溯矩阵。

### 本章要点回顾（面试速答）

- 车载信息安全有法规门槛：**ISO 21434 + UN R155**；与功能安全（ISO 26262）关注点不同。
- UDS 安全访问（0x27）的四个攻击面：**绕过、重放、爆破、固定种子**；外加**权限矩阵越权**。
- 本项目真实缺陷：`27 02` 未请求种子时用默认 seed=0 计算密钥 → 直接 `27 02 5A5A5A5A` 解锁；已修复为 **0x24**，并加一次性种子、nonce、3 次错误锁定 5 秒（0x36）。
- 安全测试方法：正向基线 + 攻击负向（精确断言 NRC）+ 模糊测试（混合策略、可复现种子、指标判定）+ 恢复性验证。
- 自动化的价值在于**把漏洞变成永久回归项**（11 套件 ③），而不是只修不测。
