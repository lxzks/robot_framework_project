## 19.2 场景 1：动力域信号验证

**业务背景**：仪表盘上所有动力信息（车速/转速/水温/档位/里程）都来自 ECU 的周期报文。
这是"每天都会跑"的基础回归。

**三个层次的验证**（这是方法论，不只是这一场景的）：
1. **存在性**：信号在不在（ECU 发了没有）
2. **范围**：值合不合理（用物理极限判：水温不可能 -50℃）
3. **联动**：信号之间关系对不对 ← **最有价值**

```robotframework
转速应与车速保持设计比例
    ${speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    90    110    timeout=25
    ${rpm}=    Read Signal From Bus    EngineData    EngineSpeed
    ${expected}=    Evaluate    max(800, ${speed} * 80)
    ${diff}=    Evaluate    abs(${rpm} - ${expected})
    ${tolerance}=    Evaluate    max(200, ${expected} * 0.05)
    Should Be True    ${diff} <= ${tolerance}
    ...    msg=转速 ${rpm} 与期望=${expected}（车速×80）偏差 ${diff}，超过容差 ${tolerance}
```

**为什么联动断言值钱**：如果 ECU 的转速模型写错（比如系数写成 60 而不是 80），
单看"转速在 0~16000 范围内"永远是绿的 —— **只有联动断言能发现**。

**新技巧**：里程单调性用"排序前后是否相同"来验（比在 Evaluate 里手写列表推导稳）：

```robotframework
${sorted}=    Copy List    ${readings}
Sort List    ${sorted}
Lists Should Be Equal    ${readings}    ${sorted}    msg=里程未单调累积
```

## 19.3 场景 2：警告灯矩阵

**业务背景**：警告灯（telltale）是**法规强制**的安全显示项。三个测试层面：
① 该亮时亮 ② **不该亮时别亮**（最易漏测） ③ 全亮自检（产线 EOL 用）。

**脚本技巧**：数据驱动遍历 12 个灯名，失败时能精确报出是哪个灯没实现：

```robotframework
@{ALL_TELLTALES}    MilWarning    OilPressureLow    CoolantTempHigh    BatteryLow
...                 AbsFault    AirbagFault    SeatbeltWarning    TurnLeft
...                 TurnRight    HighBeam    LowBeam    ParkBrake

自检清单应包含全部 12 个灯名
    Enter Extended Session                 # ⚠ 0x31 例程在默认会话不可用！
    Start Light Test Routine
    ${lit}=    Get Lit Telltales
    FOR    ${telltale}    IN    @{ALL_TELLTALES}
        Should Contain    ${lit}    ${telltale}
        ...    msg=灯光自检未点亮 ${telltale}，实际点亮: ${lit}
    END
```

> 🔴 **写这个场景时真的抓到一个 bug**：ECU 的灯光自检清单漏了 `SeatbeltWarning`，
> 只点亮 11 个灯。而**灯清单在三个地方各有一份**（ECU 的 override、仪表 UI、DBC 信号），
> 三处不同步就是典型缺陷。这就是"遍历式断言"的价值 —— 它精确地指出了是**哪一个**灯。

## 19.4 场景 3：诊断权限矩阵

**业务背景**：诊断服务有**严格的权限模型**，权限边界是 Tier1 交付物里必查的项。

**用矩阵表达覆盖**（一眼看出有没有漏）：

```
                默认会话   扩展未解锁   扩展已解锁   复位后
读数据           ✅ 允许     ✅ 允许      ✅ 允许     ✅ 允许
写数据           ★0x7F      ★0x33       ✅ 成功     ★0x7F
```

**关键写法**：写操作后**必须回读**（正响应只说明"收到了"，不代表"写对了"）：

```robotframework
扩展会话已解锁写数据应成功且可回读
    Enter Extended Session
    Security Unlock
    Write DID    F1A0    56332E302E30
    ${ver}=    Read DID As ASCII    F1A0      # ★ 回读验证
    Should Be Equal    ${ver}    V3.0.0
```

**"复位后权限应失效"** 这条容易被忽略：权限残留是安全隐患（退出诊断后别人能直接接着写）。

## 19.5 场景 4：DTC 全生命周期

**业务背景**：DTC 有状态机（连续 N 个周期异常才 confirmed），为的是**防误报**。

**技巧**：用**状态掩码**查询，比"码存在"更严格：

```robotframework
DTC 应以 confirmed 状态存在
    [Arguments]    ${expected_dtc}
    ${records}=    Read DTC By Mask    08          # 08 = confirmed
    ${names}=    Evaluate    [r[0] for r in $records]
    Should Contain    ${names}    ${expected_dtc}
    ...    msg=confirmed 状态列表中未找到 ${expected_dtc}，实际: ${names}
```

**闭环的最后一步最容易被漏**（"故障仍在时应重新记录"）：它证明清除没破坏检测能力。
真实场景对照："清码后过几天又亮"。

## 19.6 场景 5：会话时序与保活

**业务背景**：非默认会话有 **S3 定时器**（本项目 5 秒）：静默超时会自动回退默认会话
并锁定安全访问 —— 防止"诊断接头拔了但权限还开着"。

**时序类需求的铁律：验"变化"，不是验"状态"**。要同时证明两件事：
1. **静默 → 会回退**（超时生效）
2. **保活 → 不会回退**（保活有效）

```robotframework
静默超过 S3 时间应回退默认会话并锁定权限
    Enter Extended Session
    Security Unlock
    Sleep    6s                                    # 这里的 Sleep 是需求本身
    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x7F   # ← 0x7F 而不是 0x33
```

**NRC 的区别就是证据**：`0x7F`（会话不支持）= 已回退默认会话；
`0x33`（权限不足）= 还在扩展会话但没解锁。**断言哪个 NRC 决定了用例在验什么**。

## 19.7 场景 6：座舱多屏一致性

**业务背景**：车机上点歌/开导航/调空调，仪表要立即同步（链路：车机状态 → CAN → 仪表）。

**最后一个用例很特别** —— **域隔离验证**：

```robotframework
座舱设置不应影响动力域信号
    Set Headunit Media State    track_index=5    volume=100
    Broadcast Headunit State To Bus
    Start Bus Recorder
    Drain Bus For    2
    Stop Bus Recorder
    Period And Jitter Should Be Within    0x100    100
    ...    period_tolerance_ms=25    jitter_tolerance_ms=60
```

**真实缺陷对照**：车机疯狂发报文会把总线负载拉高，挤压动力报文的周期 ——
"娱乐功能影响安全功能"是真实发生过的严重问题。这条用例就是防它。

## 19.8 场景 7：刷写流程与失败路径

**业务背景**：刷写（固件升级）是诊断测试里权重最高的场景 —— **失败路径比成功路径更重要**
（刷一半失败不能让 ECU 变砖）。

六条用例 = 1 条成功流程 + 4 条失败路径 + 1 条**恢复验证**：

| 用例 | 验证点 |
|---|---|
| 完整刷写流程应成功 | 四步曲 + 完整性校验 0x00 |
| 失败路径_未解锁 | NRC 0x33 |
| 失败路径_块序号错乱 | NRC 0x73（真实刷写最常见的失败：丢块） |
| 失败路径_字节数不足 | 校验结果 0x01（固件不完整必须被识别） |
| 失败路径_地址超范围 | NRC 0x31（越界保护） |
| **刷写失败后应能重新开始** | 失败一次不该把 ECU 卡死 |

**用例隔离**（刷写场景必须做）：

```robotframework
Test Teardown    复位 ECU 清理刷写状态

复位 ECU 清理刷写状态
    Run Keyword And Ignore Error    Send UDS Request    11 01
    Sleep    0.2s
```

> 不做隔离会导致"前一个用例留下的 flash_state 让后续 0x34 全撞 NRC 0x24" ——
> 而且**单独跑能过、连续跑才挂**，是最难查的一类失败。

## 19.9 场景 8：总线健康度监控

**业务背景**：报文**周期是设计指标**（车速 100ms / 水温 200ms / 灯状态 500ms）。
周期跑偏或抖动过大会让依赖它的节点异常。台架上用 CANoe 看这个，我们用录制器自己算。

**两个概念**（真实工作高频词）：
- **周期均值**：相邻两帧时间差的平均 —— 该 100ms 就得接近 100ms
- **抖动 Jitter**：最大间隔 − 最小间隔 —— **均值正常但抖动大是最隐蔽的问题**

```robotframework
车速报文周期应为 100ms 且抖动可控
    Period And Jitter Should Be Within    0x100    100
    ...    period_tolerance_ms=20    jitter_tolerance_ms=40
```

**这个场景还演示了"Setup 造场景"**：录制在 Suite Setup 完成，各用例只做分析，
避免"用例之间抢着录制"的顺序依赖。

## 19.10 场景 9：响应时序一致性

**业务背景**：ECU 在会话响应里**声明** P2=50ms（最长响应时间）。实测超标会让诊断仪
误判超时 → 现场表现为"诊断仪连不上车"。

**关键技巧：多点采样**。时序问题往往是"偶尔慢"，单次测量会漏掉：

```robotframework
读数据响应时间应稳定在 P2 内（多点采样）
    @{samples}=    Create List
    FOR    ${i}    IN RANGE    ${SAMPLE_COUNT}
        ${ms}=    Measure Response Time    22 F187
        Append To List    ${samples}    ${ms}
    END
    ${max_ms}=    Evaluate    max($samples)
    ... （断言最大值 < P2）
```

> ⚠ 变量名故意叫 `${SAMPLE_COUNT}` 而不是 `${SAMPLES}`：**RF 的变量名大小写不敏感**，
> 会和列表 `${samples}` 撞车（报 `Expected number, got list`）。踩过这个坑。
>
> 另外 `max($samples)` 里的 `$samples`（无花括号）是 RF 引用"Python 对象"的语法 ——
> 写成 `${samples}` 会展开成多个参数而报错。

## 19.11 场景 10：冒烟回归集（Tag 分层）

**业务背景**：`tests/robot` 主套件 198 个用例约占大头，全量 276 个（主套件 + 场景）
约 6 分钟（本机实测 359~380s（多次实测））；改代码后只想"快速确认没坏主要功能"。用 **Tag** 分层：

```bash
python run_tests.py                                        # 全量（276 用例）
python -m robot --include smoke tests/robot/ scenarios/     # 冒烟（当前 smoke 都在 scenarios，29 条约 40~60 秒）
python -m robot --include negative tests/robot/ scenarios/  # 只跑负向
python -m robot --include diagnostic scenarios/             # 只跑诊断相关
```

**冒烟集的选择原则**：覆盖"三条主链路"就够 ——
① 信号链（ECU → 总线 → 仪表）② 诊断链（会话 → 读 → 写+权限）③ 故障链（注入 → DTC → 灯）。

**这条用例抓到过一个"经典陷阱"**：

```robotframework
主链路_信号链应通
    Wait Until Signal In Range    EngineData    VehicleSpeed    58    62    timeout=20   # ★ 先等稳态
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    ${shown}=    Get Displayed Speed
```

> 🔴 第一版写的是等车速进入 50~70 就立刻比较 —— 结果**总线 50.25 vs 仪表 60.0**。
> 原因：`Wait Until` 在进入区间的**瞬间**就返回了，此时车速还在爬升，
> 两次读取的采样时刻不同，两个**动态值**必然对不上。
> **跨系统一致性测试必须先等系统进入稳态** —— 这是很值钱的一条经验。

## 19.12 场景 11：故障注入与鲁棒性测试

**业务背景**："功能都对"只是软件测试；**异常条件下行为对**才是系统验证。
真实台架用可编程电源 + 故障注入盒造异常；本场景用 ECU 的**工程模式 DID（F1B0）**
注入三类激励：

- **供电电压异常**：低压 9V（冷启动临界）/ 过压 16V（发电机调节器失效）
- **报文停发**（`suppress_mask`）：模拟信号源失效（CAN 线瞬断）
- **丢帧率**（`drop_rate`）：模拟总线质量下降

```robotframework
低压工况应记录电压过低故障并点亮电池灯
    Enter Extended Session                  # 写工程模式 DID 需要扩展会话
    Security Unlock                         # 并做安全解锁（权限不放松）
    Set Test Stimulus    voltage=9          # 注入 9V 低压
    Wait Until Keyword Succeeds    15x    1s    DTC List Should Contain    P0562
    Telltale Should Be Lit    BatteryLow    timeout=10   # 诊断视角 + 仪表视角都要对

车速信号丢失时仪表应保持最后有效值
    ${speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    55    65    timeout=20
    ${shown_before}=    Get Displayed Speed
    Enter Extended Session
    Security Unlock
    Set Test Stimulus    suppress_mask=1     # bit0 = 停发 0x100(EngineData)
    Sleep    2s                             # 这里的等待是需求本身：观察丢失后的行为
    ${shown_after}=    Get Displayed Speed
    Should Be True    ${shown_after} > 1
    ...    msg=信号丢失后仪表跳到 ${shown_after}（应保持最后有效值，不该归零）
```

**最关键的一条：注入类用例必须清理激励**：

```robotframework
Test Teardown    清除测试激励并复位
```

> 🔴 不清理的后果：下一个用例（甚至下一个套件）都在 9V/丢帧/停发状态下运行，
> 表现为"单独跑能过、全量跑才挂"——和场景 7 的 `flash_state` 残留是同一类隔离问题。
> `Set Test Stimulus` 背后是工程模式 DID `F1B0`，真实台架对应"可编程电源 + 故障注入盒"。

**这个场景的 4 条失败路径/恢复思路**：低压/过压 DTC → 信号丢失保持 → 丢帧下诊断仍可用 →
清除激励后周期报文恢复（恢复性验证）。

## 19.13 场景 12：电源模式与网络管理（NM）

**业务背景**：车辆熄火后所有 ECU 必须协商进入低功耗睡眠 —— 整车"暗电流"通常要求
**< 20mA**，任何一个节点偷偷发报文都会导致亏电、车主第二天打不着火。协商机制是三重：

- ① **电源模式广播**：BCM 通过 CAN `0x600` 广播 IGN OFF
- ② **网络管理协商**：各节点周期发 NM 报文（`0x510`）+ 睡眠就绪位
- ③ **总线静默判定**：都就绪且静默够久 → 一起进睡眠；任意 CAN 活动（车门/遥控/IGN）可唤醒

> 注：仿真把"静默判定时长"缩短到 **2 秒**（真实项目通常几十秒），其余机制与真实一致。

**验证"睡着了"的方法不是读状态位，而是"录一段总线看有没有帧"**：

```robotframework
总线静默后节点应进入睡眠（总线零帧）
    Send CAN Frame    0x600    00      # 模拟 BCM 广播 IGN OFF（真实由 BCM 发，仿真里测试扮演）
    Sleep    4s                        # 等过睡眠判定（2 秒）+ 余量
    Start Bus Recorder
    Drain Bus For    3
    Stop Bus Recorder
    ${n}=    Recorded Frame Count
    Should Be Equal As Integers    ${n}    0
    ...    msg=进入睡眠后总线应完全静默，实际录到 ${n} 帧（暗电流不达标）
```

```robotframework
IGN OFF 后应用报文应停发且 NM 应置睡眠就绪位
    Send CAN Frame    0x600    00
    Sleep    1s
    Start Bus Recorder
    Drain Bus For    2
    Stop Bus Recorder
    Recorded Frames Should Not Contain ID    0x100   # 应用报文停了
    Recorded Frames Should Contain ID    0x510       # NM 报文还在发
    ${nm}=    Get Last Frame Data For ID    0x510
    ${sleep_ready}=    Evaluate    int('${nm}'[2:4], 16) & 0x01
    Should Be Equal As Integers    ${sleep_ready}    1
```

**唤醒与恢复**：睡眠中最怕"叫不醒"——

```robotframework
CAN 唤醒帧应唤醒节点并恢复应用报文
    Send CAN Frame    0x600    00

    Send CAN Frame    0x123    00      # 模拟唤醒源（车门/遥控）

```

**同样必须做隔离清理**（否则后续套件全在"熄火"状态跑，表现为"报文突然全消失"）：

```robotframework
Test Teardown    恢复正常电源模式     # 内部发 0x600 02（IGN）+ 唤醒帧
```

## 19.14 场景 13：车身域 LIN 联动

**业务背景**：车身域控制器（BCM）通过 **LIN 单线主从总线**连接雨量传感器、雨刷电机、
座椅模块等低速执行器。真实工作里这是"车身功能回归"的日常：**传感器信号 → BCM 策略 →
执行器动作**；以及熄火后的 LIN 睡眠/唤醒（静态电流指标）。脚本：
`scenarios/13_lin_body_control.robot`（**6 条用例，连跑两次 6/6 全绿**）。

**6 条用例覆盖什么**：

| 用例 | 验证点 |
|---|---|
| 车身 LIN 调度表应按 10ms 时基轮询四个报文 | 4 槽位 × 10ms = 40ms 周期，帧间隔均值/抖动（REQ-LIN-001） |
| 雨量增大时 BCM 应把雨刷从 OFF 切到 HIGH 档 | 雨量 → BCM 策略 → 雨刷档位/转速下发（REQ-LIN-002） |
| 座椅记忆位置应能保存、移动后恢复 | 0x12 两字节位布局 + "存→动→恢复"业务流（REQ-LIN-002） |
| 校验和错误的雨量帧应被识别为无效（负向） | 注入 checksum 错误 → 该帧被标记无效、独立重算断言失败（REQ-LIN-003） |
| 进入睡眠后 LIN 总线应保持静默 | 0x3C 主请求首字节 0x00 = 睡眠，之后 0.5s 零帧（REQ-LIN-004） |
| 唤醒后调度应恢复且从机信号保持 | 唤醒脉冲 → 调度恢复、雨量 42% 不丢（REQ-LIN-004） |

**关键代码**（业务侧的"BCM 决策"显式写成关键字，真实车上这段逻辑在 BCM 软件里）：

```robotframework
雨量增大时 BCM 应把雨刷从 OFF 切到 HIGH 档
    ${marker}=    Set LIN Slave Signal    ${FRAME_RAIN}    rain_intensity=75
    ${rain}=    Wait For LIN Frame    ${FRAME_RAIN}    timeout=2    since_seq=${marker}
    LIN Frame Should Contain Signal    ${rain}    rain_intensity    75    tolerance=0.5
    ${gear}=    BCM 根据雨量决策雨刷档位    75        # 0%→OFF，1~30→间歇，31~70→低速，>70→高速
    ${speed}=    Evaluate    ${gear} * 1200
    ${marker}=    Set LIN Slave Signal    ${FRAME_WIPER}    wiper_state=HIGH    wiper_speed=${speed}
    ${wiper}=    Wait For LIN Frame    ${FRAME_WIPER}    timeout=2    since_seq=${marker}
    LIN Frame Should Contain Signal    ${wiper}    wiper_state    HIGH
    Should Be Equal As Integers    ${wiper}[data][0]    147     # 3 | (3600/100)<<2
```

**为什么这样测**：LIN 是**主从**总线（从机不许主动说话），所以①调度表时基/周期必须单测；
②业务联动要同时断言"物理值"（LDF 解码）和"原始字节"（位布局），否则编码错位时两层一起错；
③睡眠/唤醒必须用"总线是否还有帧"来验证，而不是读状态位（和场景 12 的 NM 同理）。

**踩坑**：①**枚举信号断言要按枚举名**（`wiper_state    HIGH`），传数字 `3` 会被当成
"不存在的枚举名"直接报错（LDF 值表只认名字和数字两种形态，字符串数字走名字分支）；
②读帧一律带 `since_seq=${marker}`，否则可能读到"设置之前"缓存的旧帧（LIN 关键字天然支持
这个机制，别浪费）；③睡眠状态会跨用例残留，`Test Setup` 必须显式唤醒 + 清缓存（脚本里
`恢复 LIN 总线到清醒状态`）。

## 19.15 场景 14：DoIP 远程诊断

**业务背景**：4S 店远程诊断 / OTA 升级前，诊断服务器先通过**车载以太网**做一轮健康检查：
识别车辆（VIN）→ 激活诊断路由 → 读故障码确认可升级 → 必要时清码 → 断线重连继续。
链路：`Tester ⇄ DoIP 网关(13400) ⇄ 虚拟 CAN ⇄ ECU`——**UDS 服务完全不变，只是运输层从
CAN/ISO-TP 换成以太网**。脚本：`scenarios/14_doip_remote_diag.robot`（**6 条用例，连跑两次 6/6 全绿**）。

**6 条用例覆盖什么**：

| 用例 | 验证点 |
|---|---|
| 远程健康检查应能识别车辆（VIN + 逻辑地址） | UDP 车辆识别 0x0001→0x0004（REQ-DOIP-001） |
| 路由激活后经诊断通道读 VIN 应与车辆识别一致 | 激活 0x0005→0x0006 code=0x10 + 透传读 VIN（REQ-DOIP-002/003） |
| OTA 前健康检查：默认工况应无故障码 | `19 01` 数量=0，作为"能否升级"门禁（REQ-DOIP-003） |
| 清码后健康检查应重新通过（数量归零） | `14 FF FF FF` 后回读 0（写了 ≠ 生效）（REQ-DOIP-003） |
| 断开重连后必须重新路由激活才能继续诊断 | 路由激活状态按 TCP 连接有效（REQ-DOIP-005） |
| 未路由激活时发诊断应被 NACK 0x06（负向） | 安全边界：未授权连接不能直接诊断（REQ-DOIP-004） |

**关键代码**（"远程健康检查"的门禁逻辑）：

```robotframework
OTA 前健康检查：默认工况应无故障码
    DoIP Connect
    ${code}=    DoIP Routing Activation          # 0x10 = 激活成功
    Should Be Equal As Integers    ${code}    0x10
    DoIP Send Diagnostic    19 01                # DoIP 0x8001 承载 UDS
    ${ack}=    DoIP Read ACK                     # 0x8002 肯定确认
    ${resp}=    DoIP Read Response               # 透传回来的 UDS 响应
    Should Start With    ${resp}    5901ff
    ${count}=    Evaluate    int('${resp}'[-2:], 16)
    Should Be Equal As Integers    ${count}    0
```

**为什么这样测**：远程诊断的价值在"不上车也能判断车况"，所以①必须先证明"连的是同一台车"
（车辆识别 VIN == 诊断通道读到的 VIN）；②健康检查用"读 DTC 数量"而不是"看那几条码"，
因为 OTA 门禁只关心"有没有码"；③**路由激活是安全边界**：未激活直接发诊断必须被拒
（NACK 0x06），否则任何能连 13400 端口的人都能做诊断。

**踩坑**：①网关的诊断透传依赖 ECU 在线，所以 `Suite Setup` 必须先
`Start Vehicle Environment`、再 `Start DoIP Gateway`，`Suite Teardown` **逆序**回收；
②路由激活状态是"按连接"的，每个用例用 `Test Teardown    DoIP Disconnect` 隔离，重连后
必须重新激活（不要以为"连上就能诊断"）；③`DoIP Read ACK` 和 `DoIP Read Response` 是
两条独立报文，顺序不能反。

## 19.16 场景 15：HMI 视觉回归

**业务背景**：座舱仪表是用户每天看的安全显示界面。功能测试断言 JSON 状态正确，但
"布局错位、指针卡死、警告灯没画出来、配色变灰"这类缺陷**只有像素级断言能发现**。
真实做法：维护基准图（golden），发版前跑视觉回归，失败自动留差异图给 UI/开发定位。
脚本：`scenarios/15_vision_regression.robot`（**6 条用例，连跑两次 6/6 全绿**）。
本场景**不启动任何子进程**（纯离屏渲染 + 纯像素比对，秒级、稳定、跨机器可复现）。

**6 条用例覆盖什么**：

| 用例 | 验证点 |
|---|---|
| 发布前默认首页画面应与基线一致 | 整图 golden 比对，容差 2%（REQ-VIS-001） |
| 车速变化时指针角度应符合刻度换算 | 60→67.5°、120→135°、240→270°，容差 ±2°（REQ-VIS-002） |
| 水温报警灯点亮时对应区域应识别为 lit | 整图报警基线 + 区域红色占比 ≥25%（REQ-VIS-003） |
| 同一区域灯灭时应识别为 off（亮灭成对） | 负向：同场景灯灭，占比 ≤5%（REQ-VIS-003） |
| 画面变化必须能被差分检出（mutation） | 故意改车速 240 → 差分 ≥2% 且与基线比对**必须失败**（REQ-VIS-004） |
| 比对失败时应留下差异图证据 | `diff_speed240.png` 存在且红色高亮像素 >1000（REQ-VIS-004） |

**关键代码**（"指针角度"与"证明比对有杀伤力"）：

```robotframework
车速变化时指针角度应符合刻度换算
    ${png60}=    Render Cluster State    ${{ {"speed": 60} }}    ${OUT}/speed_60.png
    Needle Angle Should Be Near    ${png60}    67.5    tolerance=2.0

画面变化必须能被差分检出（mutation，证明比对不是恒真）
    ${mutated}=    Render Cluster State    ${{ {"speed": 240} }}    ${OUT}/mutation_speed240.png
    Images Should Differ    ${mutated}    ${BASELINE}    min_ratio=0.02
    Run Keyword And Expect Error    *整图与黄金图不一致*
    ...    Compare With Golden    ${mutated}    ${GOLDEN_DEFAULT}
```

**为什么这样测**：视觉测试最大的坑是**"比对恒真"**（差分算法写错/容差 1.0，全绿但什么
都没验证）——所以必须有一条 mutation 用例证明"该失败时真会失败"。另外"灯亮"用例必须和
"灯灭"用例成对，否则一个"永远返回 lit"的识别 bug 也会通过。

**踩坑**：①**golden 是测试资产**：更新基准图要走 review（`Update Golden` 关键字只给
"确认过 UI 变更"时用），否则"改坏了直接重录基线"= 视觉回归形同虚设；②跨平台抗锯齿有
亚像素差异，所以整图断言是"≤2% 容差"而不是逐位相等；③区域坐标来自渲染器的
`TELLTALE_REGIONS`（库与画面共用一份几何常量），不要手写坐标；④纯离屏渲染让本场景
不依赖总线/子进程，适合放进发版门禁每次跑。

## 19.17 场景 16：版本性能基线

**业务背景**：System Validation 发版前要回答四个问题：诊断**多快**（P2 一致性）？总线
还剩**多少带宽**？周期报文**多稳**？连续压/长时间跑**会不会挂**？本场景用真实测量
（`time.monotonic` 计时 + 真实收帧）建立可对比的性能基线。脚本：
`scenarios/16_perf_baseline.robot`（**6 条用例，连跑两次 6/6 全绿**，单次约 20~30s）。

**6 条用例覆盖什么**：

| 用例 | 验证点 |
|---|---|
| 诊断响应时间应满足声明的 P2（多点采样 p95） | 采样 9 次取 p95 < 50ms（REQ-PERF-001） |
| 默认工况总线负载率应低于 30% | 真实收帧估算 500kbps 负载（REQ-PERF-002） |
| 车速报文周期应为 100ms 且抖动受控 | 0x100 均值 ±15ms、标准差/最大间隔受控（REQ-PERF-004） |
| 突发压力：连续 200 条 TesterPresent 应 100% 成功且吞吐达标 | 成功率 100% + 吞吐 ≥50 条/s（REQ-PERF-003） |
| 压力测试后 ECU 应仍在线（诊断链路未被打挂） | 压力后 3E 00 仍正常响应（REQ-PERF-003） |
| 发布前短长稳：10s soak 应无丢帧、无诊断超时（并输出基线） | soak 10s + 基线汇总（REQ-PERF-004） |

**关键代码**（非功能测试的核心是"多点采样 + 看长尾"）：

```robotframework
诊断响应时间应满足声明的 P2（多点采样 p95）
    ${samples}=    Measure UDS Response Time    3E 00    samples=9
    ${stats}=    Response Time Stats    ${samples}
    Response Time P95 Should Be Below    ${stats}    ${P2_MS}

突发压力：连续 200 条 TesterPresent 应 100% 成功且吞吐达标
    ${burst}=    Send UDS Requests In Burst    200
    Should Be Equal As Integers    ${burst}[success]    200
    Throughput Should Be Above    ${burst}    50
```

**为什么这样测**：①**p95 而不是平均值**——平均值 2ms 但偶尔 80ms 的 ECU，在实车上表现
就是"诊断仪偶发超时"，单次测量会漏掉长尾；②总线负载是**带宽余量**指标（超过 30% 后低
优先级报文延迟抖动急剧变大）；③压力测试的价值一半在"压完还能不能干活"（队列卡死/线程
静默退出这类缺陷只在压力后显现）；④**基线只记录、不硬编码成断言**——否则换机器就是假失败。

**踩坑**：①阈值必须按"实测值 + 足够余量"定（本项目实测 p95≈2ms、负载≈0.5%、周期≈104ms），
否则 CI 慢机器必 flaky；②PerfLibrary 用**两条独立虚拟总线**（sniffer 只看不摸、diag 专做
诊断），复用一条会和诊断收包线程抢帧，负载永远测不到；③`Suite Teardown` 先
`Close Perf Library` 释放总线，再 `Stop Vehicle Environment`，顺序反了会报
"UdpMulticastBus was not properly shut down"；④soak 时长要可控（发布门禁用 10s 版本，
真实台架通常跑数小时）。

## 19.18 从这十六个场景提炼的写法清单

| 场景 | 可复用的写法 |
|---|---|
| 1、8 | 断言分三层：存在 → 范围 → **联动/周期** |
| 2、4 | 遍历式断言（精确指出是哪一个不满足） |
| 3 | **矩阵式覆盖**（用表格确认没漏象限） |
| 3、7 | 写操作后**回读**；用 **Teardown** 做用例隔离 |
| 5 | 时序需求验**变化**；用 NRC 差异作为状态证据 |
| 6 | 域隔离验证（A 域操作不该影响 B 域指标） |
| 7 | 失败路径 + **恢复性验证**（失败后能重来） |
| 8 | Setup 造场景 + 周期/抖动分析 + Trace 归档 |
| 9 | 时序测试**多点采样**取最差 |
| 10 | **Tag 分层**：冒烟 / 负向 / 长时分开 |
| 11 | **故障注入 + Teardown 清激励**；异常工况下断言正常行为 |
| 12 | 电源/NM：先造工况（0x600）→ 录制验证"总线零帧" → 唤醒/恢复 |
| 13 | 主从总线：**marker 防旧帧**；枚举信号按名断言；睡眠状态用 Test Setup 唤醒复位 |
| 14 | 运输层可换、UDS 不变；**路由激活=安全边界**；子进程逆序清理 |
| 15 | golden 回归 + **mutation 证明断言有杀伤力**；差异图=失败证据 |
| 16 | 非功能四问：p95/负载/抖动/长稳；**基线只记录不硬编码** |

**四条最值钱的经验**（都在这 16 个场景里踩出来的）：

1. **跨系统比较前先等稳态**（场景 10）—— 动态值采样时刻不同会对不上
2. **同一份清单在多处实现必然不同步**（场景 2 的灯清单漏项）—— 遍历断言能抓出来
3. **用例隔离不做，失败只在连续跑时出现**（场景 7 的 flash_state、场景 11 的注入激励、场景 12 的电源模式都是同一类问题）—— 最难查的类型
4. **异常工况要断言"正常行为"**（场景 11/12）—— 不是只看"没崩"，而是验证降级/保持/恢复是否符合需求

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | 范围断言只能发现"值超界"；**联动断言能发现模型/参数错误**。例：转速系数写成 ×60（而非 ×80）时，转速仍在 0~8000 范围内 → 范围断言永远绿，联动断言立刻检出 |
| 2 | 两个维度：**会话**（默认/扩展/编程）× **安全访问**（未解锁/已解锁）。"复位后权限应失效"必测，因为**权限残留是安全隐患**（退出诊断后别人能直接接着写） |
| 3 | 要证明"**会变化**"而不是"当前状态"。证据 = 能区分两种情况的信号：**回退后报 0x7F**（会话不支持）vs 未回退报 0x33（权限不足） |
| 4 | 因为刷写状态（`flash_state`）会残留 → 下一个 0x34 撞 NRC 0x24。不隔离的现象：**单独跑能过、连续跑才挂**（最难查的一类失败） |
| 5 | "周期均值正常但个别帧晚了几十毫秒" → 接收方可能超时。测法：`Period And Jitter Should Be Within`（算最大间隔 − 最小间隔） |
| 6 | 因为时序问题往往是"**偶尔慢**"，单次测量会漏掉（真实发现过"第 3 次响应慢 80ms"的缺陷） |
| 7 | 因为车速还在爬升时，两次读取的**采样时刻不同** → 两个动态值必然对不上（场景 10 实测 50.25 vs 60.0）。要先等进入稳态（58~62）再比较 |
| 8 | 三条链路：**信号链**（ECU→总线→仪表）、**诊断链**（会话→读→写+权限）、**故障链**（注入→DTC→灯）。单独维护是因为全量 276 用例要 6 分钟，而改代码后需要在 30 秒内知道"主要功能没坏" |
| 9 | 激励（9V/16V/停发/丢帧）是**全局状态**，不清理会污染后续用例与套件，典型现象是"单独跑能过、全量跑才挂"；对应场景 11 的 `Test Teardown    清除测试激励并复位` |
| 10 | 因为"总线静默"才是睡眠的可观测证据（暗电流的根因是节点还在发帧）；读状态位可能只是 ECU 自己声明的"我想睡"，不代表真的停发。等价于场景 12 的"录 3 秒，`Recorded Frame Count` 必须为 0" |
| 11 | 因为 LIN **从机不许主动说话**，只有主机轮询到才应答；CAN 的"谁都能广播"模拟不了主从调度。本项目用独立进程 `lin_sim.py`（主节点按 10ms 槽位调度表发帧）+ `LinLibrary`（UDP 30001 帧流 / TCP 30002 控制口）实现测试端观察与驱动 |
| 12 | **完全一样**（10/22/19/14/3E…），只是运输层从 CAN/ISO-TP 换成 DoIP/TCP。路由激活（0x0005→0x0006，code=0x10）让网关确认"这条 TCP 连接代表哪个 tester 地址"，是安全边界：未激活发诊断必须被 NACK 0x06 拒绝 |
| 13 | 最大风险是**"比对恒真"**（差分算法/容差写错，所有用例全绿但什么都没验证）。mutation 用例故意制造大变化，要求"与基线比对**必须失败**"——证明断言有杀伤力；再配合"灯亮/灯灭成对"防"永远返回 lit"的识别 bug |
| 14 | 它们回答不同问题：**p95** 看长尾（平均值掩盖偶发慢响应，实车表现=诊断仪偶发超时）；**负载/抖动**看实时性与带宽余量；**长稳**看时间维度（10s 不丢帧不代表 2 小时不丢）。只看一个指标会漏掉"功能对但不可交付"的缺陷 |
