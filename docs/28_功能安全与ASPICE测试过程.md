## 28.1 为什么测试工程师也要懂功能安全和 ASPICE

两个真实场景：

**场景 A（面试/评审）**
> 主管："这个诊断功能，你怎么证明它达到了安全目标？"
> 新手："我测了，用例都过了。"
> 主管：（沉默）—— 因为"用例过了"不能证明"安全机制有效"，也不能证明"测试过程可信"。

**场景 B（入职第一周）**
> 开发提了 bug 单，你修完验证通过，回复"已验证"。
> 质量经理问："需求 ID 是多少？证据在哪？回归范围？"你答不上来 —— 这份工作不是"跑测试"，而是**产出可审计的证据链**。

**一句话理解**：
- **功能安全（ISO 26262）** 回答："**系统坏掉也不能伤人** —— 你怎么证明？"
- **ASPICE** 回答："**你的开发和测试过程靠谱吗** —— 客户/审核方怎么相信？"

两者都不是"写代码"，而是"**用证据说话**"。测试是这两套体系里证据的主要生产者。

## 28.2 ISO 26262 速览（测试视角，够用版）

### 28.2.1 核心链条：危害 → 安全目标 → 安全需求 → 安全机制 → 验证

```
危害事件（车辆层面）             例：仪表突然黑屏，驾驶员看不到车速
      │ 风险分析 HARA
      ▼
安全目标（Safety Goal）          "仪表不得在行驶中黑屏"（ASIL 由 S/E/C 评出）
      │
      ▼
功能安全需求 FSR                 "显示链应检测黑屏并进入备份显示模式"
      │
      ▼
技术安全需求 TSR                 "看门狗应在 100ms 内检测到渲染阻塞并重启显示任务"
      │
      ▼
安全机制（Safety Mechanism）     看门狗、双核锁步、CRC/E2E 保护、范围检查、降级
      │
      ▼
测试/验证（你要做的）            证明机制有效 + 故障注入后能进入安全状态
```

### 28.2.2 ASIL：风险的等级（A 最低，D 最高，QM=不按 26262 管）

| 等级 | 典型要求（对测试的影响） |
|---|---|
| **QM** | 常规质量流程即可（很多座舱功能） |
| **A** | 基本测试覆盖 + 证据 |
| **B** | + 故障注入、边界/异常测试要求提高 |
| **C** | + 安全机制验证、独立性要求、工具确认 |
| **D** | 最严：单元级覆盖率（语句/分支/MC/DC）、形式化方法、双人评审 |

> 测试视角记忆法：**ASIL 越高，越要求"测异常/测故障/测安全机制"，而不是多跑几条正常用例。**

### 28.2.3 安全机制：功能安全测试的主要对象

| 机制 | 干什么 | 怎么测（本项目的影子） |
|---|---|---|
| 看门狗（Watchdog） | 程序跑飞/卡死时复位 | 注入卡死 → 断言复位/恢复；本项目可加"ECU 主循环卡死"仿真 |
| 双核锁步 / 内存保护 | 检测 CPU/内存错误 | 安全机制自检结果读取（诊断 DID） |
| E2E 保护（End-to-End） | 报文 CRC + 计数器，防丢帧/乱序/篡改 | 本项目 CAN 帧可加 CRC/counter 并注入错误帧 |
| 范围/合理性检查 | 信号超范围时降级 | `scenarios/11` 信号丢失/电压异常用例 |
| 降级/安全状态 | 故障时进入受限但安全的状态 | 仪表信号丢失 → 显示"--"（`scenarios/11`） |
| 诊断自检（0x31 例程） | 灯测/自检/内存校验 | `scenarios/02` 灯测试例程、DID 自检 |

> **关键认知**：功能安全测试 ≠ 功能测试。功能测试问"功能对吗"；功能安全测试问"**坏了以后对吗**"。
> 同一个"车速显示"：功能测试看 60km/h 显示 60；功能安全测试看"总线断了、信号错了、程序卡了，仪表有没有进入安全状态并报告"。

## 28.3 功能安全测试怎么做（可落地的四类活动）

### ① 安全机制验证（Safety Mechanism Verification）
逐条验证每个安全机制**能检测、能反应、能恢复到安全状态**：
- 能检测：注入故障（CRC 错、超时、超范围）→ 机制报告故障；
- 能反应：系统进入降级/安全状态（如显示"--"、报警灯亮、限速）；
- 能恢复：故障消失后能恢复正常（或按设计保持锁定）。

### ② 故障注入测试（Fault Injection Test）
这是功能安全测试的"主力手段"，本项目的 `scenarios/11` 就是它的入门版：
- 信号级：丢帧/超范围/信号丢失；
- 报文级：CRC 错/计数器跳变/长度错；
- 电源级：欠压/过压/掉电；
- 软件级：卡死/内存越界/任务超时（需要激励接口，本项目可用工程 DID 扩展）。

### ③ 覆盖率与独立性
- 单元级（ASIL C/D）：语句/分支/MC/DC 覆盖率（工具：VectorCAST、gcov、Cantata）；
- 集成/系统级：需求覆盖率、接口覆盖率、异常场景覆盖率；
- **独立性**：安全机制不能自己证明自己（看门狗的测试不能依赖被测的看门狗）—— 测试工具/人员要独立。

### ④ 证据链
每个安全机制的验证都要留下：**需求 ID → 测试用例 → 执行结果 → 缺陷单 → 回归记录**。
这就是为什么本项目要做 `requirements.yaml` + `trace_matrix.py` + `deliverables/` —— 它们是"证据链"的雏形。

## 28.4 ASPICE 速览（汽车软件过程评估）

ASPICE（Automotive SPICE）是**客户审核供应商开发流程**的标准。它不看"你有多聪明"，看"**过程是否可重复、可追溯、可改进**"。

### 28.4.1 与测试最相关的过程域

| 过程域 | 名字 | 测试角色做什么 |
|---|---|---|
| **SYS.4** | 系统集成测试 | 集成多个 ECU/子系统，验证接口与交互 |
| **SYS.5** | 系统合格性测试 | 对照系统需求做验收，出系统测试报告 |
| **SWE.4** | 软件单元验证 | 单元测试/静态分析（通常开发做，测试评审） |
| **SWE.5** | 软件集成测试 | 软件模块间接口测试 |
| **SWE.6** | 软件合格性测试 | 对照软件需求做验收 |
| **SUP.1** | 质量保证 | 检查过程是否按计划执行（审你） |
| **SUP.8** | 配置管理 | 版本/基线管理（你提交的代码、用例、报告都要可追溯） |
| **SUP.10** | 变更管理 | 需求变→影响分析→测试更新→回归 |

### 28.4.2 ASPICE 能力等级（看测试成熟度）
- **Level 1 已执行**：测试做了，但靠人、不稳定；
- **Level 2 已管理**：有计划、有标准、有跟踪（**多数 Tier1 要求至少 L2**）；
- **Level 3 已建立**：组织级标准过程 + 裁剪（大厂常见目标）；
- L4/L5：量化管理与持续优化（少数头部）。

### 28.4.3 测试过程要留的证据（"审计看什么"）

| ASPICE 要求 | 项目里对应的东西（模板/工具） |
|---|---|
| 需求可追溯 | `requirements/requirements.yaml` + `[Tags] REQ-xxx` + `trace_matrix.py` |
| 测试规范 | `deliverables/test_spec_ic_alarm.yaml`（测试项/步骤/预期结果） |
| 测试计划 | （本项目缺失，见 28.6 模板要素） |
| 测试环境 | `simulators/` 全量仿真 + `run_tests.py`（环境即代码） |
| 执行结果 | `results/output.xml` / `log.html` / `report.html` |
| 测试报告 | `results/test_summary.html`（`generate_report.py`） |
| 覆盖率 | `results/coverage.html` + RTM |
| 缺陷管理 | `deliverables/defect_report_template.md` + 回归记录 |
| 变更影响分析 | （本项目缺失，见 28.6） |

## 28.5 把本项目映射到 ASPICE/安全证据链（重点表）

> **这张表就是你向主管/面试官证明"我懂流程"的话术**：左边是标准要什么，右边是我项目里有什么。

| 标准要求 | 本项目产物 | 对应章节 | 差距（怎么补） |
|---|---|---|---|
| 需求规格 | `requirements.yaml` 86 条（含来源/优先级/验证方法） | 20 章 | 真实项目要 SRS 全文/评审记录 |
| 需求↔用例追溯 | `trace_matrix.py` → 100% 关联 | 13/20 章 | 真实项目要双向追溯 + 变更影响 |
| 测试规范 | `test_spec_ic_alarm.yaml` 7 个测试项 | 20 章 | 覆盖全部需求而不是一个功能 |
| 测试执行记录 | `output.xml`/`log.html`（RF 原生） | 05/13 章 | 真实项目要签名/基线 |
| 测试报告 | `test_summary.html`（通过率/覆盖率/失败明细） | 13 章 | 真实项目要评审签字 |
| 缺陷管理 | `defect_report_template.md`（含关联需求/复现步骤/证据） | 20 章 | 真实项目接 JIRA |
| 回归管理 | 冒烟集（`scenarios/10`）+ CI 每次全量 | 13/19 章 | 真实项目要分层回归策略 |
| 配置管理 | Git + CI 归档 artifact | GIT_GUIDE/13 章 | 真实项目要基线/版本矩阵 |
| 安全机制验证 | `scenarios/11` 故障注入 + 降级断言 | 19 章 | 需补 E2E/看门狗类机制 |
| 功能安全证据 | `KNOWN_ISSUES.md` 主动披露 + DTC 安全策略 | 04/20 章 | 需补 FMEA/HARA 输入 |

> 💡 **面试话术**："我不只跑用例，我按 ASPICE 的证据链组织工作：需求可追溯、规范可评审、执行有记录、缺陷有闭环。
> 我这个学习项目里用 requirements.yaml + trace_matrix + deliverables 做了最小可验证闭环。"

## 28.6 测试策略 / 测试计划怎么写（模板要素）

> 真实项目里这份文档常由测试负责人写，新人至少要知道它由什么组成。

**测试策略（Test Strategy）——回答"整体怎么测"**
1. 范围：测什么/不测什么（含边界声明）；
2. 测试层次：单元/集成/系统/HIL/实车 各覆盖什么；
3. 测试类型：功能/性能/诊断/刷写/故障注入/网络/信息安全；
4. 环境与工具：台架/HIL/仿真/真实工具；
5. 进入/退出准则（Entry/Exit Criteria）：什么时候开始、什么条件算完成；
6. 风险与应对：高风险功能优先、资源不足怎么砍（**明确写"不测什么"**）。

**测试计划（Test Plan）——回答"具体什么时候谁做什么"**
| 要素 | 示例 |
|---|---|
| 测试项清单 | 按需求 ID 列出 |
| 用例设计 | 边界值/等价类/负向/组合 |
| 排期 | 按里程碑（D1~D6 相对日，不写死绝对日期） |
| 资源 | 人、台架、HIL、真机 |
| 度量 | 执行率、通过率、需求覆盖率、缺陷密度/遗留缺陷 |
| 变更管理 | 需求变更→影响分析→用例更新→回归范围 |

**本项目缺的**：正式《测试计划》和《变更影响分析记录》——可以作为你的下一步练习（见 `KNOWN_ISSUES.md`）。

## 28.7 ISO 26262 / ISO 21434 / SOTIF 三者关系（一句话版）

| 标准 | 管什么 | 一句话 |
|---|---|---|
| **ISO 26262**（功能安全） | 系统故障导致的风险 | "**坏了不能伤人**" |
| **ISO 21434**（网络安全） | 被攻击导致的风险 | "**被黑不能伤人**" |
| **ISO 21434 配套 UN R155/R156** | 车企网络安全管理体系/软件升级 | 法规强制，出口欧盟必查 |
| **ISO 21448 SOTIF**（预期功能安全） | 功能正常但设计不足导致的风险 | "**没坏、没被黑，但场景超出设计，也可能出事**"（如 AEB 误识别） |

> 测试视角：三者最终都落到"**故障/攻击/边界场景的注入 + 安全状态验证 + 证据链**"，
> 手段相似、输入不同。先把本项目的故障注入、模糊测试吃透，再学标准会很快。

## 28.8 本章自检

1. 用一句话向非汽车行业的人解释"功能安全和信息安全有什么区别"。
2. 给出一个仪表 HMI 场景：它的 ASIL 可能是什么级别？为什么？需要验证哪些安全机制？
3. ASPICE 的 SYS.5 和 SWE.6 分别测什么？对应本项目哪个层级？
4. 假设需求从"水温 >120℃ 报警"改成">110℃ 报警"，按 ASPICE 变更管理列出你要做的 4 件事。
5. 为什么"看门狗的测试不能依赖被测的看门狗"？（提示：独立性）

> 📋 **自查要点**
> 1. 功能安全=防系统故障伤人（26262）；信息安全=防被攻击（21434）；SOTIF=防设计不足/场景超界。
> 2. 仪表黑屏大概率 ASIL A/B（不同 OEM 不同）；需验证：渲染监控、看门狗、备份显示、故障告警、降级策略。
> 3. SYS.5=系统级对照系统需求验收（整车/域级）；SWE.6=软件级对照软件需求验收（单个 ECU 软件）；本项目 `tests/robot` 更接近 SWE.6/软件级，`scenarios` 偏 SYS.4/5 的跨系统交互。
> 4. ①需求变更评审/影响分析 ②更新测试规范与用例 ③更新追溯矩阵 ④回归测试并记录（+配置基线更新）。
> 5. 因为看门狗可能本身失效/被绕过；安全机制需要独立的验证手段（外部激励/独立观测）。
