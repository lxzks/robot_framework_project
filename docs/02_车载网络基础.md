## 2.1 为什么车内通信要用 CAN，而不是USB/WiFi

1986 年博世发明 CAN 时，车内布线是噩梦：每个功能一根专线，一辆豪华车电线重量超过 100 kg。CAN 的设计目标：

| 需求 | CAN 的答案 |
|---|---|
| 省线 | **两根线（CAN_H/CAN_L）串起全车**，所有 ECU 挂同一根总线 |
| 可靠 | 差分信号抗干扰；硬件级错误检测（CRC/ACK/位监测）；故障自动关闭 |
| 实时 | 非破坏性位仲裁，高优先级报文"零延迟"抢占总线 |
| 便宜 | 一个 CAN 控制器几十块钱，协议由硬件实现，CPU 零负担 |

**CAN 不是最快的**（最快是车载以太网 100Mbps+），但它是**最皮实、最便宜、最成熟**的——安全相关（发动机、制动、气囊）至今几乎全用 CAN/CAN-FD。娱乐系统才用以太网。

## 2.2 物理层：两根线发生了什么

### 2.2.1 差分信号

CAN 用一对双绞线：`CAN_H` 和 `CAN_L`。传输的是两根线的**电压差**：

```
显性位 (Dominant, 逻辑 0):  CAN_H = 3.5V, CAN_L = 1.5V  → 差 = 2V
隐性位 (Recessive, 逻辑 1): CAN_H = 2.5V, CAN_L = 2.5V  → 差 = 0V
```

**为什么用差分？** 车内电机、点火线圈产生巨大电磁干扰。干扰同时加到两根线上，收端看"差值"就抵消了。这也是为什么要用**双绞线**——把干扰均匀分享给两根线。

### 2.2.2 终端电阻：120Ω 的秘密

如果你摸过 CAN 线束，会在线束两端各发现一个 **120Ω 电阻**：

```
  ECU-A ────┐                        ┌──── ECU-Z
            │                        │
           [120Ω]                  [120Ω]     ← 总线两端各一个
            │══════ CAN 总线 ════════│
```

作用：**防信号反射**。高速信号传到线缆末端会像回声一样反射回来，和原信号叠加导致错乱。让线的"特征阻抗"（双绞线约 120Ω）和两端电阻匹配，反射就消失了。

- 总线只有两端有 120Ω → 总电阻 = 120 ∥ 120 = **60Ω**
- 万用表测总线电阻：**60Ω 左右正常**；120Ω 说明少了一个终端电阻；0Ω 短路了。这是最基础的台架排故技能。

### 2.2.3 位速率

经典 CAN 常用 **500 kbps**（动力域/底盘域主流）和 250 kbps（车身域）。一帧 108 bit 的标准帧，500kbps 下传完约 **0.22 ms**。

## 2.3 数据链路层：一帧报文长什么样

### 2.3.1 标准帧结构（11 位 ID）

```
                  一帧标准 CAN 报文 (Standard Frame)
 ┌─────┬─────┬─────┬──────────┬─────┬──────┬─────┬─────┬─────┬─────┐
 │ SOF │仲裁段│控制段│  数据段  │ CRC │ ACK  │ EOF │ IFS │ 合计│
 │ 1bit│12bit│ 6bit│ 0~8 字节 │16bit│ 2bit │7bit │3bit │     │
 └─────┴─────┴─────┴──────────┴─────┴──────┴─────┴─────┴─────┴─────┘
```

逐个字段：

| 字段 | 位数 | 作用 | 测试要知道的 |
|---|---|---|---|
| SOF | 1 | 帧起始（一个显性位，同步用） | — |
| **仲裁段** | 11(标准)/29(扩展) | **报文 ID，决定优先级** | 抓包第一眼就看它 |
| 控制段 | 6 | 含 DLC（4 bit 数据长度） | DLC=8 不代表 8 字节都有意义 |
| **数据段** | 0~8 字节 | 载荷（经典 CAN 最多 8 字节；CAN FD 最长 64 字节） | 信号都在这里 |
| CRC | 15+1 | 校验，硬件算 | 错误帧的锅经常是它 |
| ACK | 2 | 至少一个节点正确收到才置位 | 总线上"只有诊断仪"时发不出去 |
| EOF | 7 | 帧结束 | — |

### 2.3.2 位仲裁：高优先级如何"零延迟"抢占总线

**这是 CAN 最精妙的设计**，面试高频。

场景：节点 A 发 ID `0x100`，节点 B 同时发 ID `0x200`，谁让谁？

规则：
1. 显性位（0）**覆盖**隐性位（1）——就像一群人喊话，嗓门大的（显性）压过嗓门小的（隐性）；
2. 每个节点一边发一边**回听**总线，发现自己发的 1 被总线覆盖成 0，说明有更高优先级的报文在发 → **立即闭嘴，退出去等**；
3. 显性多的 ID（数值小）优先级高。

**数字演算**：

```
ID 0x100 = 0001 0000 0000
ID 0x200 = 0010 0000 0000
             ↑ 第 10 位开始不同：0x100 发 0，0x200 发 1
```

- 第 10 位：A 发显性(0)，B 发隐性(1) → 总线是 0 → B 回听到"我发 1 但总线是 0" → **B 退出发送**；
- A 完全不知情，继续把帧发完 → 约 0.22 ms 后总线空闲，B 自动重发。

**结论：高优先级报文最多被延迟"一帧的时间"，这就是 CAN 的"实时性"。** 0x100（车速，100ms 周期）永远打得过 0x700（座椅加热，1s 周期）。

### 2.3.3 错误帧与总线关闭

CAN 硬件自动监测 5 类错误（位错误、填充错误、CRC、ACK、格式错误）。发错 8 次重复错误后节点 **bus-off**（自动下线防干扰总线）。测试中遇到"某个 ECU 突然不发报文了"，查 bus-off 是常规动作。

## 2.4 DBC 文件：测试工程师的字典

**DBC（Database CAN）是描述"哪个报文的哪个 bit 是什么信号"的文本文件。** 没有它，抓包看到的只是 `c4 09 80 0c...` 这种天书。

### 2.4.1 DBC 三要素

以本项目的 `vehicle.dbc` 为例（`simulators/dbc/vehicle.dbc`）：

```
BO_ 256 EngineData: 8 ECU
 SG_ VehicleSpeed : 0|16@1+ (0.01,0) [0|655.35] "km/h" CLUSTER,TESTER
```

拆解：

| 部分 | 含义 |
|---|---|
| `BO_ 256 EngineData: 8 ECU` | 报文：ID=256(0x100)，名 EngineData，长 8 字节，发送者 ECU |
| `SG_ VehicleSpeed` | 信号名：车速 |
| `0\|16` | 起始 bit 0，长度 16 bit |
| `@1` | **字节序：1=Intel 小端（低位在前），0=Motorola 大端**。车载 DBC 两种都常见（欧系 OEM 常用 Motorola，J1939 用 Intel）；**本项目 `vehicle.dbc` 全部是 `@1+`（Intel）** |
| `+` | 有无符号 |
| `(0.01,0)` | **缩放：物理值 = 原始值 × 0.01 + 0** |
| `[0\|655.35]` | 物理值范围 |
| `"km/h"` | 单位 |

### 2.4.2 手算一次：`c4 09 80 0c 82 33 00 00` 是什么

拿本项目 DBC 定义算：

| 信号 | bit 位置 | 字节 | 十六进制 | 原始值(十进制) | 物理值 |
|---|---|---|---|---|---|
| VehicleSpeed | 0~15 | 0,1 | `c4 09` | 0x09c4=**2500** | 2500×0.01=**25.00 km/h** |
| EngineSpeed | 16~31 | 2,3 | `80 0c` | 0x0c80=**3200** | 3200×0.25=**800 rpm** |
| CoolantTemp | 32~39 | 4 | `82` | **130** | 130×1−40=**90℃** |
| ThrottlePosition | 40~47 | 5 | `33` | **51** | 51×0.392=**20%** |

**验证方法**（你可以现在就试）：

```python
import cantools
db = cantools.database.load_file("simulators/dbc/vehicle.dbc")
db.decode_message(0x100, bytes.fromhex("c409800c82330000"))
# {'VehicleSpeed': 25.0, 'EngineSpeed': 800.0, 'CoolantTemp': 90, 'ThrottlePosition': 20.0}
```

Intel 小端的手算要点：bit 0 是**字节 0 的最低位（LSB）**。16 位信号占字节 0-1 时，字节 0 是低 8 位：`c4` 是低位、`09` 是高位 → 0x09c4。**顺序是反的，这是新人最常犯的错。**

### 2.4.3 值表（VAL_）：枚举信号

档位这种离散值用值表：

```
VAL_ 512 GearPosition 0 "P" 1 "R" 2 "N" 3 "D" 4 "S" 5 "L" ;
```

原始值 3 显示为 "D"。

### 2.4.4 cantools 的著名大坑：NamedSignalValue

用 cantools 解码带 `VAL_` 的信号，拿到的**不是普通 int**，而是 `NamedSignalValue` 对象（打印出来像 `GearPosition.D`）。它在某些 cantools 版本里**不可哈希、不能 int()**——本项目开发时就栽在这里：

```python
decoded = db.decode_message("ClusterData", data)
gear = decoded["GearPosition"]      # NamedSignalValue！
GEAR_NAMES.get(gear)                # TypeError: unhashable type!（真机上踩过的坑）
int(gear)                           # 某些版本也报错
```

**正解**：`decode_message(..., decode_choices=False)` —— 让枚举信号直接返回原始数值。本项目所有 decode 调用都带这个参数。**这个坑值得记住，面试可以当"踩坑经验"讲。**

## 2.5 其它车载网络速览（面试会被问）

| 网络 | 速率 | 拓扑 | 用在哪 | 关键点 |
|---|---|---|---|---|
| **CAN** | 500k/250k | 总线 | 动力/底盘/车身控制 | 位仲裁、8字节、便宜可靠 |
| **CAN-FD** | 5M+ | 总线 | 新架构主干 | 数据段最长 64 字节、可变速率；兼容经典 CAN 帧 |
| **LIN** | 20k | 单主多从 | 车门/座椅/雨刮/天窗 | **单线**、主从调度（从机不许主动说）、极便宜 |
| **FlexRay** | 10M | 星型/总线 | 老一代线控底盘/转向 | 时间触发、冗余；正被以太网淘汰 |
| **车载以太网** | 100M~1G | 交换式 | 域控主干、ADAS 传感器、DoIP | 需要交换机；支持 TCP/IP 协议栈 |
| **DoIP** | 基于以太网 | — | **远程诊断**（Diagnostics over IP） | 4S 店远程刷写就走它；UDS over Ethernet |

**和测试的关系**：你做系统验证，抓包工具（CANoe）同时支持这些网络；诊断从 DoIP 走时，UDS 报文被封装在 TCP 里，但**服务号/NRC/会话逻辑完全一样**——协议是通用的，只是"运输层"换了。

## 2.6 动手：读懂本项目的总线

启动 ECU 模拟器，用诊断仪的视角观察总线（或者直接跑 01 套件），然后回答：

1. `0x100` 多少毫秒发一次？`0x200` 呢？`0x300` 呢？
2. 车速 60 km/h 时，`0x100` 的数据段前两字节是什么？（提示：60/0.01 = 6000 = 0x1770，小端 → `70 17`）
3. 把 ECU 水温设到 125℃，`0x300` 哪个字节哪个 bit 会变 1？（提示：CoolantTempHigh 是 bit 2 → 字节 0 从 0x00 变 0x04）

这三个问题都能回答，02 章的核心你就掌握了。

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | **显性 = 逻辑 0**、**隐性 = 逻辑 1**。仲裁不损坏数据：显性位会"压过"隐性位（线与逻辑），且**发隐性位的一方发现被压成显性时立刻退出仲裁转为接收**，不继续发 |
| 2 | **0x100 先发完** —— ID 越小优先级越高。原因：仲裁从 ID 逐位比较，ID 小的在某个位发显性、ID 大的发隐性 → 后者检测到冲突主动退出 |
| 3 | `@1+` = **Intel 格式（小端）+ 无符号**；`@0-` = **Motorola 格式（大端）+ 有符号**。**两种字节序在车载 DBC 里都常见**（欧系 OEM 常用 Motorola，J1939 用 Intel）；判断只能查 DBC、不能凭经验 —— 本项目 `vehicle.dbc` 全部是 `@1+`（Intel） |
| 4 | 总线**两端各一个 120Ω**，并联后总线呈 **60Ω**（吸收反射、保证信号完整）。在中间测到 **120Ω → 说明只有一端接了终端电阻**（正常应是 60Ω）—— 详见 2.2.2 |
| 5 | ①**LIN 单线 / CAN 双线差分** ②**LIN 主从（主机轮询）/ CAN 多主（谁都能发，靠仲裁）** ③速度：LIN ≤20kbps，CAN 500k~1M |
| 6 | `NamedSignalValue` = cantools 解码**枚举信号**时返回的特殊对象（**不可哈希、不能直接和 int 比较**）→ 放进 set/dict 或 `== 数字` 会出错。绕过：取 `.value`，或解码时用 `decode_choices=False` —— 详见 2.4.4 |
