# 03 · UDS 协议详解：车载诊断的通用语言

> UDS（Unified Diagnostic Services，ISO 14229）是**诊断仪和 ECU 之间的"对话协议"**。
> 4S 店的诊断电脑、产线检测台架、你的自动化测试，说的都是 UDS。
> 本章是全教程最重要的一章——诊断测试是伟世通系统验证岗的核心技能。
>
> 学习方法：打开 `simulators/uds_client.py`，边读边发请求。

> **一句话抓重点**：UDS 就是"**发一条 hex 请求 → 等一条 hex 响应 → 判断正/负**"。
> 你要记住的是**三种响应断言**（正响应 / 负响应+NRC / 没响应），
> 其余细节（服务清单、NRC 表）都可以查。

## 3.1 诊断的通信模型

```
┌──────────────┐  请求(0x7E0)   ┌──────────────┐
│   Tester     │ ──────────────►│     ECU      │
│  (诊断仪/你)  │                │  (被测设备)   │
│              │◄────────────── │              │
└──────────────┘  响应(0x7E8)   └──────────────┘
```

- **Tester**：诊断仪。真实世界是 CANoe/UDS 控制台/诊断电脑；本项目是 `uds_client.py`。
- **ECU**：被测设备。本项目是 `ecu_sim.py`。
- **请求/响应走不同的 CAN ID**：物理寻址（单点定向）时 Tester→ECU 用 `0x7E0`、ECU→Tester 用 `0x7E8`（这是单 ECU 台架的惯例）；功能寻址（群发所有 ECU）用 `0x7DF`，各 ECU 仍用各自的响应 ID 回复（`0x7E8~0x7EF`）。

**为什么响应要用不同 ID？** 总线上几十个 ECU 都在听。用固定响应 ID，Tester 一眼能认出"这是回给我的"；也让多诊断仪并行成为可能。

## 3.2 请求与响应的格式

### 3.2.1 请求

```
[服务号 SID, 1 字节][参数, 0~N 字节]
```

例：读取 DID 0xF187（零件号）→ `22 F1 87`
- `22` = ReadDataByIdentifier 服务
- `F1 87` = 要读的 DID（2 字节）

### 3.2.2 正响应

```
[请求 SID + 0x40][参数...]
```

例：`62 F1 87 48 57 2D ...`（"HW-IC-..." 的 ASCII）

**+0x40 是 UDS 的铁律**：10→50, 22→62, 27→67, 31→71……看到响应第一个字节，立刻知道是哪个服务的回复。

### 3.2.3 负响应

```
[7F][导致失败的服务号][NRC 负响应码]
```

例：`7F 22 31` = "你的 22 服务失败了，原因是 requestOutOfRange"

**注意第二个字节是"原服务号"**（不是 +0x40），第三个字节才是错误码。

### 3.2.4 NRC 表（必背前 10 个）

| NRC | 名称 | 中文含义 | 常见触发 |
|---|---|---|---|
| 0x11 | serviceNotSupported | 服务不支持 | 发了 ECU 没实现的服务 |
| 0x12 | subFunctionNotSupported | 子功能不支持 | 例程 ID 不存在 |
| 0x13 | incorrectMessageLengthOrInvalidFormat | 长度/格式错 | 参数个数不对 |
| 0x22 | conditionsNotCorrect | 条件不满足 | 行车中请求刷写 |
| 0x31 | requestOutOfRange | 参数超范围 | DID 不存在 |
| 0x33 | securityAccessDenied | 安全访问被拒 | 没解锁就写数据 |
| 0x35 | invalidKey | 密钥错误 | 27 02 密钥算错 |
| 0x7F | serviceNotSupportedInActiveSession | 当前会话不支持 | 默认会话里刷写 |
| 0x78 | responsePending | 请稍等，正在处理 | ECU 忙（ flash 擦除中） |
| 0x7E | subFunctionNotSupportedInActiveSession | 当前会话不支持该子功能 | — |

**0x78 是特殊的**：它不是最终失败，而是"我收到了，正在办，等一下"。Tester 收到 0x78 要**继续等**（P2* 超时 5000ms 就是为它设计的），不能算失败。本项目为简化没实现 0x78，真实 ECU 刷写时到处都是它。

## 3.3 会话管理（0x10）：ECU 的"工作模式"

ECU 有几种会话（session），**不同会话开放不同服务**——这是基本的安全设计：

| 会话 | 值 | 特点 | 典型用途 |
|---|---|---|---|
| 默认会话 Default | 0x01 | 上电就在这；只开放读类服务 | 日常读数据、读 DTC |
| 编程会话 Programming | 0x02 | 关App跳Bootloader；开放刷写 | 升级固件 |
| 扩展会话 Extended | 0x03 | 开放大部分诊断功能（写/例程/控制） | 台架测试、产线 |

**切换会话**：`10 03` → 正响应 `50 03 00 32 01 F4`

响应里的 `00 32 01 F4` 是两个超时参数（ISO 14229-1）：
- **`P2` = 0x0032 = 50 ms**（单位 1ms）：Tester 发出请求后等首个响应（正响应/负响应/0x78）的最长时间；
- **`P2*` = 0x01F4 = 5000 ms**（单位 10ms，0x01F4×10）：收到 0x78 responsePending 后等最终响应的最长时间。

### 3.3.1 S3 定时器：5 秒不说话就"踢下线"

ECU 在非默认会话下有个 **S3 定时器（5 秒）**：如果 Tester 5 秒内没发任何请求（尤其 `3E` TesterPresent），ECU **自动跳回默认会话并锁定安全访问**。

```
Tester                              ECU
  │──10 03──────────────────────────►│ 进入扩展会话
  │◄─50 03...────────────────────────│
  │                                   │ S3 开始倒计时(5s)
  │──3E 00(每 2 秒一次)──────────────►│ 保活，S3 重置
  │◄─7E 00────────────────────────────│
  ...（安静 5 秒）...                  │ S3 超时 → 回默认会话
  │──2E F1 A0 xx─────────────────────►│ 此时已被踢回默认会话 → 7F 2E 7F!
```

**这就是测试脚本里到处插 `Tester Present` 的原因**。本项目 `ecu_sim.py` 的 `_session_timer` 线程实现了这个逻辑。

## 3.4 安全访问（0x27）：种子与密钥的握手

想改 ECU 的数据（写 DID）或刷写，必须先过安全访问。流程像对暗号：

```
Tester                              ECU
  │──27 01──────────────────────────►│ "请求种子" (requestSeed)
  │◄─67 01 [4字节随机种子]────────────│ ECU 给一个随机数 seed
  │                                  │
  │  本地用约定算法算 key = f(seed)    │  ← 算法只有 OEM 和授权方知道
  │──27 02 [4字节密钥]───────────────►│ "这是我对的暗号"
  │◄─67 02────────────────────────────│ 对 → 解锁！之后才允许 2E/31/34...
  │◄─7F 27 35─────────────────────────│ 错 → invalidKey，重新来
```

- **种子（seed）**：ECU 每次生成的随机数（防重放攻击）。
- **密钥（key）**：用约定算法由种子算出。真实 OEM 算法是保密的（查表法/CRC/时间窗），但**流程永远是这个流程**。
- **本项目的教学算法**：`key = seed XOR 0x5A5A5A5A`（见 `ecu_sim.py` 的 `compute_key`）。你可以打开 `uds_client.py` 输入 `unlock` 看它自动完成握手。

**安全设计常识**（面试可讲）：
- 错误次数超限（如连续 5 次）→ ECU 锁死一段时间（NRC 0x36）；
- **切会话/ECU 复位后必须重新解锁**——本项目 02 套件专门测了这条；
- 高安全等级功能（如刷写）还要叠加功能安全校验，不只是 0x27。

## 3.5 核心服务逐个过（本项目实现的 14 个）

以下每个服务都可以在 `uds_client.py` 里手动发。建议边读边试。

### 3.5.1 0x10 DiagnosticSessionControl 诊断会话控制

```
10 01 → 50 01 ...   回默认会话
10 02 → 50 02 ...   进编程会话
10 03 → 50 03 ...   进扩展会话
```

注意请求里的子功能（01/02/03）如果最高位置 1（如 `10 83`）表示**抑制正响应**——ECU 执行但不回复（用于群发场景，避免响应风暴）。

### 3.5.2 0x11 ECUReset ECU 复位

```
11 01 → 51 01   硬复位（等价于断电重启）
11 02 → 51 02   钥匙关-开复位
11 03 → 51 03   软复位
```

响应后 ECU 重启：**会话回默认、安全访问重新锁定、DTC 不清除**（DTC 存在非易失存储器，掉电不丢）。

### 3.5.3 0x14 ClearDiagnosticInformation 清除 DTC

```
14 FF FF FF → 54        清除所有 DTC（本项目实现并测试的路径）
14 01 16 00 → 54        按 groupOfDTC 单清 P0116（真实 ECU 必做；本项目教学版未实现，见下方说明）
```

**这是维修师傅最常用的服务**——"清码看一眼还亮不亮"。清除后所有 pending/confirmed 归零，警告灯策略由 ECU 重新评估。

> ⚠️ **已知限制（务必看）**：本项目 `ecu_sim._svc_clear_dtc` 目前只真正处理 `14 FF FF FF` 全清；带 groupOfDTC 的单清虽然会回 `54`，但实际不会命中任何 DTC（内部把 3 字节转成 `"011600"` 字符串去和 `"P0116"` 比较，永远不相等）。这是教学版简化，真实 ECU/台架必须支持单清——不要把示例当成已验证能力。

### 3.5.4 0x19 ReadDTCInformation 读取 DTC

子功能最丰富：

| 子功能 | 请求 | 响应 | 用途 |
|---|---|---|---|
| 0x01 | `19 01` | `59 01 FF 02` | 报告 DTC **数量** |
| 0x02 | `19 02 08` | `59 02 FF [DTC3B][status1B]...` | 按**状态掩码**报 DTC+状态 |
| 0x03 | `19 03` | `59 03 ...` | 报 DTC **快照**（冻结帧） |
| 0x04 | `19 04 FF` | `59 04 ...` | 报扩展数据 |
| 0x0A | `19 0A FF` | `59 0A ...` | 报所有**已确认** DTC |

本项目实现了 0x01/0x02/0x03。**0x02 是最常用的**——mask 0x08 只问 confirmed（确认故障），0xFF 问全部。

### 3.5.5 0x22 ReadDataByIdentifier 读 DID

```
22 F1 87 → 62 F1 87 "HW-IC-2026-001"     零件号
22 F1 90 → 62 F1 90 "LSVAM4180NC000001"  VIN（17字节，多帧！）
```

DID（Data Identifier）是 2 字节编号，每个 ECU 有自己的 DID 表（真实项目里由 ODX/CDD 文件定义）。常用 DID：

| DID | 含义 | 备注 |
|---|---|---|
| F187 | 零件号 | 只读 |
| F188 | 软件版本 | 本项目设为可写 |
| F189 | 序列号 | 只读 |
| F18A | 供应商代码 | 只读 |
| F190 | VIN 码 | 17 字节，必然多帧 |
| F1A0 | 应用数据 | 本项目设为可写（默认 `V1.0.0`） |
| F1B0 | 工程测试激励 | 4 字节：供电电压/丢帧率/报文停发位图/保留；仅扩展会话+解锁可写，故障注入用（见 `scenarios/11_fault_injection.robot` 与 `Set Test Stimulus` 关键字） |

### 3.5.6 0x27 SecurityAccess 安全访问

见 3.4 节。本项目实现了 0x01/0x02。

### 3.5.7 0x2E WriteDataByIdentifier 写 DID

```
2E F1 A0 56 33 → 6E F1 A0     把应用数据写成 "V3"
```

**权限**：扩展会话 + 安全解锁，两者缺一不可（本项目 02 套件有两条对应测试）。响应只回显 DID，不回数据。

### 3.5.8 0x31 RoutineControl 例程控制

让 ECU 跑一个内置程序（自检、标定、动作测试）：

```
31 01 02 00 → 71 01 02 00 00  启动例程 0x0200（自检，末位 00=结果通过）
31 03 02 00 → 71 03 02 00 00  查询例程结果（00=通过）
```

子功能：01=启动、02=停止、03=请求结果。本项目的 `0x0301` 例程是**灯光测试**（点亮所有警告灯、持续 4 秒后自动熄灭，`threading.Timer(4.0)`）——产线终检必做，用来验证每个 Telltale 都能亮。

### 3.5.9 0x3E TesterPresent 诊断仪在线

```
3E 00 → 7E 00    保活（S3 重置）
3E 80            抑制响应（静默保活）
```

**这是测试脚本里出现频率最高的服务**——长时间测试中每隔 1-2 秒发一次，防止被 S3 踢出扩展会话。

### 3.5.10 0x85 ControlDTCSetting 控制 DTC 设置

```
85 02 → C5 02    暂停故障检测（测试时避免误记录）
85 01 → C5 01    恢复检测
```

产线/台架测试利器：先暂停检测→做各种操作→恢复，避免测试动作触发无关 DTC 污染结果。

### 3.5.11 0x28 CommunicationControl 通信控制

```
28 03 01 → 68 03 01    关闭正常报文收发（只留诊断通信）
28 00 → 68 00          恢复正常
```

用途：刷写时关闭 App 的正常通信，防止总线被刷写过程干扰；也用于"总线静默测试"。

### 3.5.12 0x34 / 0x36 / 0x37 刷写三件套

刷写（Flash Programming）是诊断测试的天花板：把新固件分块写进 ECU。它必须**编程会话（`10 02`）+ 安全解锁（`27`）**后才允许（本项目 `_check_session_for_service` 对这三条服务做了两层权限校验）。完整流程见 08 章 8.12，对应用例在 `tests/robot/06_uds_flash_conformance.robot`（11 条）。最小序列：

```
34 00 44 08000000 00000080  → 74 20 04 00       请求下载：地址 0x08000000、共 128 字节；
                                                 正响应 = 74 + lengthFormat 0x20 + maxBlockLength 0x0400(=1024)
36 01 <最多 1024 字节数据>    → 76 01             传输数据块：块序号 1、2、3…（0xFF 后回 0x00）
37                           → 77                退出传输
31 01 FF00                   → 71 01 FF 00 00    检查编程完整性（结果 00=通过）
```

- **0x34 请求**：`dataFormatIdentifier` + `addressAndLengthFormatIdentifier` + 目标地址 + 写入字节数；本项目把地址范围限制在 `0x08000000~0x08100000`，超范围回 NRC 0x31。
- **0x36 块序号必须严格递增**，错乱回 NRC 0x73（本项目实现了该检查）；发超声明大小回 NRC 0x13。
- **0x37 退出后**用 0x31 例程 0xFF00 做完整性校验；刷写状态在 `0x11 01` 复位后清空（06 套件用例间隔离正是靠它）。
- 常见负响应：没进编程会话 → `7F xx 7F`（当前会话不支持）；未解锁 → `7F xx 33`；未请求下载就传数据 → `7F 36 24`（序列错误）。

## 3.6 ISO-TP：当 UDS 报文超过 7 字节

CAN 一帧最多 8 字节，减去 1 字节 PCI（协议控制信息），**单帧最多装 7 字节 UDS 数据**。`22 F1 90` 的请求只要 3 字节没问题，但**响应有 20 字节（62 F1 90 + 17 字节 VIN）**，必须拆帧——这就是 **ISO 15765-2（CAN 上的传输协议，俗称 CAN TP）**。

### 3.6.1 三种帧

| 帧类型 | PCI 首字节 | 结构 | 例子（发 20 字节数据） |
|---|---|---|---|
| 单帧 SF | 0x0_ | `[0x0L][数据...]` L≤7 | `03 22 F1 87` |
| 首帧 FF | 0x1_ | `[0x1_][长度低8位][数据前6字节]` | `10 14 62 F1 90 4C 53 56`（总长0x14=20，带前 6 字节数据） |
| 连续帧 CF | 0x2_ | `[0x2_序号][数据7字节]`，序号从 1 开始循环（1..F,0,1…） | `21 56 41 4D ...` |
| 流控帧 FC | 0x30 | `[30][块大小BS][STmin]` | `30 08 00` |

### 3.6.2 完整拆帧演算（读 VIN 的响应）

要传的数据（20 字节）：`62 F1 90 4C 53 56 41 4D 34 31 38 30 4E 43 30 30 30 30 30 31`（"LSVAM4180NC000001"）

```
ECU → Tester:
  FF:  10 14 62 F1 90 4C 53 56     ← 0x14=20字节总长；带前6字节数据
Tester → ECU:
  FC:  30 08 00                    ← " BS=8: 你连发8个CF不用再问我; STmin=0: 不用等"
ECU → Tester:
  CF1: 21 41 4D 34 31 38 30 4E     ← 序号1
  CF2: 22 43 30 30 30 30 30 31     ← 序号2（20 字节 = 前 6 + 7 + 7，CF2 是最后一帧）
```

- **BS（Block Size）**：一次允许多少个 CF。BS=0 表示"不限量，发完为止"。
- **STmin（Separation Time minimum）**：两个 CF 之间的最小间隔（防止接收方缓冲溢出），单位 ms。

### 3.6.3 接收方状态机

本项目 `uds_lib.py` 的 `IsoTpReceiver` 实现了它：

```
收到 FF → 记录总长、启动缓冲、回 FC
收到 CF → 校验序号（必须连续！乱序=错误）→ 追加数据
缓冲够总长 → 交付完整数据
```

**序号错乱会怎样？** 真实 ECU 会中止重组（TP 层 watchdog 超时或序号错误，现象是**等不到最终响应**，而不是收到某个 NRC——0x78 是"请稍等"，属于 UDS 层、不是 TP 错误）。本项目 `IsoTpReceiver` 直接抛 `ValueError`——TP 层的错误处理是高级话题，知道"有序性由 4 bit 序号保证"即可。

### 📋 自查要点（答完再对，别提前看）

| # | 自查要点 |
|---|---|
| 1 | **请求**：`SID + 参数`（如 `22 F1 87`）｜**正响应**：`SID+0x40 + 参数`（如 `62 F1 87 "HW-IC-..."`）｜**负响应**：`7F + 原SID + NRC`（如 `7F 22 31`） |
| 2 | `0x31` = **requestOutOfRange**（参数超范围，如 DID 不存在）｜`0x33` = **securityAccessDenied**（没解锁）｜`0x78` = **responsePending**（处理中 → **要继续等，不是失败**） |
| 3 | 默认会话**只允许读**；扩展会话允许写/跑例程。S3 超时（5s 无请求）→ **自动回退默认会话 + 锁定安全访问**。脚本里防：定期发 `3E 00` 保活 |
| 4 | 流程：`27 01` 要种子 → ECU 回 `67 01 [seed]` → 按算法算 key → `27 02 [key]` → ECU 回 `67 02`。切会话要重新解锁，因为**解锁状态与当前会话绑定**（回退/切换即清除） |
| 5 | ①**FF 首帧**：`1n [总长度] [前 6 字节数据]` ②**FC 流控帧**（接收方发）：`3x [BS 块大小] [STmin 间隔]` ③**CF 连续帧**：`2n [7 字节]`，n 从 1 递增 —— 完整格式见 3.6 |
| 6 | 读 VIN 用 **`F190`**。一定多帧，因为 VIN 是 **17 字节**，响应共 20 字节，远超单帧 7 字节的上限 |
