# 15 · 车载脚本模式库：20 个必会写法

> **真实工作中 90% 的车载脚本都是这 20 个模式的组合。**
> 学会它们，遇到新需求就是"该用哪个模式"的选择题，而不是"从零想怎么写"。
>
> 每个模式：**场景 → 代码 → 要点**。建议对照 [速查表](../training/cheatsheet.md) 边看边试。

---

## A 组 · 读取与断言（模式 1-4）

### 模式 1：读一个值并断言范围

**场景**：最基础。验证某个信号在合理区间。

```robotframework
车速信号应处于合理范围
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Should Be True    50 <= ${speed} <= 70
    ...    msg=车速 ${speed} 不在 50~70 范围内
```

**要点**：
- 用**范围**不用精确值（信号有噪声、有斜坡、有量化误差）
- `msg=` 里带上 `${speed}` —— 失败时一眼看到实际值
- 范围要有依据：50~70 来自"目标 60 ± 容差"，不是拍脑袋

### 模式 2：等值进入范围（车载最常用 ★）

**场景**：信号会变化（车速爬坡、水温升温、故障确认），需要等它到位。

```robotframework
车速应稳定在目标区间
    ${speed}=    Wait Until Signal In Range    EngineData    VehicleSpeed    50    70    timeout=20
    Log    车速已稳定在 ${speed} km/h ✓
```

**要点**：
- **绝不用 `Sleep` 猜时间**（偶发失败的头号来源）
- 区间退化成单值 = "等它精确等于"：`Wait Until Signal In Range    ClusterData    GearPosition    3    3`
- **timeout 要有物理依据**（爬坡 7.5s → 给 20s；水温 15s → 给 25s）

**反例（新手必踩）**：

```robotframework
# ❌ 错的：Wait Until Keyword Succeeds 只看"抛不抛异常"，
#    Read Signal From Bus 读到 5 km/h 也算成功 → 等待立即结束 → 后面断言失败
Wait Until Keyword Succeeds    20x    1s    Read Signal From Bus    EngineData    VehicleSpeed
```

### 模式 3：发一帧并验证回读

**场景**：模拟另一个节点发报文，验证总线/接收方行为。

```robotframework
注入车速信号后仪表应更新
    Send Signal Values    EngineData    VehicleSpeed=88    EngineSpeed=3000
    Wait Until Keyword Succeeds    10x    200ms
    ...    Get Displayed Speed Should Be Near    88
```

**要点**：
- `Send Signal Values` 只需给关心的信号，**其余自动补默认值**
- 发完必须**验证接收端**（仪表/ECU）—— 只发不验等于没测
- 若总线上有别的节点也在发同一报文（如 ECU 周期帧），
  先用 `Suspend ECU Periodic Messages` 暂停它（见模式 20）

### 模式 4：断言"存在/包含"

**场景**：结果是个集合，验证其中包含某元素。

```robotframework
故障发生后 DTC 列表应包含 P0116
    ${dtcs}=    Read DTC By Mask    FF
    DTC List Should Contain    P0116          # 库关键字（内部做了格式化比较）

灯亮时告警摘要应包含水温
    ${lit}=    Get Lit Telltales
    Should Contain    ${lit}    CoolantTempHigh
```

**要点**：
- 列表断言优先用库提供的语义化关键字（`DTC List Should Contain`），
  比自己解析返回值更稳
- 空列表断言：`Should Be Empty    ${list}`

## B 组 · 诊断（模式 5-9）

### 模式 5：诊断请求-响应（诊断脚本的骨架）

**场景**：所有诊断测试的基础三步。

```robotframework
默认会话下应能读取零件号
    ${pn}=    Read DID As ASCII    F187          # ① 发请求（库封装）
    Should Be Equal    ${pn}    HW-IC-2026-001  # ③ 断言内容

读取未知 DID 应返回参数超范围
    ${resp}=    Send UDS Request    22 F9 99     # ① 裸 hex 请求
    Response Should Be Negative With NRC    0x31 # ③ 断言负响应
```

**要点**：
- 三种响应断言：`Response Should Be Positive` / `...Negative With NRC 0xXX` / 比对描述文本
- 能用封装关键字就别写裸 hex（可读性 + 不拍错 hex）
- 需要 hex 时查 [速查表·第三节](../training/cheatsheet.md)

### 模式 6：负向断言（面试加分项 ★）

**场景**：验证"该拒绝时真的拒绝了"。

```robotframework
未解锁时写 DID 应被拒绝
    Enter Extended Session
    ${resp}=    Send UDS Request    2E F1 A0 4841434B
    Response Should Be Negative With NRC    0x33    # securityAccessDenied
```

**要点**：
- 负向用例要覆盖**权限的两个维度**：会话（0x7F）+ 安全访问（0x33）
- NRC 要断言**具体值**，不能只断言"失败了"（可能是别的错）
- 常用 NRC 见速查表

### 模式 7：期望"没有响应"

**场景**：验证 ECU 的"静默执行"（抑制正响应 0x80 位）。

```robotframework
抑制正响应的请求 ECU 应保持沉默
    Run Keyword And Expect Error    *没等到*    Send UDS Request    3E 80
    ECU Should Respond      # ★ 必须补这一步：确认是"正确地沉默"而非 ECU 挂了
```

**要点**：
- 用 `Run Keyword And Expect Error` + `*没等到*` 验证超时
- **"验证沉默"和"验证存活"必须成对做** —— 否则 ECU 整体挂了也会"通过"

### 模式 8：会话 + 解锁 + 操作 三连

**场景**：任何"敏感操作"（写数据、刷写、例程）的固定前置。

```robotframework
完成种子密钥握手后写 DID 应成功
    Enter Extended Session        # ① 会话
    Security Unlock               # ② 解锁（27 01/02 握手）
    Write DID    F1A0    56332E302E30    # ③ 操作
    ${ver}=    Read DID As ASCII    F1A0
    Should Be Equal    ${ver}    V3.0.0   # ★ 写后回读
```

**要点**：
- 顺序不能反：**先会话、再解锁、后操作**
- **写操作后必须回读验证**（正响应只说明"收到了"，不代表"写对了"）
- S3 定时器 5 秒：长测试中每隔 1-2 秒发 `3E 00` 保活（或用库的封装）

### 模式 9：等 DTC 出现（轮询的正确用法）

**场景**：故障注入后等 DTC 被记录（要经过 N 个诊断周期）。

```robotframework
诊断仪应能读到 confirmed 的 P0116
    Wait Until Keyword Succeeds    15x    1s    DTC List Should Contain    P0116
```

**要点**：
- 这里 `Wait Until Keyword Succeeds` **是对的** ——
  因为被等待的 `DTC List Should Contain` **自己会断言**（不满足就抛错）→ 重试有意义
- 对比模式 2 的反例：那里被等待的关键字不会断言 → 重试无效

> **一句话总结**：`Wait Until Keyword Succeeds` 要包**会断言的关键字**。

## C 组 · 跨系统与场景（模式 10-13）

### 模式 10：跨系统一致性（同一个事实，两个视角）

**场景**：同一个故障，仪表和诊断都要能看到 —— 这类用例最能发现问题。

```robotframework
水温超限时仪表与诊断应一致
    Telltale Should Be Lit    CoolantTempHigh    timeout=25   # 仪表视角
    Wait Until Keyword Succeeds    15x    1s    DTC List Should Contain    P0116  # 诊断视角
```

**要点**：
- 单点验证价值低（"灯亮了"），**跨系统验证价值高**（"灯亮的依据在诊断里也成立"）
- 量产座舱的多屏一致性测试就是这个思路

### 模式 11：用 Setup 造场景，不在用例里造

**场景**：整个套件需要特定工况（故障车、行车中、特定配置）。

```robotframework
*** Settings ***
Suite Setup      Start Vehicle Environment    speed=60    coolant=125
Suite Teardown   Stop Vehicle Environment
```

**要点**：
- 环境参数化（`speed` / `coolant` / `with_android`）比在用例里"造"更稳、更快
- 一个套件一个场景；不同场景就分套件（而不是一个套件里换来换去）

### 模式 12：闭环（造 → 验 → 干预 → 恢复）★

**场景**：完整业务流程验证，也是面试时最能讲的部分。

```robotframework
清除 DTC 后报警灯应熄灭
    Clear DTC                                   # 干预
    ${count}=    Read DTC Count
    Should Be Equal As Integers    ${count}    0
    Telltale Should Be Off    CoolantTempHigh    timeout=5

故障仍在时 DTC 应重新确认
    Wait Until Keyword Succeeds    20x    1s    DTC List Should Contain    P0116
    Telltale Should Be Lit    CoolantTempHigh    timeout=10
```

**要点**：
- 最后一步"恢复性验证"最容易被漏，但**价值最高**：
  它证明"干预没把系统搞坏"（清码后系统还能重新检测）
- 真实对照："清码后过几天又亮" = 故障真的还在，不是清除失效

### 模式 13：时序断言（一致性测试必备）

**场景**：验证响应速度符合协议声明（P2 参数）。

```robotframework
响应时间应符合声明的 P2 参数
    Enter Extended Session
    ${ms}=    Measure Response Time    22 F187
    Should Be True    ${ms} < 50    msg=响应耗时 ${ms}ms 超过 P2(50ms)
```

**要点**：
- P2 是 ECU 在会话响应里**声明**的最长响应时间（本项目 50ms）
- 实测持续超过 P2 → 诊断仪会误判超时 → 真实缺陷
- 同理可测**报文周期**（0x100 应 100ms 一帧，抖动 < 20ms）

## D 组 · 组织与复用（模式 14-17）

### 模式 14：数据驱动（Template）

**场景**：同一逻辑、多组数据。

```robotframework
读取多个 DID 应正确
    [Template]    读取 DID 并断言
    F187    HW-IC-2026-001
    F189    ECU-2026-0918-007
    F18A    VISTEON

*** Keywords ***
读取 DID 并断言
    [Arguments]    ${did}    ${expected}
    ${value}=    Read DID As ASCII    ${did}
    Should Be Equal    ${value}    ${expected}    msg=DID ${did} 不符
```

**要点**：
- **`[Template]` 只能写一个关键字名**，参数放数据行里（踩过这个坑）
- 报告里每组数据独立统计 → 一眼看出哪组挂了
- 逻辑不同别硬套模板（宁可写两个用例）

### 模式 15：循环遍历

**场景**：对一组对象重复同样操作（但**参数不在报告里独立统计**时用循环）。

```robotframework
所有 DID 都应能读取
    @{dids}=    Create List    F187    F189    F18A
    FOR    ${did}    IN    @{dids}
        ${value}=    Read DID As ASCII    ${did}
        Should Not Be Empty    ${value}    msg=DID ${did} 读取为空
    END
```

**要点**：
- 循环里失败 → 整个用例算一条失败（定位不如 Template 细）
- 需要"每行独立统计"用 Template，需要"聚合判断"用循环

### 模式 16：什么时候抽自定义关键字

```robotframework
*** Keywords ***
进入扩展会话并解锁
    [Documentation]    敏感操作的固定前置（会话 + 安全访问）
    Enter Extended Session
    Security Unlock
```

**三条判断标准**（满足任一就抽）：
1. 同样两步以上在 **3 个以上用例**出现
2. 用例里的步骤超过 **5 行**，需要按业务语义分组
3. 有**复杂逻辑**（循环/条件/计算）→ 下沉到 Python 库

**不要过度抽象**：只用一次的逻辑别抽（增加跳转成本）。

### 模式 17：用例隔离（前一个用例改的状态会影响后一个）

```robotframework
*** Settings ***
Test Teardown    复位 ECU 清理刷写状态

*** Keywords ***
复位 ECU 清理刷写状态
    Run Keyword And Ignore Error    Send UDS Request    11 01
    Sleep    0.2s
```

**要点**：
- 典型场景：刷写用例会留下 `flash_state`，下一个 0x34 会撞 NRC 0x24
- **优先用被测系统自带的"复位"机制**（`11 01` ECU 复位）而不是自己造清理逻辑 —— 更真实
- 残留状态导致的失败往往**只在连续跑时出现**（单独跑能过）→ 最难查

## E 组 · 工程与排错（模式 18-20）

### 模式 18：让失败看得懂（日志三件套）

```robotframework
车速应处于合理范围
    ${speed}=    Read Signal From Bus    EngineData    VehicleSpeed
    Log    读到车速 ${speed} km/h（含缩放后物理值）      # ① 过程日志
    Should Be True    50 <= ${speed} <= 70
    ...    msg=车速 ${speed} 不在 50~70，检查 ECU 目标速度与爬坡时间   # ② 带实际值+排查方向
```

**要点**：
- `Log` 写进 `log.html`（过程证据）；`Log To Console` 输出终端（跑的时候看）
- `msg=` 三要素：**期望值 + 实际值 + 排查方向**
- 别用它当调试打印用完不删（日志噪音会淹没证据）

### 模式 19：保留失败现场（Trace 归档）

```robotframework
录制总线并导出 Trace 文件（CANoe 兼容）
    Start Bus Recorder
    Drain Bus For    2
    Stop Bus Recorder
    ${n}=    Recorded Frame Count
    Export Bus Trace    ${ROOT}/results/bus_trace.asc
    Trace Files Should Be Valid    ${ROOT}/results/bus_trace.asc    ...    ${n}
```

**要点**：
- 测试失败时最需要"当时总线上发生了什么"——Trace 就是证据
- ASC 可直接用 CANoe 打开分析；`common.resource` 的 teardown 会自动归档
- 面试加分："我产出的 Trace 能直接进 CANoe 流程"

### 模式 20：暂停干扰源（让测试环境"干净"）

```robotframework
环境就绪并暂停 ECU 周期报文
    Start Vehicle Environment
    Enter Extended Session
    Suspend ECU Periodic Messages     # 28 01 01：ECU 停发周期报文，保留诊断

恢复 ECU 周期报文并关闭环境
    Run Keyword And Ignore Error    Enter Extended Session
    Run Keyword And Ignore Error    Resume ECU Periodic Messages   # 28 00
    Stop Vehicle Environment
```

**场景**：测试要"发帧 → 读回"，但 ECU 每 100ms 也在发同一报文 → 读回的是谁的不确定。

**要点**：
- 用 **UDS 0x28**（通信控制）暂停 ECU，这是**真实刷写流程的前置动作**
- `28 01 01` = 只停发送（保留诊断）；`28 03 01` = 停收停发（刷写用）
- Teardown 里的恢复要包 `Run Keyword And Ignore Error`（环境可能已异常，别让清理失败掩盖真正的失败）
