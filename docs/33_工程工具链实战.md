## 33.1 为什么"会写用例"还不够：工具链是岗位基础设施

先看一个真实差距。同样"测完 276 个用例"，两种工程师的交付：

| | 只会写用例 | 工程化测试工程师 |
|---|---|---|
| 代码改了一行 | 等 6 分钟全量 RF 跑完才知道对不对 | 先跑 **30 个 pytest 单元测试（0.5s）**，挂了立刻定位 |
| 换台机器/新人入职 | "我这能跑，你环境有问题" | `docker run` **一条命令**，环境完全一致 |
| Python 升级 | "升级了不知道会不会坏" | CI **矩阵 [3.12, 3.14]** 一次看全 |
| 报告 | 截图贴群里 | CI 自动归档 `results/`（HTML + Trace），给客户链接 |
| 对接台架/CANoe | 手工点 CANoe 录 Trace，再人工比对 | 明确**接口抽象层**，把仿真 IO 换成真实 IO，用例零改动 |

本章的四个交付物正好覆盖后四行：

| 交付物 | 位置 | 作用 |
|---|---|---|
| pytest 单元测试 | `tools/pytest_style/`（4 个测试文件 / 30 个 test case） | 秒级门禁，防"纯函数/数据文件"回归 |
| CI 矩阵 + pytest step | `.github/workflows/ci.yml` | Python 3.12/3.14 双版本 + 快速失败 |
| Docker 化环境 | `Dockerfile` / `.dockerignore` | 一条命令复现全量测试环境 |
| 工具链接口 | 本章 33.8~33.10 | CANoe / Appium / HIL 对接的真实写法与替换点 |

## 33.2 pytest vs Robot Framework：分工与边界

这是最常被问、也最容易用错的知识点。

| 维度 | pytest | Robot Framework（本项目主框架） |
|---|---|---|
| **定位** | **开发者测试框架**（单元/接口级为主） | **验收/系统测试框架**（关键字驱动，面向业务与交付） |
| 语法 | 纯 Python 函数 + `assert` | 表格/关键字 DSL（`.robot`），用例即文档 |
| 适合测什么 | 纯函数、数据结构、协议编解码、算法边界 | 多进程系统、CAN/UDS 端到端、HMI 联动、故障注入 |
| 执行速度 | 毫秒级（本目录 30 个测试 **0.45s**） | 秒级/条，全量 **约 6 分钟**（359~380s（多次实测）） |
| 报告 | 终端/JUnit XML，可接 Allure | 自带 `log.html`/`report.html`（含每步入参返回值） |
| 谁看报告 | 开发（快速定位） | 测试主管/客户/审核（看结论与证据链） |
| 本项目对应 | `tools/pytest_style/` | `tests/robot/`（主套件）+ `scenarios/`（场景）；合计用例数以 `python run_tests.py` 输出为准 |

**什么时候用哪个（决策口诀）**：

```
只依赖内存里的输入输出           → pytest
需要起进程 / 走 UDP 组播 / 等物理过程 → Robot Framework
要"给客户/主管看"的验收证据       → Robot Framework（+ 20 章交付链）
纯逻辑改错要 1 秒内知道           → pytest
```

> 💡 **不要用 RF 写单元测试**：每个 RF 用例都有解析/执行开销，把 30 个纯函数检查塞进 `.robot`
> 会让反馈从 0.5 秒变几秒，并且定位失败要看 log.html。反过来，**不要用 pytest 硬测多进程系统**——
> 起停进程、等总线稳态、清理状态，这些 RF 的 `Suite Setup/Teardown` 已经做得很好。

## 33.3 分层测试：单元（pytest）→ 系统（RF）→ 台架/HIL

把项目现有的测试按"测试金字塔"摆一下：

```
                   ┌────────────────────────────┐
                   │  实车 / 整车验收（本课程外）│  最少、最慢、最贵
                   ├────────────────────────────┤
                   │  HIL 台架（33.10）          │  真 ECU + 仿真其余
                   ├────────────────────────────┤
                   │  Robot Framework 系统测试   │  276 用例 / ~6 分钟
                   │  tests/robot + scenarios    │  ← 本项目主战场
                   ├────────────────────────────┤
                   │  pytest 单元测试（33.4）    │  30 test case / 0.45s
                   │  tools/pytest_style         │  ← 本章新增：第一道门禁
                   └────────────────────────────┘
```

**为什么需要底层的 pytest 层**：越往下越快、越便宜，越应该把"能在下层抓到的错误"留在下层。
DTC 编码算错、ISO-TP 拆帧边界错、需求 ID 格式错——这些都是**不需要上总线就能判定**的错误，
让 pytest 在 0.5 秒内拦住，不要让它们混进 6 分钟的 RF 全量里（那样定位成本高 100 倍）。

## 33.4 实战：本项目的 pytest 单元测试

### 33.4.1 目录与运行

```
├── test_uds_lib.py                # DTC 编解码往返、ISO-TP 拆帧/重组（7/20/64B）、负响应格式
├── test_dtc_manager.py            # DTC 状态机 pending→confirmed→aging→clear（纯内存）
├── test_requirements_yaml.py      # 需求清单可解析、ID 唯一/格式/字段/枚举值
├── test_generate_testcases.py     # DBC 解析（5 报文/35 信号）、BVA 点、pairwise 两两覆盖
└── README.md                      # 分工说明与新增测试规范
```

```bash
# 在项目根目录
.\.venv\Scripts\python.exe -m pytest tools/pytest_style -q
```

本机实测（Python 3.14.5 / pytest 9.2.0）：

```
30 passed, 1 warning in 0.45s
```

### 33.4.2 关键代码要点

**① conftest.py：把项目根加进 `sys.path`**

pytest 从 `tools/pytest_style/` 收集测试，而 `uds_lib.py` / `dtc_manager.py` 在
`simulators/` 下（根脚本通常用 `sys.path.insert(0, ROOT / "simulators")` 注入）。
`conftest.py` 统一做这件事，测试文件里就能直接 `import uds_lib`：

```python
ROOT = Path(__file__).resolve().parents[2]      # tools/pytest_style/conftest.py → 项目根
for _p in (str(ROOT), str(ROOT / "simulators")):
    if _p not in sys.path:
        sys.path.insert(0, _p)
```

**② 纯函数测试：给输入、断言精确输出**（`test_uds_lib.py`）

```python
def test_dtc_known_encoding():
    assert uds_lib.string_to_dtc("P0116") == (0x01, 0x16, 0x00)

@pytest.mark.parametrize("size", [7, 20, 64])          # 单帧 / 1FF+2CF / 1FF+9CF
def test_isotp_split_and_reassemble(size):
    data = bytes(range(size))
    frames = uds_lib.IsoTpSender.split_frames(data)
    rx = uds_lib.IsoTpReceiver()
    for frame in frames:
        done, payload = rx.feed(frame)
        if done:
            assert payload == data
```

**③ 状态机测试：纯内存推进，不碰进程**（`test_dtc_manager.py`）

```python
NORMAL   = {"coolant_temp": 90.0,  "battery_voltage": 13.5, "o2_heater_fault": False}
FAULT_HOT = {"coolant_temp": 125.0, "battery_voltage": 13.5, "o2_heater_fault": False}

mgr = DtcManager(confirm_threshold=2, aging_limit=3)
mgr.advance_cycle(FAULT_HOT)        # 第 1 循环 → pending
mgr.advance_cycle(FAULT_HOT)        # 第 2 循环 → confirmed + 点灯
mgr.advance_cycle(NORMAL)           # 故障消失 → 非保持型灯灭，confirmed 仍保留（aging=1）
```

**④ 数据质量测试：让"需求清单写坏了"在 0.5 秒内暴露**（`test_requirements_yaml.py`）

```python
def test_yaml_and_regex_counts_agree(requirements_path):
    """两套独立口径（yaml 解析 vs 正则数 `- id:` 行）必须一致"""
    reqs = yaml.safe_load(requirements_path.read_text(encoding="utf-8"))["requirements"]
    regex_ids = re.findall(r"^\s*-\s*id:\s*(\S+)", requirements_path.read_text(encoding="utf-8"), re.M)
    assert [r["id"] for r in reqs] == regex_ids
```

> 💡 **为什么值得写**：需求清单是需求追溯的源头。ID 重复/格式错会让 `trace_matrix.py`
> 静默失真（例如两条需求合成一条、Tag 匹配不上）。这类检查不写测试就永远靠"跑一遍看看"。

**⑤ 算法/组合测试：pairwise 必须真的覆盖所有两两组合**（`test_generate_testcases.py`）

```python
def test_pairwise_covers_all_pairs():
    params = [("A", [0, 1, 2]), ("B", [0, 1]), ("C", [0, 1])]
    rows = generate_testcases.pairwise(params)
    assert len(rows) < 3 * 2 * 2                       # 比全组合 12 行少
    # 每个参数对的每个取值组合都至少出现一次
    for p1, p2 in itertools.combinations(["A", "B", "C"], 2):
        ...
```

## 33.5 CI 矩阵：多 Python 版本 + 失败快速反馈

### 33.5.1 为什么要 Python 版本矩阵

本项目开发机是 **Python 3.14.5**，GitHub Actions 默认稳定版本是 **3.12**。
只测一个版本会出现两种事故：

- 只测 3.12 → 本地在 3.14 上跑得欢，但某些 API 行为变了，CI 才发现；
- 只测 3.14 → 新版本依赖兼容性没保证（PySide6/python-can 的 wheel 支持滞后是常态）。

所以 CI 改成了**矩阵**：

```yaml
strategy:
  fail-fast: false                 # 一个版本失败，另一个版本继续跑完（一次看全）
  matrix:
    python-version: ['3.12', '3.14']
```

### 33.5.2 pytest 作为"快速失败"门禁

矩阵里第一步跑的不是 RF，而是 **pytest（0.5s）**：

```yaml
      - name: pytest 单元测试（快速失败）
        run: |
          python -m pip install pytest
          python -m pytest tools/pytest_style -q
```

**收益**：如果改动把 DTC 编码弄坏了，CI **5 秒内**失败在 pytest 步骤，而不是等 6 分钟 RF
跑到一半才在 log.html 里翻失败原因。这是"失败快速反馈（Fail Fast）"在流水线里的落地。

> ⚠️ 为什么 CI 里要单独 `pip install pytest`：pytest 是**本地 venv 已有的开发工具**，
> 没有进 `requirements.txt`（保持运行依赖最小）；CI/Docker 各自补装即可。

### 33.5.3 产物与矩阵的冲突

`upload-artifact` 在矩阵下会跑 N 次，**artifact 名字必须带版本号**，否则 GitHub Workspace
会因同名冲突报错：

```yaml
          name: test-results-${{ github.run_number }}-py${{ matrix.python-version }}
```

### 33.5.4 实际耗时预期

| 步骤 | 耗时（单版本） |
|---|---|
| 安装依赖（缓存命中） | ~10-20s |
| **pytest（30 test case）** | **<1s** |
| `test_spec_check.py` | <1s |
| `generate_testcases.py` | <1s |
| RF 全量（276 用例） | 约 6 分钟（本机 359~380s（多次实测）；CI 双版本矩阵无缓存约 8 分钟/版本） |
| 上传产物 | ~1s |

矩阵 2 个版本**并行**跑，总墙钟时间约等于单版本 + 排队，不会翻倍。

## 33.6 Docker 化测试环境

### 33.6.1 为什么需要 Docker

"在我机器上能跑"是测试工程师最大的职业风险之一。本项目虽然是纯软件仿真，
但依赖仍然敏感：Python 版本、PySide6 运行库（libGL/libEGL）、python-can 版本、系统 locale。
Docker 把"操作系统 + Python + 依赖 + 代码"打包成一个**不可变镜像**：

- 新人入职：`docker build` + `docker run`，不装任何东西就能跑 276 用例；
- CI 回归：镜像和本地一致，减少"环境差异导致的 flaky"；
- 面试演示：一条命令复现，比"先装 20 分钟环境"可信得多。

### 33.6.2 Dockerfile 关键设计（见仓库根 `Dockerfile`）

```dockerfile
FROM python:3.12-slim                 # 与 CI 主版本一致

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PYTHONIOENCODING=utf-8            # Linux 容器也固定 UTF-8（日志友好）

RUN apt-get update \
 && apt-get install -y --no-install-recommends libgl1 libegl1 libglib2.0-0 \
 && rm -rf /var/lib/apt/lists/*      # PySide6 运行库；清理 apt 缓存减小镜像

WORKDIR /app
COPY requirements.txt ./             # 先装依赖（依赖不变时复用层缓存）
RUN pip install -r requirements.txt && pip install pytest
COPY . .

CMD ["python", "run_tests.py"]       # 默认跑全量 RF 套件（276 用例）
```

### 33.6.3 构建与运行命令（本机没装 Docker 就跳过；不要尝试 build）

```bash
# 构建（首次约 2-3 分钟；依赖层会缓存）
docker build -t vehicle-test-framework:latest .

# 跑全量（默认 CMD）
docker run --rm vehicle-test-framework:latest

# 跑全量 + 生成三份 HTML 报告，并把 results/ 挂载到宿主机
docker run --rm -v "$PWD/results:/app/results" vehicle-test-framework:latest \
    python run_tests.py --report

# 只跑 pytest 单元测试
docker run --rm vehicle-test-framework:latest python -m pytest tools/pytest_style -q

# 某些平台容器内 UDP 组播受限时（Linux 常用）：使用 host 网络
docker run --rm --network host vehicle-test-framework:latest
```

> 💡 **UDP 组播在容器里的注意点**：本项目多个仿真进程**都在同一个容器内**，组播回环
> （同一网络命名空间）通常可用；若宿主机/平台限制组播，优先加 `--network host`。
> Windows/macOS 的 Docker Desktop 对组播支持较弱，建议在 Linux CI/服务器上跑容器全量。

### 33.6.4 .dockerignore 与镜像瘦身

```text
.venv/          # 绝不能进镜像（Windows 解释器 + 几百 MB）
results/        # 运行产物
.git/ .audit/   # 版本/审计
__pycache__/    # Python 缓存
simulators/*.log  simulators/*.pid  simulators/*_state.json   # 运行时状态
```

**常见坑**：忘记排除 `.venv/` 会把本机 5 万个文件打进镜像（构建慢、镜像大、还可能
把 Windows 的 `.exe` 混进 Linux 镜像）。`.dockerignore` 与 `.gitignore` 思路相同，但**必须单独写**。

### 33.6.5 在 CI/GHCR 上构建的建议（本任务不引入 docker job）

本地/CI 不需要立刻加 Docker 任务（会增加 CI 复杂度且难本地验证）。推荐路线：

```yaml
# 未来可选：只在 main 分支构建并推到 GHCR
build-image:
  if: github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  permissions:
    contents: read
    packages: write
  steps:
    - uses: actions/checkout@v4
    - uses: docker/setup-buildx-action@v3
    - uses: docker/login-action@v3
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}
    - uses: docker/build-push-action@v6
      with:
        push: true
        tags: ghcr.io/${{ github.repository }}:latest
```

## 33.8 CANoe 对接：以"分析"和"录制"为主

### 33.8.1 真实工作中 CANoe 的位置

CANoe/CANalyzer 是 Vector 的商业总线工具，行业标配，负责：

- **总线监控/分析**：看报文、周期、信号、Trace（`.asc`/`.blf`）；
- **仿真节点**：CAPL 脚本模拟 ECU；
- **诊断控制台**：发 UDS 请求；
- **自动化**：通过 **CANoe COM API**（Windows COM，Python 用 `pywin32`）控制工程。

### 33.8.2 Python 调 CANoe COM API（示例代码，本项目不依赖 pywin32）

> 只在装了 CANoe 的 Windows 办公机/台架上可用；本项目没有 license，所以只给**可迁移的写法**。

```python
# 需要：pip install pywin32   （真实台架环境才装；本项目不引入）
import win32com.client

app = win32com.client.Dispatch("CANoe.Application")   # 启动/连接 CANoe
app.Open(r"C:\Vector\Projects\Cockpit\Cockpit.cfg")   # 打开 CANoe 工程（.cfg）

measurement = app.Measurement
measurement.Start()                                    # 开始测量（开始收/发总线）

# 通过 COM 访问总线对象（不同 CANoe 版本对象模型略有差异，按实际工程调整）
bus = app.Networks.Item(1).Buses.Item(1)

# 示例：等 10 秒测量，然后停止并把测量结果导出为 ASC
import time; time.sleep(10)
measurement.Stop()

# CANoe 的 Trace 导出通常走 Measurement/Logging 配置；
# 最简单的通用做法：在 CANoe 工程里配置 Logging 输出 .blf/.asc，
# 然后用本项目的 trace_tools.py 做分析（见 33.8.3）。
app.Quit()
```

**关键认知**：COM API 是"控制 CANoe"的通用入口，但**不同版本对象模型/工程配置差异很大**，
真实项目里工程也会封装成 CAPL/Test Module 或 vTESTstudio 用例。面试时讲清"我用 Python
控制过 CANoe 启动测量/读取总线对象"比背 API 更有说服力。

### 33.8.3 把 CANoe 的 Trace 喂给本项目分析

本项目的 `simulators/trace_tools.py` 已经实现 ASC 读写与校验，可以直接分析**真实台架/实车**
录出来的 Trace（不依赖 CANoe 是否安装）：

```python
import sys
sys.path.insert(0, "simulators")
from trace_tools import verify_asc

frames = verify_asc("results/real_bench_trace.asc")   # [(ts, can_id, dlc, data), ...]
for ts, can_id, dlc, data in frames[:10]:
    print(f"{ts:8.3f}s  0x{can_id:03X}  dlc={dlc}  {data.hex().upper()}")
```

反过来，本项目导出的 `results/bus_trace.asc` / `.blf`（`09`/`01` 套件里的 `Export Bus Trace`）
**可以直接用 CANoe/CANalyzer 打开回放**——这是 13 章"Trace 归档"的行业兼容性亮点。

### 33.9.3 Appium：跨设备/跨平台的标准方案

Appium 适合"一套脚本跑多个车型/多个 Android 版本"：

```python
# pip install Appium-Python-Client   （真机环境才装；需先启动 Appium Server）
from appium import webdriver
from appium.options.android import UiAutomator2Options

options = UiAutomator2Options()
options.platform_name = "Android"
options.automation_name = "UiAutomator2"
options.device_name = "VEHICLE2026AUTO"          # adb devices 里的序列号
options.app_package = "com.vehicle.media"
options.app_activity = ".MainActivity"
options.no_reset = True                           # 不重启 app（车机常驻进程）
options.new_command_timeout = 300                 # 车机响应慢，超时放宽

driver = webdriver.Remote("http://127.0.0.1:4723", options=options)
driver.find_element("id", "com.vehicle.media:id/play").click()
driver.save_screenshot("results/appium_headunit.png")
driver.quit()
```

**Capabilities 要点**：

| capability | 车机场景取值/说明 |
|---|---|
| `platformName` / `automationName` | Android / UiAutomator2 |
| `deviceName` | `adb devices` 里的序列号（车机通常是固定序列号） |
| `appPackage` / `appActivity` | 被测应用；`no_reset=True` 保留车机常驻状态 |
| `newCommandTimeout` | 车机慢，建议 300s |
| `uiautomator2ServerLaunchTimeout` | 老车机可加大（默认 20s 常见超时） |

### 33.9.4 三种车机测试路线怎么选

| 路线 | 优点 | 缺点 | 本项目对应 |
|---|---|---|---|
| adb 命令（mock/真机） | 最轻、最稳、CI 友好 | 只能测"命令行能看到的状态"，测不到 UI 细节 | `AdbLibrary` + `adb_sim` |
| UiAutomator2 | 直接操作真实 UI、无 Server | 车机系统可能限制（部分 AAOS 无 uiautomator dump 权限） | 本章示例 |
| Appium | 跨设备/跨版本、生态成熟 | 重、要维护 Appium Server、车机兼容性要调 | 本章示例 |
| HMI 视觉比对（25 章） | 能测像素级 UI 缺陷 | 不能驱动交互 | `09_hmi_vision` |

**真实项目里通常是组合拳**：adb/UiAutomator2 驱动交互 + 视觉/状态断言验证结果 + CAN/Trace 验证底层信号。

## 33.10 HIL 台架对接：把"仿真 IO"换成"真实 IO"

### 33.10.1 HIL 是什么

HIL（Hardware-in-the-Loop，硬件在环）= **真实 ECU 硬件** + **电脑仿真其余整车环境**
（传感器/执行器/总线/电源）。真实 Tier1 的座舱测试大部分自动化跑在 HIL 台架上：

- **dSPACE SCALEXIO / AutomationDesk**：德国主流 HIL 平台；
- **Vector VT System + CANoe**：Vector 生态（VT7001 电源、VT 板卡 IO）；
- **自研台架**：可编程电源 + CAN 卡（CANable/Vector XL）+ 工控机。

### 33.10.2 关键思路：抽象一个 TestIO 接口层

本项目所有测试都通过 `libraries/` 和 `simulators/bus.py` 访问"总线"。
接台架时**不是重写用例**，而是把底层实现换成"真实 IO 适配器"：

```python
# 抽象层（示意）：系统测试只依赖这个接口，不关心底层是 UDP 还是 CAN 卡
from typing import Protocol, Optional

class TestIO(Protocol):
    def send_frame(self, can_id: int, data: bytes) -> None: ...
    def recv_frame(self, timeout: float = 1.0) -> Optional[tuple]: ...
    def wait_frame(self, can_id: int, timeout: float = 5.0) -> tuple: ...

class SimulationIO:                      # 现有：UDP 组播（simulators/bus.py）
    ...

class VectorHardwareIO:                 # 台架：真实 CAN 卡
    def __init__(self, channel: int = 0, bitrate: int = 500_000):
        import can
        self._bus = can.Bus(interface="vector", channel=channel, bitrate=bitrate)

    def send_frame(self, can_id: int, data: bytes) -> None:
        import can
        self._bus.send(can.Message(arbitration_id=can_id, data=data, is_extended_id=False))

    def recv_frame(self, timeout: float = 1.0):
        msg = self._bus.recv(timeout=timeout)
        return None if msg is None else (msg.timestamp, msg.arbitration_id, len(msg.data), bytes(msg.data))
```

替换点清单（真实项目改造时按这个顺序）：

| 位置 | 仿真（当前） | 台架（改造） |
|---|---|---|
| `simulators/bus.py` | python-can `udp_multicast` | python-can `vector` / `socketcan` / `slcan` |
| `resources/common.resource` 的 `Start/Stop Vehicle Environment` | 起 `ecu_sim.py` 等进程 | 连接 HIL 工程、上电、启动测量 |
| `libraries/VehicleBusLibrary.py` | 走虚拟总线 | 走真实 IO 适配器（接口不变） |
| 故障注入 | 工程模式 DID F1B0（仿真） | HIL 的故障注入板卡 / 可编程电源（真异常） |
| 电源管理场景 | 仿真 NM 报文 | VT7001/可编程电源控制 IGN/电压 |

### 33.10.3 HIL 自动化的三个硬点

1. **时序/实时性**：真 ECU 的响应、总线负载、测试步间隔都需要实时性保证（HIL 平台是硬实时）；
   Python 脚本通常作为"上位机调度"，关键动作交给 dSPACE/CANoe 的实时侧执行。
2. **资源独占**：台架是稀缺资源，自动化框架要处理排队、锁、运行失败时的安全回滚（关电源/停测量）。
3. **安全**：真 ECU + 真电源的故障注入可能损坏样件，必须按台架 SOP 来（电压/温度/脉冲限值）。

> 💡 **面试话术**："我的项目是纯软件仿真（等价于 SIL），但我把测试库抽象成了 TestIO 接口，
> 换真实 IO 只需改适配器；HIL 台架自动化本质就是把'仿真进程'换成'台架控制 + 实时侧调度'。
> 我知道 HIL 的硬点是实时性、资源锁和样件安全。"

| # | 问题 | 要点 |
|---|---|---|
| 1 | pytest 和 Robot Framework 怎么分工？ | pytest=单元/逻辑（毫秒级、开发者反馈）；RF=系统/验收（多进程/总线/报告给客户）。不要互相替代 |

| 4 | 矩阵下 upload-artifact 要改什么？ | artifact 名字必须带 `${{ matrix.python-version }}`，否则同名冲突 |
| 5 | Docker 里为什么先 COPY requirements.txt 再 COPY 代码？ | 利用镜像层缓存：依赖不变时不用重新 pip install |
| 6 | .dockerignore 必须排除哪些？举 4 个 | `.venv/`、`results/`、`.git/`、`__pycache__/`（还有 .audit/、日志/state） |

| 9 | 本项目导出 Trace 怎么和 CANoe 互操作？ | 导出 ASC/BLF → CANoe 可直接打开；CANoe/台架录的 ASC 可用 `trace_tools.verify_asc` 分析 |

| 11 | HIL 对接时用例要不要重写？ | 不用。抽象 TestIO 接口，替换 `simulators/bus.py` 等底层适配器即可 |
| 12 | HIL 自动化的三个硬点？ | 实时性、资源独占（锁/排队）、样件安全（故障注入 SOP） |

## 33.13 本章小结

- **pytest 层**（`tools/pytest_style/`，4 个测试文件 / 30 个 test case / 0.45s）负责纯逻辑与数据质量；
- **RF 层**（276 用例 / ~6 分钟）负责系统级仿真验证；
- **CI** 用 Python 版本矩阵 [3.12, 3.14] + pytest 快速失败 + artifact 归档，把两层串成流水线；
- **Docker**（`Dockerfile` + `.dockerignore`）把"环境"变成一条命令；
- **外部工具**：CANoe 走 COM API / Trace 互操作，Appium/UiAutomator2 接真实车机，
  HIL 台架通过 TestIO 抽象层替换仿真 IO —— 用例资产不重写。

> 🎯 **岗位价值**：System Validation 工程师不止"会跑用例"，而是**让验证可复现、可回归、可交付**。
> 这一章的四件套（pytest / CI 矩阵 / Docker / 工具链接口）就是最直接的证据。
